## 1. 需求解读与翻译

### 1.1 客户原话(节选)

> 我们目前大概是 200 人的电商公司,全公司各部门都要使用,财务,人事,行政,视频部,电商业务部。目前想给他们做一个定制化的企业智能体办公工具,数据库能集成进去最好,然后我们已经搭好了很多定制化的 Dify 工作流,尤其是针对职能部门的场景并做好接口可以做成 skill,目前想要做成部门成员与部门成员之间的专属 skill 隔离,因为财务的很多工作流别人是不能使用的,然后大老板是能够看到所有部门情况的,而且我们希望后台能够看到每一条调用的过程,方便我们的定制工作流出问题了可以立马找到原因。

### 1.2 逐句拆解

| # | 原话 | 真实意图 | 关键约束 |
|---|------|---------|---------|
| 1 | 200 人的电商公司 | 组织规模中等偏大,纯行政分发不可行 | 需要「管理员集中管理」而非每人一台 DIY |
| 2 | 全公司各部门都要用:财务、人事、行政、视频部、电商业务部 | 多部门、多职能并行使用 | 必须有多用户 + 组织架构(部门) |
| 3 | 定制化的企业智能体办公工具 | 不是通用聊天助手,是围绕本公司业务场景定制的生产力平台 | 平台化 + 可定制扩展 |
| 4 | 数据库能集成进去最好 | 希望 AI 能直接查业务数据(订单、库存、财务账等) | 数据库连接能力 + 连接级授权 |
| 5 | 已搭好很多定制化 Dify 工作流(接口已做好,可做成 skill) | 已有存量 AI 资产(Dify),不想推倒重来,要求接入/编排 | Dify 工作流 → Skill 的适配层 |
| 6 | 部门成员之间的专属 skill 隔离,财务的工作流别人不能用 | 部门级权限隔离(可见性 + 可调用性双重要求) | Skill 挂「所属部门」,授权模型按部门解析 |
| 7 | 大老板能看到所有部门情况 | 需要跨部门全局视角的超级角色 | 老板角色,不受部门隔离限制,另有数据总览 |
| 8 | 后台能看到每一条调用的过程,出问题立马找到原因 | 全链路审计 + 可观测性(谁、何时、用了哪个 skill、输入输出、成败、耗时) | 审计事件持久化 + 管理后台检索/回溯 |

### 1.3 显性需求清单(可直接验收)

1. 多用户登录,用户归属于部门(财务 / 人事 / 行政 / 视频部 / 电商业务部)。
2. 每个用户只能看到并调用**本部门**被授权的 Skill(含对接的 Dify 工作流)。
3. 部门外不可见、不可调用、不可搜索到其他部门的 Skill(财务场景尤其强调)。
4. 「老板」账号拥有跨部门查看/调用/总览权限(需定义是全部放开还是只读总览)。
5. 数据库集成:平台侧统一管理数据库连接,Agent 可查询;敏感连接(如财务库)同样按部门/角色授权;写操作默认只读防护。
6. 后台管理页:查看每一条调用的完整过程(用户 → 会话 → Skill → Dify 工作流调用 → 输入输出 → 状态 → 耗时),可按时间/部门/用户/Skill/结果筛选,支持排障。

### 1.4 隐性需求(客户没说但必然存在)

| 隐性需求 | 原因 |
|---------|------|
| 模型密钥统一管理(企业统一采购,而非每人 BYOK) | 200 人不可能各自配 key;财务要成本可控 |
| 用量与成本按部门归集 | 老板要看全局 → 必然关心各部门花了多少 |
| 管理员能做 Skill 上下架、授权调整、账号管理 | 「定制化 + 全公司用」必然要运营角色 |
| 数据合规与保密边界(财务数据不出内网) | 财务内容敏感,多数会要求私有化部署 |
| 权限模型要能解释「老板能看一切」 | 需要有角色分层,不是简单部门过滤 |
| 账号来源贴近客户已有身份源(飞书/钉钉通讯录) | 200 人公司日常维护成本与入职离职节奏决定 |

### 1.5 一句话结论

> 客户要的不是「桌面软件的批发授权」,而是一个**私有化部署、以桌面壳为界面、带组织架构与部门级权限、能接入存量 Dify 工作流与业务数据库、带全链路审计后台的企业级 Agent 平台**。
>
> 补充(本轮新增):客户**正是因为桌面壳的视觉与体验才对产品感兴趣**,因此企业版界面必须是桌面壳本身(或其同源视觉),而不是另起一套粗糙的 Web 界面。

## 2. 关键产品决策(必须先读)

### 2.1 决策总表

| # | 决策点 | 结论 | 理由 / 备注 |
|---|--------|------|-------------|
| D1 | 客户端形态 | **以开源版为基线整树复制 → 独立企业代码库,不做 Web** | 客户被桌面壳视觉吸引;Web 版是"另造一个不漂亮的界面"。整树复制(桌面壳+全部内核包)保证单机功能与能力完整,企业改动 100% 落在独立库里,见 §8 |
| D2 | 单机功能 | **桌面壳全部单机功能保留**,云端是登录后的叠加层 | 员工既能用完整单机功能,也能用云端;未登录 = 今天的壳 |
| D3 | 云端服务 | **必须自研、随企业版交付**(不是客户已有,也没有现成货架产品) | 见 §6、§11 |
| D4 | 部署形态 | 私有化单租户(内网或客户云),不是 SaaS 多租户 | SaaS 是 v2/P2 之后再评估 |
| D5 | 授权模型 | 复用开源 `capability-runtime` 的 Capability Grant + audit 语义;主体扩展为用户/部门/角色;**默认拒绝** | 见 §5 |
| D6 | 执行位置 | 对话在桌面壳本地内核运行;**云端不跑 Agent**,只做身份/授权/审计/网关 | 模型密钥可不上收;云端只"裁决与记账" |
| D7 | 界面与安全分层 | UI 收敛(体验)+ 目录收敛(数据)+ 调用断言(安全),三层都要做 | UI 隐藏不等于安全,本地应用可被调试 |
| D8 | 管理权与数据可见权 | **分离**:管理员管系统不碰业务数据;老板看业务数据不改授权 | 防止"能看财务数据的人能给自己加权限" |
| D9 | 老板视角 | 首期 **全部部门只读 + 全局审计**;可写/例外需客户确认 | 财务场景只读更安全 |
| D10 | 企业数据边界 | 企业数据只经云端网关返回界面,**不落本地盘**;本地调用不进企业审计 | 财务敏感 + 审计可信 |
| D11 | 授权裁决权威 | 策略只存在云端;员工壳只有会话与策略快照(有过期) | 防"拔网线 = 永久全权限";本地文件不可自证 |
| D12 | 账号来源 | 初始化码 → 组织管理员 → 建号/CSV 导入/身份源同步(见 §6.3) | 账号唯一权威副本在云端数据库 |
| D13 | 代码组织 | **基线复制·独立一套**:在开源版某发布点整树下载代码 → 建独立企业仓库(不与开源 git 关联)→ 企业改动只进企业仓库;开源仓库零改动、只做开源 | 本轮定稿:不 fork、不把企业代码先塞进开源仓库再拆;开源不发布 npm 包 → 内核层只能随整树复制获得,不阉割单机桌面壳,同时承载云端企业能力(§8) |

### 2.2 形态演进记录(为什么最终是桌面壳 + 云端)

- **v1 假设(早期)**:Web 对话工作台为主入口 + IM 机器人次要 + 桌面端可选。**否决**:客户正是被桌面壳视觉吸引,且"不丢失单机功能 + 复用桌面壳体验"诉求强烈;Web 会引入第二套 UI 维护成本,且达不到桌面壳质感。
- **v1.5 假设**:企业版 = 纯桌面壳收敛版(员工无 dock、看不到管理入口)。**部分采纳**:员工端收敛仍然成立;但用户明确要求"不丢失桌面壳已有的单机功能" → 收敛不等于阉割,而是"单机世界全保留 + 云端世界按角色叠加"。
- **v2(本方案)**:**混合形态** —— 完整桌面壳 + 登录后叠加企业世界;管理员/老板/员工同一安装包、不同身份看到不同世界。
- **v3(本轮定稿)**:代码组织确定为「基线复制」——在开源版某发布点整树下载代码,建立**完全独立**的企业仓库(独立 git、私有 remote),在其上实现企业版;**不是 fork 开源代码,也不是把企业代码先放进开源仓库再迁移**。开源仓库保持纯净、只做开源演进;复制范围 = **整树全量**(桌面壳 + 全部内核 packages)——因为开源不发布 npm 包,不复制即不可用,见 §8。

### 2.3 "桌面壳能否实现企业版"的直接回答

能,但前提是先认清:桌面壳当前**没有任何账号/服务器/远程概念**(已查证 main 层无 login/account/cloud)。企业版的三条命脉(账号与部门结构、授权策略、审计聚合)都要求一个**中央权威点**。所以:

> 桌面壳实现企业版 = **基线复制整套开源代码(整树)+ 新增登录 + 接一个自研云端服务**(飞书/钉钉桌面端的模式),而不是"给单机壳加几个企业页面"。整树复制让企业版成为完全独立、离线可控的一套(见 §8)。

云端服务**没有 UI、不叫 Web**:组织管理、授权矩阵、审计台这些"管理界面"全部做在桌面壳内(见 §7)。

## 3. 与现状的差距分析

### 3.1 可直接复用的现成资产

| 仓库现状 | 对企业版的用处 |
|---------|--------------|
| Agent 内核(`coding-agent`/`agent`/`ai`),宿主无关,已跑在 desktop / CLI / im-gateway | 桌面壳本地对话直接复用,无需改动 |
| `capability-sdk` / `capability-runtime`:Capability ID Grant、AccessSession、constraints、**audit hooks**([access.ts](/Users/zhugeyue/Desktop/project/bigdate/source-code/astravia/packages/capability-runtime/src/access.ts)) | 天然的授权与审计底座;企业版把 grant 主体从「本机功能」扩展为「组织主体(用户/部门/角色)」,审计事件形状直接对齐 |
| 桌面壳 UI 分层:`@astravia/ui` + `@astravia/theme-sdk` + `@astravia/theme-ui`(仓库内源码,随整树复制) | 企业 UI(登录页/组织管理/授权矩阵/审计台)与桌面壳同源同视觉,无需复制 desktop 私有代码做 UI |
| dock/页面入口注册机制:renderer 的 `registerActivityTab` 带 `hasPermission(plugin, "ui.slot.activity-tab")` 检查 | 「按权限决定 UI 出现什么」是产品内建机制;企业版把判定源从插件 manifest 换成云端角色策略即可 |
| 数据库引擎 dbx(40+ 数据库、写分级授权、prod 默认只读)——位于 **PRIVATE** `desktop-app/src/main/database` | 客户「数据库集成」的能力主体存在;需从 Electron 壳提取为服务端模块(见 §8.3) |
| Skill 机制(`SKILL.md` + manifest + 市场分发)、MCP 接入 | Dify 工作流封装为 Skill 的承载机制已存在;缺「按部门下发/隔离」 |
| `runtime-telemetry`:RuntimeTracer 契约 + Langfuse exporter(支持 userId/sessionId/tags) | 审计与调用链可观测性的技术底座(私有化 Langfuse 或自建均可) |
| im-gateway(IM 入口,飞书已通) | 次要入口(IM 机器人)现成;企业版按需带走 |
| 批量任务 / 定时调度 / 通知 | 企业办公场景(日报、批量处理)可直接平移 |
| 首次启动引导窗口模式(`onboarding-window.ts` + `renderer/onboarding`) | 企业登录窗口照此模式做,不发明新范式 |

### 3.2 完全缺失、需要新建的部分(企业版核心增量)

| 缺失项 | 说明 |
|-------|------|
| **身份与组织** | 账号、登录、部门树、角色——现状是「无账号」本地单机 |
| **组织级授权模型** | 把单机 Capability Grant 泛化为「主体=用户/部门/角色 × 资源=Skill/数据库连接/工具」,含部门隔离与老板放行 |
| **云端服务(Server / API)** | 认证、组织、授权、审计、Dify 网关、数据网关——现状核心库无网络服务形态 |
| **审计存储与调用链检索** | 每条调用落库可查,按部门/用户/Skill/时间/状态过滤与单条回溯 |
| **企业 Skill 资产库与受管分发** | 内部 Skill 集中存储、版本、授权、按部门发布(owner_department) |
| **Dify 适配层** | 把已就绪的 Dify 工作流接口标准化封装为 Skill(鉴权、入参出参映射、错误透传) |
| **模型密钥集中管理** | 企业统一 key/网关(基线复制后的桌面壳改造点;若对话留在本地则按需) |
| **企业 UI 域**(登录/组织管理/授权矩阵/审计台) | 全部做在桌面壳 renderer 内(见 §7) |

### 3.3 定位判断

仓库是「本地优先、单机、BYOK」的产品哲学;企业版是「集中管控、多用户、私有化」。**产品形态级差异是研发计划的第一矛盾**——本方案用「混合形态」(单机世界 + 云端叠加)化解:不是改造单机内核,而是给它接上身份、授权、审计与云端服务。

| | 开源桌面版 | 企业版桌面壳(同安装包,登录区分) |
|---|---|---|
| 账号 | 无(本地单机) | 登录企业账号后带 `{userId, departmentId, role}` |
| dock | 全部单机入口 | 单机入口全保留 + 企业区按角色出现 |
| 能力目录 | 本地已装 Skills | 本地 Skills + 云端按部门下发的企业 Skills(带"企业"徽标) |
| 审计 | 本地无企业审计 | 企业调用全审计;本地调用不进企业审计(默认) |
| 数据 | 本地文件/本地连接 | 同上 + 经云端网关只读查询企业数据(结果不落盘) |

### 4.3 单机功能不丢的实现原则

1. 基线复制后,现有 `src/main` 各域(conversations/capabilities/skills/filesystem/knowledge/database/mcp/plugins/sandbox/scheduler/...)与 `preload`/`renderer` **只加不改**;
2. 企业代码全部集中在新增的 `enterprise/` 命名域与 `domains/enterprise/*`(见 §8.2);
3. e2e 固定跑一条「登录前后单机功能回归」用例防漂移。

## 5. 角色与部门管控设计(核心)

### 5.1 授权模型:五张表 + 一次查表裁决

沿用仓库已有 Capability Grant + audit 语义,把主体维度从「本机/单功能」提升为组织维度。云端核心数据 = 五张表:

```
users(账号)        →  id/工号 · 密码哈希 · department_id · role
departments(部门)  →  财务部/人事部/行政部/视频部/电商业务部
roles(角色)        →  员工 | 部门主管(预留) | 组织管理员 | 老板
skills(资源)       →  企业 Skill 统一登记:id/名称/owner_department/类型(Dify工作流|数据源)
grants(授权)       →  唯一的"谁能用"事实:授权给谁(部门|角色|用户) × 对象资源 × 范围(完整|只读)
audit_logs(审计)   →  每次放行调用记一条
```

**规则:默认拒绝。grants 表里写了才允许。** 部门隔离 = grants 表里没有给人事部的人写"报销核对"这一行——请求到云端,查表,查无此行,拒绝。不可见、不可调、不可搜。

授权判定:

```
subject  = (userId, departmentId, role)
resource = Skill(owner_department) | 数据库连接 | Dify 工作流
policy   = 显式 Grant:<部门|角色|用户> → <资源> → allow(scope)
默认拒绝:无 Grant 即拒绝
```

### 5.2 角色定义与"快捷方式"

| 角色 | grants 里实际是什么 | 界面可见 |
|------|--------------------|---------|
| 员工 | `本部门 → 本部门 Skill + 本部门数据源(只读)`(自动一行) | 企业工作台 + 我的调用记录 |
| 部门主管(预留) | 员工 + `本部门 → 本部门审计查询` | 同上 + 本部门审计 |
| 组织管理员 | `全部资源 → 可配置/可授权`,**无业务数据读写权** | 企业工作台 + 审计台 + 组织管理 |
| 老板 | `全部部门资源 → 只读`,审计全局只读 | 企业工作台(带部门切换器)+ 审计台 |

### 5.3 界面三层收敛(UI 层、目录层、调用层)

| 层 | 位置 | 机制 |
|----|------|------|
| ① UI 注册层(体验) | renderer dock/路由/页面入口 | 渲染自云端下发的可见性清单;员工 dock 下半段只有"企业工作台",**审计/组织管理代码路径不渲染**(不是按钮变灰) |
| ② 内容目录层(数据) | 能力目录、引导语、数据源列表 | 按 `(departmentId, role)` 返回;其他部门 Skill 连名字都不出现 |
| ③ 调用断言层(安全,命门) | main 进程 + 云端 authz | UI 可被调试绕过;真正拦截在 capability 授权断言 + 云端 authz——按 subject 拒绝,与 UI 显示无关 |

**为什么必须做第 ③ 层**:桌面壳是本地应用,懂技术的人可改路由/直接发调用。授权只在 UI 藏 → 形同虚设。策略只存在云端,壳里只有会话 + 有过期时间的策略快照。

### 5.4 管理权与数据可见权分离

- 管理员 = 管系统的人(建账号、配授权、看审计),**不需要看财务报表具体数字**;
- 老板 = 看业务的人(看所有部门数据),**不需要能改授权**;
- 二者混一则出现"能看财务数据的人同时能给自己加权限",审计失去意义。

### 5.5 数据面隔离

- 数据库连接凭据只存云端密钥库,不下发到用户端;查询经云端代理执行;
- 跨部门表结构不进提示词(数据面隔离);
- 企业数据查询结果只回界面,禁止被本地"写文件/保存到工作区"类工具二次落盘(首版 UI 提示 + 审计;后续可升级正式 DLP);
- 保持默认只读 + 行数/超时上限(单机 dbx 已有能力平移)。

### 5.6 需要建模确认的点

1. 一人是否可属多部门(如电商部兼财务对账员)?→ 表结构预留多对多;
2. 是否需要"部门主管"档?(客户只提老板/管理员,但主管看本部门大概率会被提出)→ 角色位先预留;
3. 老板"看所有部门"的范围:全放开 vs 只读总览 vs 只读 + 敏感字段脱敏(员工身份证号等)→ 客户确认。

## 6. 云端服务:功能模块与账号体系

### 6.1 云端是什么、装在哪

- 一个 **TypeScript/Bun 后台进程,无窗口无网页**,跑在客户内网一台普通电脑/Docker 上;
- 200 人规模一台办公机绰绰有余;数据全内网,不出公司;
- 内部模块与客户需求一一对应(见图 §4.1 ①②③④⑤)。

### 6.2 桌面壳 ↔ 云端怎么对话

不是网页,是**内网 HTTPS 请求**(与桌面壳现调本地能力同理,目标从"本地"换成"内网机器"):

```
桌面壳                         云端
  │ 1. 登录(工号+密码) ────────▶ │ 查表:财务部·员工 → 签发会话 token + 策略快照
  │ ◀─ 会话 + 身份 + 可见性清单 ─ │
  │ 2. 渲染:单机全量 + 企业区(仅财务部可见项)
  │ 3. 调"报销核对" ──带 token─▶ │ authn 验 token → authz 查 grants → 放行
  │                              │ 调 Dify 工作流(密钥在云端) → 记审计
  │ ◀─ 结果 + traceId ────────── │
  │ 4. 显示结果卡(来源:财务库·只读 + trace 调用链)
```

离线:壳用策略快照继续已授权功能,快照过期强制重连校验。

### 6.3 账号是怎么来的(云端账号体系)

**原则:账号/部门/角色唯一权威副本在云端数据库。** 员工电脑上没有可编辑的账号文件——本地可被本人调试,存本地等于可自改角色。

| 步骤 | 谁做 | 干什么 |
|------|------|--------|
| 1 | 客户 IT 或你 | 内网一台机器装云端服务;首次启动屏幕显示**一次性初始化码**(像路由器管理密码) |
| 2 | 同上 | 打开桌面壳 → 输入初始化码 → **创建第一个账号:组织管理员(超管)** |
| 3 | 管理员 | 桌面壳"组织管理"页:建 5 个部门 → 建账号 / **Excel(CSV)导入 200 人** / **对接飞书·钉钉通讯录自动同步(SCIM)** |
| 4 | 员工 | 拿到工号密码 → 桌面壳登录 → 看到本部门世界 |

- 有身份源(飞书/钉钉/企微/AD)→ OIDC/SSO 免密 + 通讯录同步;入职自动有号、离职自动回收;
- 无身份源 → 管理员手工建 + CSV 导入起步,后续再加;
- 部门与角色**不在登录时让用户自选**,云端查表后打进会话;角色变更改表后重登/同步生效;离职停号 → 旧会话吊销(复用现有 `access.ts` 的 revoke 语义)。

### 6.4 会话与安全底线

- 密码只存哈希;会话 token 有时效可吊销;
- 内网 HTTPS(自签证书);
- 审计日志只追加、不可被普通账号删;
- 云端数据库定期备份。

**日常**:企业工作台问"对一下昨天 3 笔报销" → 云端放行 → Dify 工作流 → 结果卡(来源 + traceId)。问人事部 JD 起草 → 云端查无此行 → 界面友好拒绝"不在你的可见范围"。随时切回单机区用本地功能(不进公司审计)。换部门 → 重登自动换技能集;离职停号 → 登录被拒。

### 7.4 老板使用流程

登录 → dock 有"企业工作台 + 审计"、无"组织管理" → 工作台顶部部门切换器 → 看各部门应收/招聘/销量周报(全部只读)→ 审计台看全局调用(只读)。管系统的人(管理员)和看数据的人(老板)分开。

## 8. 代码组织:基线复制 · 独立一套(不做 fork、不混开源仓库)

### 8.1 复制方式(本轮定稿)

> **基线复制,不是 fork**:在开源版某个发布点(建议正式发版 tag)**整树下载一份代码**,以此作为企业版基线,在**完全独立的仓库**中修改与演进。企业版从第一天就是独立的一套代码,与开源仓库没有任何 git 派生/追踪关系;开源仓库保持现状、零改动、专做开源。

| 问题 | 结论 |
|------|------|
| 基线取自 | 开源版某发版 tag 的整树快照 |
| 复制范围 | **整树全量**:desktop-app + ai/agent/ui/theme-*/capability-*/runtime-* 等全部 packages |
| 为什么必须是整树复制 | 开源不发布 npm 包,内核要进企业版**只能复制源码**;单机桌面壳功能不阉割,云端企业能力在同一套代码上叠加 |
| 开源仓库 | **零改动**:不新增目录、不改配置、不提交任何企业代码 |
| 企业仓库 | 独立目录 + 独立 git(私有 remote),与开源仓库无关联 |
| 后续演进 | 两边并行独立;吸收开源改进靠「diff 对照移植」(§8.4),不靠 git merge |

### 8.2 企业版仓库结构(独立一套,示例)

```
astravia-enterprise/                     ★ 企业版独立仓库 = 开源整树快照 + 企业增量
├── packages/                            ← 开源基线整树(复制于某发版 tag)
│   ├── desktop-app/                     ★ 桌面壳企业版:在复制副本上直接改造
│   │   └── src/
│   │       ├── main/                    (单机 40+ 域原样保留,只加不改)
│   │       │   └── enterprise/          ★ 新增:enterprise-client / auth-session /
│   │       │                                cloud-bridge / audit-sink
│   │       ├── preload/apis/enterprise.ts    ★ 新增(登录/会话/调 Skill/查审计)
│   │       ├── renderer/
│   │       │   ├── router.tsx                (追加企业路由)
│   │       │   ├── root-layout/              (dock 企业区按身份动态渲染)
│   │       │   └── domains/enterprise/       ★ 新增:login / workspace / org-admin /
│   │       │                                    grant-matrix / audit-console /
│   │       │                                    scope-switcher
│   │       └── shared/enterprise-ipc.ts      ★ 新增
│   ├── …(agent / ai / ui / theme-* / capability-* / runtime-* … 全部随整树复制,一般不改)
├── enterprise/                           ★ 纯企业增量(独立命名域,便于对照与同步)
│   ├── apps/server/                      ★ 云端服务(无 UI)——见 §6
│   │   └── src/
│   │       ├── main.ts                   ← HTTP 启动 + 初始化码 + 关闭钩子
│   │       ├── http/
│   │       │   ├── routes/               ← auth / org / grants / skill-proxy / data-proxy / audit
│   │       │   └── middleware/           ← authn(token→subject) + authz(默认拒绝)
│   │       ├── db/                       ← migrate(五表)+ seed(初始化码/超管)
│   │       ├── config/                   ← 端口/DB 路径/Dify 凭据/密钥
│   │       └── lib/                      ← bootstrap / session-store
│   ├── packages/                         ★ 企业共享库(内部 scope)
│   │   ├── contracts/                    ← API 契约与共享类型(唯一事实源)
│   │   ├── iam/                          ← 身份:账号/部门/角色/会话
│   │   ├── policy/                       ← 授权:grants + decide()(默认拒绝)
│   │   ├── audit-store/                  ← 审计落库 + 查询 + traceId 关联
│   │   ├── dify-gateway/                 ← Dify 工作流 → 企业 Skill 适配
│   │   ├── data-gateway/                 ← 数据库只读代理(复用提取的 dbx)
│   │   ├── enterprise-client/            ← 桌面壳↔云端 SDK
│   │   └── enterprise-ui/                ← 企业 UI 组件(基于 public ui/theme-*)
│   ├── deploy/                           ← docker-compose / init / env.example
│   ├── docs/                             ← 部署/管理员/客户文档
│   └── e2e/                              ← 授权隔离/审计回溯/单机不丢 验证
└── package.json                          (企业 workspace 根)
```

要点:
- 桌面壳的改造直接发生在复制后的 `packages/desktop-app` 上(登录/根布局/企业区必须动这里);
- 企业新增的代码全部收在 `enterprise/` 下,与基线文件天然分界,做 diff 对照时不会被增量干扰;
- 开源仓库从头到尾不被触碰——不建 `enterprise/` 目录、不改 `.gitignore`、无任何企业提交。

### 8.3 dbx 提取(整树复制后的关键动作)

dbx 数据库引擎位于 **PRIVATE** `packages/desktop-app/src/main/database`,不在任何 public 包 —— 企业版"数据库集成"最依赖它。整树复制后它已随桌面壳进入企业仓库,处置三选一:

1. **提取复制(推荐,快)**:在**企业仓库内**把该域抽成独立模块 → `enterprise/packages/data-gateway`,改造为纯 Node 服务端模块(去 Electron 依赖)。复制的是 Apache-2.0 代码,合法;需自行补齐导出/类型边界(它此前未作为独立库发布)。
2. **上游源码重构(仅用于回馈开源社区)**:开源仓库把 dbx 在**源码级**整理为独立模块/目录(仍不发布 npm),改善开源侧结构、方便社区自取;企业版不依赖任何发布动作,仍用企业仓库内的提取副本(选项 1),保持版本自治(§8.5-6)。
3. **自研替代**:不推荐,重复造轮子。

> 这是整树复制后真实工作量之一,已计入路线图(P1)。

### 8.4 与开源版并行演进(同步策略)

企业仓库不是开源仓库的 git fork,没有 upstream 自动跟踪;开源版持续演进时,企业按需吸收:

1. 开源每发一个值得跟的版本 → 在开源仓库把该 tag 与**企业基线 tag** 做 diff;
2. 评估分类:公共 bug 修复 / 内核能力升级(agent、ai、capability-*)→ 一般值得移植;纯开源社区功能 → 按需;
3. 移植方式:在企业仓库把 diff 应用到对应路径;桌面壳改过的文件(登录/根布局等少数位置)需人工 review 合并;
4. 节奏自定:可数月跟一次,也可长期停在某个基线自维护(整树复制给了完全掌控);
5. 反向:企业代码永不回写开源仓库;只有"内核通用能力"(如 dbx 抽包)以 PR 回馈上游。

### 8.5 开源侧红线(必须遵守)

1. **许可证**:复制的 Apache-2.0 代码在企业仓库保留 `LICENSE` + `NOTICE` 与原版权声明;企业新增代码不受 Apache 约束,可闭源。
2. **git 隔离**:企业仓库独立 git + 私有 remote;企业代码永不进入开源仓库的 git 历史。
3. **开源仓库零改动**:基线下载后,开源仓库不因企业版产生任何提交/目录/配置变更;企业开发只发生在企业仓库。
4. **永不反向**:企业专有代码不进开源仓库;通用能力回馈走开源 PR(§8.3-2)。
5. **长期负担预警**:开源不发布 npm 包 → 企业内一切内核能力只能以**源码复制/移植**获得。整树复制的成本 = 想吸收开源改进时要做 diff 移植。缓解方向:(a) 企业改动集中在 `enterprise/` 增量域,与基线天然分界,diff 面小;(b) 若某内核漂移成本持续过高,可拉长同步周期或只挑关键修复同步;不存在“切到 npm 依赖开源包”的退路(无包可依赖)。
6. **版本自治(唯一路线是源码)**:开源版不发布 `@astravia/*` npm 包 → 企业仓库内所有开源代码都以整树复制获得,内部包互引一律 `workspace:*`(指向本地源码);企业版不存在、也不允许出现对外部 `@astravia/*` npm 包的依赖(该等包不会发布)。构建产物由企业自行打包/私有分发,版本由企业独立掌控。

## 9. Dify 集成与数据库企业化

### 9.1 Dify 工作流 → 企业 Skill(薄适配)

客户已把工作流做成 API——现成的好消息,做一层薄适配:

```
一个 Dify 工作流 = 一个企业内部 Skill:
  SKILL.md   描述触发场景、入参(来自工作流输入)、使用约束
  入口脚本   调用 Dify 工作流 API(按客户已准备好的接口),携带服务端下发的凭据
  元数据     owner_department: 财务 / version / enabled / 可见角色
```

示例:财务 → 报税材料核对、应收账龄分析(仅财务可见可调);人事 → 考勤汇总(仅人事可见可调)。

实施要点:
1. 提供「Dify 工作流 → Skill」标准模板与脚手架(客户侧注册接口即可);
2. 审计天然覆盖:每次 Dify 调用 = 一次带 traceId 的工具调用,鉴权失败/超时/工作流内部错误随审计落库——正是"出问题立马找到原因";
3. **不迁移客户既有 Dify**;Astravia 定位是 Dify 之上的"编排 + 权限 + 审计"面(商务话术,见 §13)。

### 9.2 数据库集成企业化

单机 dbx 能力整体保留(40+ 库、写分级授权、prod 默认只读),企业化增量:
1. 连接由管理员统一登记,按部门/角色授权可见可用(财务库 → 仅财务 + 老板只读);
2. 连接凭据存云端密钥库,不下发用户端;查询经云端代理执行;
3. 默认只读 + 行数/超时上限;跨部门表结构不进提示词;
4. 电商场景常见库开箱:MySQL/PostgreSQL(订单)、ClickHouse(报表)、SQLite、MongoDB 等。

## 10. 审计与调用链回溯

落库一条完整调用链(每条都有 traceId 贯穿):

```
用户(财务-张敏) → prompt → Agent 会话 → Skill:应收账龄分析
                                          └─ Dify API 调用
                                              · 请求参数(脱敏可选) · 响应/错误
                                              · 耗时 / 状态
每次工具调用(tool_execution)也逐条落审计:输入/输出摘要、成败、耗时
```

审计台(桌面壳内,老板/管理员可见)提供:
- 列表:时间、部门、用户、Skill/工作流、状态(成功/失败/超时)、耗时、模型用量;
- 单条详情:完整过程回放(用户说了什么 → Agent 调了哪个 skill → Dify 返回了什么 → 在哪步失败);
- 筛选检索:时间 / 部门 / 用户 / Skill / 结果 / traceId;
- 排障路径:出问题 = 按 traceId 打开详情直接看到失败点,不用翻服务器日志;
- 边界:企业调用全审计;本地单机调用默认不进企业审计(隐私);受管设备策略可另行开启(客户确认)。

技术落地(仓库已有 `RuntimeTracer`/`RuntimeObservation` 契约 + Langfuse exporter,字段支持 userId/sessionId/tags):
- 方案 A(快):私有化 Langfuse 作 tracing 后端 + 自建薄审计表存授权/调用摘要;
- 方案 B(推荐,自控强):自建 audit store(云端库),tracer exporter 写本库,管理台直查,可导出合规审计记录。

## 11. 交付物边界

### 11.1 三种来源(回答"云端是不是单独开发")

| 云端模块 | 来源 | 说明 |
|---------|------|------|
| Dify 工作流 API | **客户的**(对接,不开发) | 云端只"校验→转发→记录",不碰 Dify 内部 |
| 业务数据库(财务库等) | **客户的**(对接,不开发) | 云端只读代理,连接串放云端 |
| 飞书/钉钉通讯录 | **客户的,可选**(对接) | 有则账号自动同步;没有则 CSV 导入,不影响首版 |
| 授权+审计裁决机制 | **开源代码搬**([access.ts](/Users/zhugeyue/Desktop/project/bigdate/source-code/astravia/packages/capability-runtime/src/access.ts)) | subject/grants/审计事件全有,小改即可 |
| 链路追踪契约 | **开源代码搬**(runtime-telemetry) | Langfuse / 自建 exporter |
| 数据库 SQL 引擎(dbx) | **开源代码提取**(desktop-app/src/main/database) | 需提取为服务端模块(§8.3) |
| 桌面壳 | **开源代码基线复制**(整树含 desktop-app) | 单机功能零改动 + 新增企业域(§8.2) |
| 账号/部门/角色 + 登录 | **✍ 必须新写(企业核心)** | 开源版无账号概念 |
| 授权策略存储/配置 API | **✍ 必须新写** | grants 表 + decide() |
| 审计存储与查询 API | **✍ 必须新写** | audit_store + 查询 |
| Dify 网关 + 数据只读代理 | **✍ 必须新写** | 接客户 API/数据库,鉴权转发 |
| 企业 UI 域(登录/组织/授权/审计) | **✍ 必须新写** | 桌面壳 renderer 内,基于 ui/theme-* |
| 部署包/初始化引导 | **✍ 必须新写** | Docker 镜像、初始化码、升级脚本 |

### 11.2 一句话

> **桌面壳开源谁都能 build,但云端这套"账号 + 隔离 + 审计"没人能白拿——它就是企业版的交付物与收费依据。** 客户付的钱主要买这层云端(以及部署、定制、维护);开源代码与客户已有系统只是地基与原料。

交付套装 = 桌面壳企业版安装包 + 云端服务包(Docker + 初始化引导),客户 IT 自装或你/集成商上门部署;每客户一套独立部署(单租户私有)。

## 12. 研发路线图与工作量

### P0 —— MVP:跑通「登录 → 授权 → 调用 → 审计」闭环(单人约 6~8 周)

|------|------|
| 仓库准备 | 在开源某发版点整树下载 → 建独立企业仓库(私有 remote),独立 build 跑通(第 0 天完成,隔离即生效) |
| 桌面壳基线就位 | 复制后的 desktop-app 可独立构建运行,单机功能回归通过 |
| 契约 + iam + policy + audit-store | SQLite 版五表 + 裁决 + 会话 |
| server bootstrap | auth/org/grants/audit 路由 + 初始化码创建超管 |
| enterprise-client + 桌面壳 main/enterprise | 登录窗口(onboarding 模式)+ dock 企业区动态渲染(员工/管理员两种可见性) |

### P1 —— 数据与规模化(全员 200 人)

- Skill 资产库增强:版本、启停、部门管理员自助管理本部门 Skill;

- 批量任务/定时调度按部门授权(人事月报、财务对账定时跑)。

### P2 —— 深度定制与合规

- SSO / 通讯录同步(飞书/钉钉/企微/LDAP),免建账号;

## 13. 商务与产品化建议

1. **对外定位话术**:企业版 = 私有化部署 + 组织与部门权限 + 存量 Dify/内部 API 接入 + 全链路审计的团队级 Agent 平台;界面与体验与桌面版同源(同一桌面壳),不是"另一个粗糙网页"。
2. **审计是最大卖点之一**:客户原话强调"看到每一条调用、出问题立马找到原因"——这是他们对现有 Dify 使用的痛点(黑盒),演示把审计可视化放首位。
3. **不推翻 Dify**:强调"编排 + 权限 + 审计",不是替换其已投入的工作流资产,降低迁移顾虑。
4. **私有化部署是大概率要求**(财务数据),报价按「私有化授权 + 实施/定制」结构;数据面默认内网。
5. **云端 = 交付物边界清晰**(§11),报价单上写明"我们交付什么、需要客户提供什么"。
6. **POC 策略**:第一个试点客户别急着做飞书同步与数据代理复杂面;用"管理员建号 + CSV 导入"起步,Dify 只接已包装好的两三个工作流,先跑通闭环再扩。

## 14. 需要向客户确认的问题(销售/售前清单)

1. 部署位置:客户内网 / 客户云 / 你们托管?(财务数据敏感性决定)
2. 员工客户端:全员装桌面壳企业版(推荐,与单机体验一致);是否需要 IM 机器人作为补充入口(飞书已通)?
3. 账号来源:有无统一身份源(飞书/钉钉/企微/AD)?全员 200 人都有账号,还是先给"需要用 AI 的岗位"开?
4. 「老板看所有部门」的边界:只读总览 + 审计(推荐),还是某些场景可写?财务部门例外豁免怎么定?老板本人登录还是由管理员代查?
5. 敏感字段:老板/跨部门只读时,财务金额等是否要脱敏(如员工身份证号)?
6. Dify 工作流接口形态:数量、鉴权方式(API Key/OAuth)、是否全部可经服务端统一凭据调用?
7. 数据库范围:先接哪些库(业务订单库/财务库/报表库)?财务库是否允许只读查询?
8. 模型密钥:客户统一采购配置在企业版,还是已有统一网关/代理?
9. 审计边界与合规:是否要求审计只覆盖企业调用即可;保留期限、导出、等保要求?
10. 审计的本地单机调用:默认不进企业审计(员工隐私);客户 IT 是否要求受管设备全审计?
