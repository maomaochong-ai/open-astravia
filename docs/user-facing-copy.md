# 面向用户的文案原则

> 本文记录 Vetta **所有面向用户可见文案**的原则：桌面端 UI、官网营销与 FAQ、方案/定价说明等。  
> 读者：写 UI / 官网文案的人、改设置或首页的 agent、做产品交互的人。  
> **不是** API 文档，也不是 i18n 工程规范（桌面见 [ADR-0031](./adr/0031-desktop-i18n-i18next-semantic-keys-main-owned-language.md) 与 `apps/desktop` 的 AGENTS；官网文案在 `apps/site/messages/`）。

适用范围简述：

| 场景 | 典型位置 | 额外注意 |
|------|----------|----------|
| 桌面设置 / 能力 | `desktop` i18n | 结果优先、实现下沉（见 §2–§5、§10） |
| 官网 Hero / 方案 / Q&A | `apps/site` i18n | 产品定位与品牌词统一（见 §1.1、§4.3、§11） |
| 日志 / CHANGELOG / ADR | 仓库文档与代码 | **可以说实现**，不进用户主路径 |

---

## 1. 先认清用户是谁

目标用户**大致知道**产品名词（例如 MCP、模型、知识库），但通常：

- 不知道协议细节、传输类型、配置文件路径、包管理器命令；
- 不关心「怎么实现的」；
- **在意「这东西能帮我做什么」**、开/关有什么影响、下一步点哪里。

因此：

| 可以保留 | 不要默认甩给用户 |
|----------|------------------|
| 产品级名词：MCP、模型、知识库 | 实现级词：stdio、http transport、npx、spawn、mcp.json |
| 浅层动作：添加、关闭、删除 | 内部机制：懒加载、diff-reload、子进程 |
| 结果：对话里能用浏览器 | 手段：Playwright / 命令行参数 |

**用户懂名词 ≠ 用户懂实现。** 文案应假设「知道名字、不了解内核」。

### 1.1 产品定位（写「Vetta 是什么」时）

对外一句话对齐官网 Hero 愿景，**不要**用实现架构当产品定义。

**愿景锚点（中文）：**

> AI 发展很快，但用好它不该成为沉重的学习负担。我们希望让每个人、每个企业都能便捷用上 AI，轻松跟上智能时代。

写「什么是 Vetta」时优先：

| 宜 | 忌 |
|----|----|
| 让人/企业更便捷地用上 AI | 默认写成「AI 智能体工作空间 / Agent 平台 / 工作区」当唯一定义 |
| 减轻学习负担、跟上智能时代 | 先堆模型、工具链、协议清单 |
| 开源可自用、可查看 | 用引擎/沙箱/编排等内部词当开场 |

能力细节（本地文件、批量、知识库等）可以在**功能区块**展开，但**产品自我介绍**先讲愿景与收益。

## 2. 核心原则：说结果，不说实现

每一句用户可见文案，先问：

> 用户看完，能否判断「这对我有什么用」？  
> 若只能回答「系统是怎么干的」，就改。

### 2.1 能力描述写「能做什么」

**差：**

> 基于 Playwright 的浏览器自动化。通过 stdio 启动 `@playwright/mcp`。

**好：**

> 让 AI 打开网页、点击按钮、填写表单、截图并阅读页面内容，帮你完成浏览和简单网页操作。

句式优先：**主体（AI/你）+ 具体动作 + 场景收益**。少堆产品内部品牌与技术栈名。

### 2.2 页面说明写「用途 + 下一步」

**差：**

> 管理 MCP（模型上下文协议）集成的服务器配置。配置写入 `~/.vetta/agent/mcp.json`。

**好：**

> 管理 MCP，给 AI 增加额外能力，例如浏览网页、使用外部工具。添加后可在对话中直接使用。

需要路径、JSON、命令时，放进 **JSON / 高级 / 开发者** 路径，不要占主视图。

### 2.3 开关与状态用生活语言

| 技术说法 | 用户说法 |
|----------|----------|
| disabled | 已关闭 / 关闭 |
| enable server | 启用 |
| install（若实际只是写配置） | 添加 |
| config saved | 保存 / 已添加 |

避免把「写配置」说成「安装」——除非产品真有独立安装步骤。

## 3. 信息架构与文案一体

文案乱，常常是因为 **同一批东西用三种标签、三套列表** 同时讲。

### 3.1 用户心智优先于内部分类

内部可以有：内置预设 / 远程市场 / 用户手填。  
用户心智更接近：

1. **我现在有哪些**（已添加）  
2. **我还能加哪些**（发现）

商店式结构与此对齐：

- 上方：已添加（统一列表，来源用小标签区分即可）  
- 下方：发现（推荐 / 远程 / 手动 Tab）  
- **已添加的项不要在发现区再出现一遍**

### 3.2 标签用于辨认，不是科普

- 「推荐」：应用预置，可点添加  
- 不必在每条下再解释「配置由应用维护、写入本地文件、首次 npx…」

用户加完后，在「已添加」里用开关管理即可。

### 3.3 少写解释性副标题

默认不写：

- 「关闭开关即暂停，不会删除」  
- 「配置文件路径：…」  
- 「不可编辑」的长说明  

**控件本身应讲清行为**（开关 = 开/关，删除 = 去掉）。  
只有操作不可逆、易误解或合规要求时，才加一句。

多余标题（如列表上方再写「已添加」且与页面标题重复）会增加噪音；去掉后让列表直接承接页面主标题。

## 4. 产品名与营销腔

### 4.1 保留用户已认识的产品名

若用户已把设置入口认作 **MCP**，不要为了「口语化」改成完全陌生的「扩展能力」作侧栏名。

推荐：

- 侧栏 / 页标题：**MCP 管理**（名熟 + 动作清晰）  
- 正文说明：用「能力、对话里能用」解释 **MCP 能干什么**

### 4.2 避免工程师独白

少用：

- 「不会预先安装」「首次连接时 spawn」  
- 「与远程市场添加策略一致」  
- 「仅 UI 展示用 displayName」

这些写进 ADR / 注释 / CHANGELOG 即可，不进用户 UI。

### 4.3 Vetta 与 Vivi（品牌词）

| 名称 | 用户侧说法 | 不要写成 |
|------|------------|----------|
| **Vetta** | 产品本身：帮你便捷用上 AI、跟上智能时代 | 仅「工作空间 / 控制台 / 引擎」 |
| **Vivi** | **品牌形象**，也是**陪伴型伙伴**（好奇、可靠、在侧） | 「品牌伙伴」混用；或把 Vivi 说成独立产品 |

对照句式（官网 Q&A 口径）：

- **宜：** Vivi 是 Vetta 的品牌形象，也是一位陪伴型伙伴……而不是冷冰冰的**应用**。  
- **忌：** ……而不是冷冰冰的**控制台**；「始终在你身边的陪伴形象」（「形象」重复、生硬 → 用「伙伴」收束）。

气泡 / 短句可用温度（如「Vivi 会一直陪伴你」），说明文保持清晰，不要口号堆叠。

### 4.4 少用「技术人员顺口」的词

写方案、用量、开源、FAQ 时，优先生活语言：

| 偏技术 / 内部口吻 | 更合适的用户说法 |
|------------------|------------------|
| 自托管 | 自己安装使用 / 在自己的环境里用 |
| 走 Enterprise | **选择** Enterprise |
| 更高并发 | 同时处理更多任务 |
| 私有部署、定制对接 | 专属环境、权限管理、定制服务 |
| 当期配额 / 清零工作 | 这段时间的额度；不会删掉你已做好的内容（若需说明） |
| 本地工作区 | 你已经做好的内容和文件（场景允许时） |
| 建议路径 | 建议做法 |
| 先透明，再给下一步 | 到额后的处理方式（正式、可扫读） |
| 控制台 | 应用（对比「冷冰冰」时） |
| 不必一上来就买最贵的 | 可删；避免说教、施压感 |

原则：**能让非研发同事一眼读懂；读完像正常产品 FAQ，不像架构评审。**

## 5. 分层展示（主路径 vs 高级）

| 层级 | 给谁 | 可以出现什么 |
|------|------|----------------|
| 主路径（视图） | 大多数人 | 名称、能力说明、添加/开关/删除、推荐列表 |
| 表单基础项 | 手填用户 | 名称、命令、参数 或 URL |
| 高级折叠 | 少数人 | 环境变量、超时、调试、传输类型 |
| JSON 模式 | 极客 / 排障 | 完整配置、文件路径 |

原则：**默认界面零实现细节；实现细节可发现、不主动砸脸。**

列表行优先：

```
[图标] 名称  [标签]
       一两句「能做什么」
```

不要默认挂：

```
npx -y @playwright/mcp@latest
HTTP · https://...
stdio
```

## 6. 中英与语气

- 中文：短句、动词靠前、少从句套从句。  
- 英文：同样 outcome-first；不要把中文技术说明直译成协议说明书。  
- **中英语义对齐即可，不必字字对译**（例如中文「简单说」↔ 英文 `In short` 已足够，不必硬改 `Simply put`）。  
- 统一走 i18n key；用户可见字符串不写死在组件里（desktop / site 均有约定）。  
- 空状态写 **下一步**：「还没有…，可在下方「发现」中选择。」而不是只写「暂无配置。」

### 6.1 语气刻度

| 过松 | 合适 | 过硬 |
|------|------|------|
| 额度用完也不慌 | 到额后的处理方式 | 配额耗尽后的限流与周期重置策略 |
| 别买最贵的啦 | 不确定可从开源版或试用开始 | 请根据 SLA 与并发需求选型 |

官网 / FAQ：比设置页略有温度，但**偏正式、可引用**；少卖萌口号，少工程师黑话。

## 7. 写作检查清单

发 PR / 改用户可见文案前自问：

1. **结果**：用户能否说出这功能或这句话对自己有什么用？  
2. **动作**：下一步该点什么是否清楚？  
3. **噪音**：有没有路径、命令、协议、包名可以下沉到高级区？  
4. **重复**：同一条目是否在多个区块重复出现？  
5. **名词**：产品名是否沿用用户已熟悉的说法？ Vetta / Vivi 是否用对（§4.3）？  
6. **真实性**：有没有把「写配置」说成「安装」、把「关闭」说成「卸载」？  
7. **必要解释**：这句删掉后，用户会不会严重误解？会 → 留；不会 → 删。  
8. **定位**：若在写「Vetta 是什么」，是否对齐愿景（§1.1），而不是默认「工作空间」？  
9. **口吻**：有没有 §4.4 里的工程师顺口词？能否换成生活语言？  
10. **中英**：英文是否 outcome-first，而非中文技术句硬译？

## 8. 反例与正例对照（摘自 MCP 设置迭代）

| 场景 | 避免 | 采用 |
|------|------|------|
| 页说明 | 管理 MCP 服务器配置文件 | 管理 MCP，给 AI 增加额外能力…添加后可在对话中使用 |
| 浏览器 MCP | Playwright / npx 说明 | 打开网页、点击、填表、截图、读页面 |
| 分区 | 推荐 + 远程 + 自定义三块平铺且重复 | 已添加统一列表 + 发现 Tab，发现区去重 |
| 副文案 | 「关闭开关即暂停，不会删除」 | 不写；开关语义自明 |
| 区块标题 | 页面已叫 MCP 管理，列表上再写「已添加」 | 可去掉重复标题，直接列表 |
| 侧栏名 | 改成纯「扩展能力」丢掉 MCP | **MCP 管理** |

## 9. 和代码的边界

- **用户文案**：i18n JSON、按钮 label、空状态、能力描述。  
- **开发者文案**：日志、CHANGELOG 技术段、ADR、代码注释——可以说实现。  
- Agent 改 UI 时：默认按本文写用户串；技术说明写进 CHANGELOG/注释，不要塞进 `t("…")` 的主路径文案。

## 10. MCP / 第三方连接的授权文案

用户最怕的不是「多填一个框」，而是**不知道去哪拿、要多久**。

| 优先级 | 策略 | 用户负担 |
|--------|------|----------|
| 1 | 浏览器登录（OAuth） | 最低 |
| 2 | 「去获取」链接 + 分步说明 + 粘贴 | 中 |
| 3 | 先添加、稍后填 | 可延后 |
| 4 | 对话里让 AI 带一步 | 辅助 |
| 5 | 只甩 env 名 | 禁止 |

实现约定（desktop MCP 推荐）：

- 推荐列表用标签区分：**即用 / 登录即可 / 需密钥**
- 弹窗标题用「连接××」，步骤口语化，按钮「去获取」打开官方发凭证页
- 必填密钥才阻断添加；否则可「先添加，稍后填写」
- 密钥只存本机的提示写一句即可

## 11. 官网 Hero、方案与 Q&A

`apps/site` 首页等营销文案除遵守上文通则外，额外约定：

### 11.1 Hero

- 主副文服务**愿景**（便捷用 AI、减学习负担、服务个人与企业），避免长功能清单。  
- 「学习负担」等关键词不要缩成含糊的「负担」。  
- 吉祥物气泡可短、可有温度；说明句与气泡职责分开。

### 11.3 问答（Value Q&A 等）

- 问题写成用户真会问的话：「是开源的吗？」「我该选哪个方案？」「超出使用限制会怎样？」  
- 答案结构常见为：直接答 → 补充边界 → **简单说**收束（英文可用 `In short`）。  
- 开源：肯定 + 能自己看/装 + 与付费档关系；少堆「引擎 / 审计 / 贡献链路」除非必要。  
- 用量：到额会暂停或降速、下周期重置、可升更高额度方案；进度可查。避免恐吓式「丢数据 / 清零」。  
- 副文（hook）宜正式、可扫读，避免过松口号或过硬术语。

### 11.4 官网 i18n

- 中英文键放在 `apps/site/messages/{zh-CN,en-US}.json`。  
- 改用户可见句时**双语一起改**（语义对齐，非逐字翻译）。  
- 列表类 Q&A 的题目顺序由代码中的 id 列表控制；增删题时同步 i18n 与 id 列表。

---

## 12. 一句话

> **用用户听得懂的产品词，讲清楚能做什么和怎么用；实现细节留给高级入口和文档。**  
> **对外定义 Vetta 时先讲愿景与收益；Vivi 是品牌形象与陪伴型伙伴，不是另一套产品名。**

本文随产品继续迭代；若新场景与上述冲突，优先保证「结果优先、主路径安静、定位与品牌一致」，再更新本节。
