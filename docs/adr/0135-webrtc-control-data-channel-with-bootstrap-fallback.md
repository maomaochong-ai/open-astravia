# ADR-0135：远程控制在引导后切换到 WebRTC DataChannel

## 状态

已接受；修订 ADR-0128 中控制业务长期经局域网 WebSocket或云端中继传输的决定。

## 背景

远程桌面的屏幕和输入已经通过 WebRTC 点对点传输，但会话列表、聊天、状态、诊断和确认仍走独立的控制 WebSocket。手机离开局域网后，这些交互必须绕经 Cloudflare 中继，延迟取决于双方到中继的往返路径；画面已经直连时，控制操作仍可能明显滞后。

不能删除引导链路。双方在 WebRTC 建立前仍需完成配对、身份校验、在线发现和 SDP/ICE 信令，而且部分 NAT 或受限网络无法建立可用的点对点候选。控制协议还需要保留已有的端到端加密、事件续传和重放防护。

## 决策

1. WebRTC host 除视频轨和 `vetta-input-v1` 输入通道外，再创建可靠、有序的 `vetta-control-v2` DataChannel。`@vetta/remote-desktop` 只转发不透明文本，不依赖或解析控制协议。
2. `@vetta/remote-control` v2 的完整握手和 `sealed` 帧原样运行在该 DataChannel 上。长期身份密钥、临时密钥派生、请求响应、事件序号和恢复语义不变；P2P 传输不降低应用层端到端加密。
3. Android 先按局域网 WebSocket、中继 WebSocket的顺序建立引导连接。Desktop 据此启动 WebRTC host；控制 DataChannel 完成 v2 握手后，Android 静默切换全部业务请求和事件到 P2P，并关闭原控制连接。
4. Desktop 可以同时保留 P2P、局域网和中继连接，但每个设备的事件只从当前优先级最高的在线链路发送，顺序为 P2P、局域网、中继，避免重复流量。共享事件日志保证切换后的序号连续并补发缺失尾部。
5. P2P 失败或断开时，Android 自动重新建立局域网或中继控制连接，再尝试新的 WebRTC 会话。云端的 `/v2/desktop` WebSocket继续承担鉴权和信令，不承载屏幕、输入或控制业务载荷。
6. 新 DataChannel 是可选能力。旧 Android 客户端忽略它并继续使用原控制链路；新 Android 连接旧 Desktop 时在 P2P 尝试超时后继续使用局域网或中继，因此无需提升控制协议版本或迁移配对记录。

## 备选方案

- 删除中继控制链路：在对称 NAT、UDP 被禁用或 ICE 失败时会完全失联，无法自恢复，未采用。
- 把控制协议并入输入通道：输入和业务消息的权限、解析与故障边界不同，单通道错误会扩大影响，未采用。
- 只在同一 Wi-Fi 使用局域网直连：不能改善跨网络时的控制延迟，未采用。
- 取消应用层加密并依赖 DTLS：会形成与既有 WebSocket不同的安全合同，也无法保持中继回退的一致语义，未采用。

## 兼容与验证

控制协议线格式和持久化数据没有变化。新增合同测试覆盖可靠文本通道、非法载荷关闭、P2P 优先事件路由以及 P2P 断开后按局域网和中继回退；Android 链路测试覆盖从引导连接升级到 P2P 后继续发起真实加密请求。真实跨 NAT 成功率仍取决于 ICE 候选；当前只有 STUN，没有 TURN，所以受限网络会按设计保留在中继控制链路。
