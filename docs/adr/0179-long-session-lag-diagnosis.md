# ADR-0179：长会话卡顿与 Windows 卡退的诊断与优化

## 状态

已接受，诊断驱动（先建立可回收的证据链，再针对性优化）。范围是会话打开 / 切换链路与
长会话渲染，覆盖主进程解析、渲染层列表、Windows 无响应三类症状。

## 背景

用户报告三类症状：

1. **切换项目长会话时延迟卡顿**：点不同项目的长会话，界面卡顿、长时间加载不出来；
2. **交互过程卡顿**：点按钮、对话框输入、对话过程都有延迟；
3. **Windows 上桌面应用被卡退**：长会话下应用被系统判无响应（ANR）甚至被杀。

这不是第一次出现。ADR-0164 已经做了主进程侧的一组优化（会话解析按 `(ino,size,mtime)`
缓存、追加只解析新行、图片解码缓存、prompt cache 指纹流式化），并新增了
`main-loop-lag-probe`（100ms 心跳、醒来晚于 300ms 记 `main loop blocked` 日志，带阶段
标签）。但 ADR-0164 明确写了「本机复现不了大会话卡顿，用户把日志发回来才能定位」——
**这条诊断链路当时只做了一半：探针能记日志，但没有人把它接进「用户可回收」的通道，也没有
针对渲染层的探针。**

本轮的目标不是再凭空猜一个「优化 X 就解决了」，而是先把症状变成可回收、可分层的证据，
再按证据逐项优化。没有证据的优化，即使方向对，也无法验证它解决了用户那台机器上的问题。

## 决策

### 1. 症状分三层，各自建立证据链

三类症状不能混为一谈，它们的根因可能完全不同：

| 层 | 症状 | 已有证据设施 | 缺什么 |
| --- | --- | --- | --- |
| 主进程同步阻塞 | 点什么都卡、转圈 | `main-loop-lag-probe` 能记 `main loop blocked` + 阶段标签 | 日志没有可回收通道；探针标签没有覆盖会话打开/切换的关键阶段 |
| 渲染层长列表 | 长会话首屏慢、切换慢 | 消息列表有虚拟化（`MessageFeedView`） | 无渲染层长任务探针；虚拟化是否覆盖所有切换路径未核 |
| Windows 无响应 | 卡退 / 被杀 | 无 | 无 ANR / OOM 的侧写记录 |

### 2. 主进程：把探针标签铺满会话关键路径，日志接进诊断导出

- 在会话打开 / 切换 / 解析 / 序列化的每个同步阶段打 `probe.tag("session-open:parse")` 这类
  标签，让下一条 `main loop blocked` 日志能直接指出「哪一段同步工作占了主线程」；
- 把 `main loop blocked` 日志纳入现有的「导出诊断」产物（`exportDiagnostics`），
  用户点一次导出就能把证据发回来，不再要求「手动找日志文件」；
- 探针仍在开发构建 + 显式开关下工作，不改变生产行为。

### 3. 渲染层：补一个低成本的 Long Task 探针

渲染层卡顿不会出现在主进程探针里。补一个 `PerformanceObserver("longtask")` 探针，
记录超过阈值的 long task 及其 `attribution`（哪个脚本 / 组件触发的），同样进诊断导出。
这是浏览器原生能力，成本是观察者本身，不额外计时。

### 4. Windows 无响应：先记录侧写，再决定是否做「异步化」

Windows 的 ANR 通常来自主进程同步阻塞超过系统阈值（约 5s 无消息泵响应）。在拿到
`main loop blocked` 日志 + 侧写之前，**不做**「把某个同步操作改异步」这类没有依据的改动——
异步化可能引入新的竞态，而根因根本不在猜的那个地方。先把日志接回来，看证据说话。

### 5. 已知的可疑点（待证据确认，不是结论）

这些是排查时的优先观察对象，按证据确认后才动手：

- 会话切换时是否仍在**同步**解析大文件（ADR-0164 的缓存命中路径之外）；
- 长会话首次渲染是否全量挂载消息节点（虚拟化阈值以下 / 切换时未复用）；
- 团队会话（team）与普通会话是否走了不同的、未虚拟化的渲染路径。

## 备选方案

- **直接按「会话文件异步解析」重构**：方向可能对，但没有证据就无法验证，且异步化会引入
  新的状态机复杂度；ADR-0164 已经证明「按证据逐项优化」比「一次大重构」更可控。
- **只在 Windows 上做专门的侧写记录**：覆盖不全，macOS/Linux 的长会话卡顿同样需要证据。

## 后果

- 正面：症状从「无法复现、无法定位」变成「可回收、可分层」，之后的每次优化都有据可依。
- 代价：探针与日志导出是纯增量（探针不改变业务行为，日志导出多一个条目），不引入行为变化。
- 已知限制：探针只在开发构建 / 显式开关下工作，生产构建默认不记 `main loop blocked`；
  「把探针默认打开」需要单独评估日志量，不在本 ADR 范围。

## 验证

- `main-loop-lag-probe` 用例：标签消费一次、低于阈值不记、unref 不拖住退出（已有，扩展标签断言）；
- 会话关键路径标签：打开 / 切换长会话时，构造一段同步阻塞，断言日志带上对应阶段标签；
- 渲染层 longtask 探针：mock `PerformanceObserver`，断言 longtask 记录进诊断产物；
- 诊断导出：`exportDiagnostics` 产物包含 `main loop blocked` 与 longtask 两类记录。

## 实施批次

1. 会话关键路径铺 `probe.tag` 标签 + 日志接进诊断导出；
2. 渲染层 `PerformanceObserver("longtask")` 探针，同样进导出；
3. 用户发回日志后，按证据定位主进程阻塞段 / 渲染 long task 来源；
4. 针对证据做定点优化（每条优化单独验证，不打包成一个大重构）。
