# ADR-0173：MCP 安装位置（全局 / 项目层）作为显式合同

## 状态

已接受，尚未实施。对应 ADR-0157 登记表的 `dqpd`，并解锁 `4b7x`。

## 背景

`mcp.manage` 现在只有一个落点：`~/.astravia/agent/mcp.json`。这在两种场景下都不对：

- **只有一份全局配置**：同一个工具在不同项目里需要不同的参数（工作目录、连接串、
  只读库的凭据），现在只能装全局，然后每次手工改。
- **`.mcp.json` 已经存在但只读**：仓库根目录的 `.mcp.json` 上一批刚接通读取
  （ADR-0157 §15），但它是「读进来」的兼容来源，`mcp.manage` 写不进去，用户看到
  的是「这个配置在界面上能看到、却改不了，也无法解释」。

安装 Skill 也因此无法回答「装到哪一层」，只能默认全局——而模型并不知道这一层
意味着「进不进版本库」。于是出现最难排查的一类问题：用户以为装在项目里，实际写进
了全局，换一个项目仍然生效。

## 决策

### 1. 位置是调用方必须表态的参数，不是猜出来的

`mcp.manage` 的 upsert / remove / set-enabled 增加可选 `scope: "global" | "project"`
与 `cwd`：

- 缺省 `global`——保持既有调用的行为不变，不破坏任何现有插件与技能；
- `scope: "project"` 必须带本机项目根的**绝对路径** `cwd`。`ssh://` 形式的远程项目
  直接拒绝：远端仓库的配置文件不在这台机器上，写过去只会两边不一致；
- 按名字定位时，若全局与项目层存在同名条目，**必须显式指明 scope**，否则报错。
  静默取其中一个，会让用户在两个项目之间反复看到「明明改过又变回去」。

### 2. 项目层写的是本仓自己的目录

项目层路径是 `<cwd>/<CONFIG_DIR_NAME>/mcp.json`（与 `FileMcpConfigSource` 的
`projectConfigPath` 同一个事实源），不硬编码目录名，也不借用其它工具的 `.claude`
之类路径。`.mcp.json` 依旧**只读**：它是别人的约定，不是我们的存储。

### 3. 项目层密钥只允许环境变量引用

写进仓库文件的东西会进版本库。因此项目层的 `env` / `headers` 值必须写成
`${VAR}` 形式，由启动时展开；直接把明文密钥写进项目层要在服务层拒绝并给出可读错误。
全局层保持现状（明文允许，文件在用户家目录、不入库）。

### 4. 审批弹窗必须说明落在哪一层

`McpUpsertApproval` 增加「配置位置」一行：全局或项目根绝对路径。确认后原样带回
scope，不重新推断。理由很直接——审批是用户唯一一次真正看清「这次写入会影响谁」
的机会，而全局与项目层的差别正是「影响所有项目」与「影响这个仓库」。

### 5. 合同层透传，业务判断留在服务层

`capability-sdk`、`plugin-sdk`、`astravia-actions` 的 `manageSchema` 只做形状校验
（可选枚举 + 可选字符串），不判断「远程项目能不能装项目层」这类业务规则；那条规则
在 `McpSettingsService` 里，只有一处实现。

把「位置判定」抽成纯函数（入参：scope、cwd、是否远程项目；出参：目标文件路径或
可读错误），因为它要被服务层、审批卡与技能文档三处引用，而三处对「什么算合法」
必须给出同一个答案。

## 备选方案

- **只做全局，用项目层 `.mcp.json` 手工维护**：不新增合同，但用户要在「界面能看、
  改不了」和「去仓库里手写 JSON」之间来回切换，且技能无法报告写入位置。
- **按 `cwd` 自动判断层级**：少一个参数，却把「我想装全局」这个明确意图变成猜测。
  同一台机器上先打开项目再装全局工具的情况很常见。
- **把 `.mcp.json` 变成可写**：能让用户只维护一份文件，但它属于外部工具的约定，
  写入会与那个工具争抢同一份状态；本仓也没有资格替用户改它。

## 后果

- 正面：同一份 `mcp.manage` 能覆盖两种真实用法；技能可以如实回答「装在哪」；
  项目层密钥规则把「把密钥提交进仓库」这条路从默认路径上移走。
- 代价：公共合同变更——`mcp.manage` 的 schema、capability 目录（生成物）、
  IPC/preload 类型、审批卡文案都要同步；旧宿主打开新插件时按版本拒绝。
- 兼容性：`scope` 缺省 `global`，现有调用与既有 `mcp.json` 不需要迁移。
- 已知限制：市场安装的能力仍只装全局（市场包没有「项目」概念），要在技能与文档里
  如实说明，不能让用户以为可以选。

## 验证

- 服务层单测：全局 upsert、项目层 upsert、同名未指明 scope 报错、`cwd` 为 `ssh://`
  被拒、`.mcp.json` 里的条目不可改、项目层明文密钥被拒。
- 合同测试：`manageSchema` 接受 `{operation:"upsert", name, scope:"project", cwd:"/abs"}`；
  拒绝 `scope:"project"` 缺 `cwd`；拒绝未知 scope 值。
- 审批卡组件测试：项目层时显示绝对路径，确认后 handler 收到的 scope 与展示一致。
- 生成物：`docs/capabilities/catalog.json` 由脚本重生成，不手改。

## 实施顺序

1. 服务层 `scope` / `cwd` 解析 + 位置判定纯函数（含单测）；
2. IPC 与 preload 类型透传；
3. `manageSchema` 三个分支加可选字段、能力目录重生成；
4. 审批卡位置展示（含组件测试）；
5. 技能与文档站同步（即 ADR-0157 的 `4b7x`，必须在第 3 步之后）。
