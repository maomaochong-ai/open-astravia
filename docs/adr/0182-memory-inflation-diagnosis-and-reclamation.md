# ADR-0182：内存膨胀（RSS）的诊断与分层回收

## 状态

已接受，证据驱动（先建立内存证据链，再按证据做定点回收）。范围是桌面端长时间使用后的
内存膨胀与卡顿 / 闪退，覆盖主进程会话历史、渲染层长任务、插件 remote 生命周期三类候选。

## 背景

用户报告 Windows 上长时间使用后内存占用飙到 30 GB 量级，随后「点桌面任意位置卡顿甚至
闪退」——这是典型的内存压力症状（RSS 膨胀 → 系统换页 / OOM → 无响应）。

这不是第一次出现。ADR-0179 已经建立了两层证据链（主进程 `main-loop-lag-probe`、渲染层
`PerformanceObserver("longtask")` 探针），并明确「先建证据链，再针对性优化」。但**内存层
至今没有证据链**：`--max-old-space-size=4096` 只约束 V8 老生代，管不到 RSS（原生内存、
GPU 纹理、Buffer、多进程各自的工作集），30 GB 这个数字既没有采样记录，也没有进诊断导出，
用户点「导出诊断包」也带不回任何内存侧证据。

本轮目标与 ADR-0179 一致：不凭空猜「回收 X 就解决」，先把内存变成可采样、可导出、可分层的
证据，再按证据逐项回收。

## 参考：deepseek-harness 的做法

上游 deepseek-harness 用一组架构笔记把「资源该活多久、谁拥有它」显式化，本 ADR 沿用其
三条原则（映射到本项目现状）：

| 原则 | deepseek-harness 表达 | 本项目映射 |
| --- | --- | --- |
| 生命周期与所有权合同 | 每个 agent / runtime 的创建、销毁、所有权由合同显式定义，避免「谁都没负责释放」 | 会话 historyReader、插件 remote、图片缓存的持有方与释放时机要有明确归属 |
| 客户端资源模型 | 资源分「常驻 / 按需 / 可卸载」三档，只有常驻资源允许无上限累积 | 会话历史 = 按需（切走即释放）、图片缓存 = 有上限、插件 remote = 随重载卸载 |
| 证据驱动 | 性能优化先测量再改，不靠猜测 | 先把 RSS / V8 heap 采样接进诊断导出，再按证据定点回收 |

## 根因方向（待证据确认，不是结论）

以下按现有日志证据列出的优先观察对象，每一条都要在内存证据链建立后确认：

1. **主进程会话历史常驻**：`getFullHistory` 同步 `[...historyReader.readHistory()]` 展开复制，
   长会话切换时主进程阻塞 654ms（`phase: "session-get-full-history"`）；会话关闭 / 切走后
   历史是否真正释放未验证。
2. **渲染层长任务**：日志出现 1257ms / 864ms 级 long task，消息列表 / 技能列表的重计算
   可能反复触发，渲染进程工作集随之膨胀。
3. **插件 remote 生命周期**：插件重载时反复出现「The remote X is already registered」，
   旧 module-federation remote 可能未完全卸载，随插件更新累积。
4. **图片 / 媒体缓存**：截图、生成图片、能力图标等无上限累积的边界未确认。

## 决策

### 1. 建立内存证据链：采样 + 阈值告警 + 诊断导出

- 用 Electron `app.getAppMetrics()` 周期采样各进程（Browser / Renderer / GPU / Utility）的
  `workingSetSize` 与 `peakWorkingSetSize`，主进程另用 `process.memoryUsage()` 记录 V8 heap；
- RSS 超过阈值（如总工作集 > 8 GB）时记一条告警日志进 ring buffer；
- 采样快照（最近若干条）并入 `buildDiagnosticsBundle`，导出诊断包即带出内存曲线，不必
  让用户手动描述「用了多久、占了多少」。

### 2. 定点回收：只在证据确认后动手

- 会话历史：确认切走 / 关闭后 historyReader 是否释放，未释放则补「按需加载 + 切走释放」，
  并把 `getFullHistory` 的同步全量复制改成不复制（IPC 序列化本就独立成副本）；
- 渲染层：按 long task 的 `attribution` 定位重计算来源，拆长任务 / 复用计算结果；
- 插件 remote：确认重载后旧 remote 是否被 dispose，未释放则补卸载；
- 图片缓存：加容量上限（LRU）与总字节预算。

### 3. 每条回收单独验证，不打包成大重构

与 ADR-0179 一致：每条优化对应一个可失败的回归点（内存采样断言、生命周期释放断言），
改动与验证一一对应，避免「一次大重构 + 无法归因」。

## 备选方案

- **直接给 V8 加 `--max-old-space-size` 更大值**：治标不治本，RSS 膨胀来自原生内存与
  多进程工作集，不在 V8 老生代；且更大的上限只会让 OOM 来得更晚、更猛。
- **只在 Windows 上做内存监控**：覆盖不全，macOS / Linux 长会话同样可能膨胀，且分层证据
  应该跨平台一致。

## 后果

- 正面：30 GB 从「无法定位」变成「可采样、可导出、可分进程归因」，之后的每次回收都有据可依。
- 代价：采样是纯增量（低频周期采样 + 告警日志 + 导出多一份快照），不改变业务行为。
- 已知限制：`app.getAppMetrics()` 的 workingSetSize 是操作系统工作集，包含共享页，只能
  作为相对趋势与进程间对比，不能当作精确的独占内存；精确归因仍需结合 V8 heap 与 long task。

## 验证

- 内存采样：mock `app.getAppMetrics` / `process.memoryUsage`，断言快照写入 ring buffer 且
  并入诊断导出；阈值告警只在超限时记日志。
- 会话历史释放（后续）：切走 / 关闭会话后 historyReader 引用被置空（有明确的释放断言）。
- 插件 remote 卸载（后续）：重载后旧 remote 的 dispose 被调用（生命周期断言）。

## 实施批次

1. 内存采样器（`app.getAppMetrics` 低频采样 + 阈值告警）接进诊断导出；
2. 用户发回诊断包后，按 RSS 曲线 + long task + lag 标签定位膨胀来源；
3. 针对证据做定点回收（会话历史 / 渲染层 / 插件 remote / 图片缓存），逐条单独验证。
