# ADR-0127：自动化的运行会话策略与无人值守执行

## 状态

已接受

## 背景

旧的定时任务把每次执行都建成「对话」下的一个新会话：即便任务选了项目作为工作目录，会话文件仍固定写进默认对话的 sessionDir。高频任务很快把「对话」列表刷满，用户也无法让任务在某个项目里、或在同一段上下文里持续推进。

旧任务还携带执行权限、技能引用等字段，执行时可能因提权审批、`ask_user_question` 或计划模式停下来等人——而自动化触发时通常没有人守在电脑前。调度只存在于进程内，应用未运行或系统休眠时错过的触发不留任何痕迹。

## 决策

1. 每个自动化声明一个[[运行会话策略]]：「每次新建会话」或「同一个会话」。会话落在所选项目（或「对话」）下，归属由会话本身决定；「同一个会话」下「项目」只是筛选可选会话的条件。
2. 「同一个会话」绑定一个[[绑定会话]]，可以是已有会话，也可以是首次触发时新建一次、之后复用的会话。绑定会话或目标项目被删除时，自动化暂停并提示原因，不自动换一个新会话顶上。
3. 同一个自动化同时最多只有一次执行；上次未结束时的触发记为「已跳过」。触发时绑定会话正忙（用户正在对话），本次执行等当前这一轮结束后再作为独立的一轮运行；不用会话输入队列的 followUp，那会把自动化的任务并进用户正在进行的那一轮，也拿不到属于自己的结果。
4. 自动化触发的轮次是无人值守的：执行权限固定为完全访问，新建会话的工作模式固定为 Work，本轮不注册 `ask_user_question`，也不受会话计划模式影响。用户在同一会话中手动发起的轮次不受这些约束。
5. 模型与思考强度默认「跟随默认」，在每次触发时解析；显式选择的模型不可用时本次执行失败，不回退。自动化轮次使用的模型不改变会话自身的模型选择。
6. 错过的触发不补跑。应用启动或系统唤醒时计算错过的触发点，以「已错过」记录写入执行历史并注明原因（应用未运行 / 系统休眠），连续错过合并为一条；错过的一次性任务随之停用。
7. 「每次新建会话」产生的会话在侧边栏按自动化折叠为[[自动化会话组]]；自动化页的执行历史仍是完整入口。
8. 旧任务一次性迁移到新结构：策略为「每次新建会话」，项目由旧 `cwd` 推断，技能引用转为任务正文开头的 `@skill:` / `@scene:` 行内引用，执行权限字段丢弃；原文件保留备份。

## 备选方案

- **生成的会话完全不进侧边栏，只在自动化页可见**：最干净，但用户无法在项目里找到自动化的产出，放弃。
- **错过后补跑一次**：对日报类任务有用，但补跑时刻与用户预期的触发时刻不同，且高频任务会在开机时集中爆发；改为只记录原因，由用户决定是否立即运行。
- **保留执行权限选项**：沙箱下需要提权时自动化会阻塞等人，与无人值守前提冲突。

## 后果

- 无人值守轮次里 agent 遇到不确定之处只能自行假设，需要在结论中写明假设；完全访问意味着自动化的副作用不再有逐次审批兜底。
- 调度仍依赖应用进程存活，不唤醒休眠中的系统；错过记录只是可观测性补偿，不是可靠调度。
- 「同一个会话」会持续累积上下文，依赖既有压缩机制控制长度。
