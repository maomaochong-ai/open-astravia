# ADR-0120: Desktop 发版使用下载缓存和阶段检查点

## 状态

Accepted

## 背景

Desktop 的平台矩阵已经允许独立失败，但编译、签名、公证、安装校验和 packaged E2E
处于同一个 job。验收失败会丢弃构建结果。Bun 安装失败还会立即清空下载目录。
只有 tag 范围的缓存无法解决下一版重复下载，因为 GitHub 不允许不同 tag 互读缓存。

## 决策

- 共享 Bun 安装 action 持有包下载缓存，冻结安装继续执行；首次失败保留下载重试，连续失败才清缓存。
- 在默认分支运行独立的下载预热工作流，覆盖四种 release runner；按平台和资源事实源隔离缓存。
  Node/Python 下载从 staging 编排中提取，预热和正式打包使用同一实现，原始归档通过临时文件原子落盘。
- 将 build、verify、publish、线上 feed 校验分成独立 job。build 的 tar 检查点保存本次运行的
  release 目录和签名校验要求；verify 使用相同 runner 类型恢复，成功后才提供发布制品。
  签名凭据不传给 verify。所有验收和发布条件继续生效。
- 检查点与发布制品保留 30 天，只在同一次 workflow run 内恢复；不能作为跨版本构建缓存。
- ADR-0079 的正式 `--force`、Desktop 不可缓存及 Turbo Remote Cache 禁用边界保持不变。

## 备选方案

- 只添加 tag 内缓存：不能覆盖下一版下载，且不能降低验收重试成本。
- 缓存整个 node_modules、staging 或签名输出：会扩大平台、配置、秘密和兼容性边界，当前不采用。
- 关闭检查或把校验设为非阻断：破坏发布完整性，不采用。
- 自持 runner：可以进一步复用工具链，但需要隔离、清理和运维；当前继续使用托管 runner。

## 后果

失败重试可以从已完成的阶段继续；默认分支预热让新 tag 复用公共下载。
代价是额外 runner 启动、检查点传输和 Actions 存储；验证矩阵仍等待构建矩阵整体完成。
缓存淘汰不影响正确性，但检查点过期后必须重做构建。旧运行不会自动采用新工作流。
操作方法与限制见 [发版缓存与失败恢复](../desktop/release-ci.md)。
