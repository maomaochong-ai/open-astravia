# ADR-0141：团队自动回复中的反向问题不再启动新回合

## 状态

已接受

## 背景

`team_send_message(intent="question")` 会为每个收件人创建独立 work item；收件人完成后，持久化通知又会自动唤醒发起者。同步等待期间的成员依赖由 `TeamMemberScheduler` 的等待图检查，但通知发生在前一项工作已经完成之后，不再持有等待边，因此不属于同步死锁。

openvetta/open-vetta#60 暴露了另一种失败：成员在回答入站问题时，又用 `question` 向原发起者确认；或发起者在整合某成员的完成通知时，再用 `question` 要该成员确认。每个动作单独看都合法，却会形成跨 attempt 的异步回声：A 完成后唤醒 B，B 再启动 A，随后 A 又唤醒 B。work item、通知与 continuation ID 每轮都不同，已有的幂等键、等待环检测和单任务恢复预算都无法终止它。

## 决策

1. `TeamMessageControlService` 在处理 `team_send_message` 时，根据当前 attempt 的 `sourceTurnId` 找到正在回答的 work item。
2. 下列成员属于本轮的“响应接收者”：
   - 当前 work item 是 `question` 时，它的创建者；
   - 当前 work item 携带完成通知时，通知所对应 work item 的执行成员。
3. 模型若对响应接收者再次发送 `intent="question"`，公开消息和投递记录仍照常持久化，但该收件人的实际投递按 `inform` 完成，不创建新的 work item，也不启动模型。一次消息中的其他收件人仍保持原来的 `question` 语义。
4. 模型可见的团队操作规则和工具说明明确告知：回答问题或整合完成通知时，最终回复本身已经会到达触发者，不要再向触发者发送反向问题。需要正式返工时由负责人使用 `team_delegate_task` 创建有明确目标的任务。
5. 不为所有团队流程设置固定 continuation 次数上限。合法的长流程可以继续通过不同成员、明确任务和完成通知推进；本决策只切断会自动闭合成响应回声的投递边。

## 备选方案

- **设置全局 continuation 上限**：能把无限循环变成有限循环，但阈值与任务复杂度无关，会截断合法的长团队工作流，也与 ADR-0126 对默认调用预算的取舍不一致。
- **只加强提示词**：能降低部分模型误用概率，但不能作为费用与副作用边界；模型不遵守提示时仍可无限创建新任务。
- **禁止成员之间双向通信**：可以消除回声，也会破坏正常咨询、审查和返工，不符合团队产品模型。
- **按消息文本去重**：措辞稍有变化就会失效，并把语义判断错误地放进持久化基础设施。

## 后果

- 问题回答与完成结果仍会公开展示并自动交给原发起者整合，但“收到”“请确认”“不要再回复”等反向确认不再启动对方模型。
- 一个 `team_send_message` 可以出现混合投递：触发本轮的成员收到 `inform`，其他真正需要补充信息的成员继续收到 `question`。
- 不新增持久化字段或迁移。旧 delivery/work item 按原语义恢复；升级后的新投递才应用该因果边界。
- 正式返工仍可由负责人用新的 `team_delegate_task` 表达，保留任务目标、恢复预算和可观测性。
