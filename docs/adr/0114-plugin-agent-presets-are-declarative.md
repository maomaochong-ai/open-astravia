# ADR-0114：插件贡献的智能体与团队由清单声明式维护

## 状态

Accepted

## 背景

插件贡献的智能体与团队走的是「回填」：读配置时把清单里有、文档里没有的那些补进用户的 Agent 配置，已经存在的只盖一个提供方的戳，内容一律不动。

这条路径只会加，不会改，也不会减：

- 作者在新版本里撤掉「团队 1」、改了它的阵容或任务书，用户升级后看到的还是上一版的团队 1，新增的团队 2 则并排出现。作者发出去的资产再也收不回，两台机器装同一个版本也长得不一样。
- 用户改过的名字、能力勾选与阵容被当成需要保护的用户数据，于是「插件维护的人设」实际上变成了「插件铺过一次的人设」。删除虽然被拦住，编辑却是开放的。

另一半问题在生效时机：插件变更只重建主进程的 blueprint 注册表，而用户看到的智能体与团队来自已经读进内存、且被 `AgentTeamStore` 长期缓存的那份配置文档。热重载、装卸插件都不会重铺它，也没有任何事件推给渲染进程——侧边栏要等到重启 App 才跟上。

## 决策

1. 插件贡献的智能体与团队由提供方 **1:1 维护**：宿主每次同步都按清单重铺它们的名称、说明、能力、阵容与任务书，用户的就地改动不保留。
2. 改写与删除在 Store 一层统一拒掉（`AGENT_RESOURCE_PROVIDED_BY_EXTENSION`），UI 对这类资源只读展示。
3. 清理是**声明式**的：文档里带提供方戳、而**已安装插件（含禁用）都不再声明**的智能体与团队会被移除，并从用户自建的团队里摘掉相应成员。判据是「还有没有插件声明它」，不是「此刻解析得出来吗」——否则禁用一个插件就等于把它的资产判成残骸。
4. 资源 id 与成员 id 继续沿用既有那一份（规范 id、`legacyIds` 认领、槽位推导），覆盖只换内容不换身份：用户的团队绑定与会话里的引用都挂在这些 id 上。
5. 插件变更触发「重建注册表 → 重铺配置 → 广播 `vetta:agent-teams:changed`」，渲染进程据此重取。装卸、启停与开发态热重载因此当场生效。

## 备选方案

| 方案 | 未采纳原因 |
| --- | --- |
| 保留回填，另给作者一个「撤回资产」的清单字段 | 把宿主的状态自洽问题转嫁给作者：他要为每一版的历史资产写迁移条目，漏一条就永远留在用户机器上 |
| 插件资产完全虚拟化，不进用户配置 | 用户自建的团队引用得到它们，虚拟层一缺席整份配置就读废；持久化那一份才谈得上稳定的 id |
| 禁用插件即移除它的资产 | 用户把插件智能体拉进过自己的团队，临时禁用会连带拆掉那支团队——代价远大于列表里留一条灰项 |
| 只做热重载，保留「用户改动优先」 | 覆盖不发生，作者仍然收不回上一版的团队；同一个版本在两台机器上长得不一样的问题原样还在 |

## 后果

- 作者对自己的智能体与团队有了完整的版本控制：改、删、换阵容都会在用户升级后如实生效。
- 用户在插件资产上的改动会丢。想要一份自己调教的版本，路径是复制一份自建档案，而不是就地改插件的那一份。
- 存量数据自愈：被认领过的老档案在下一次同步时对齐到清单，`legacyIds` 保证它们不会长出重复的一份。
- 禁用插件的语义不变——资产灰着留在原地，重新启用后照旧（见 `docs/plugin/manifest.md` 的「生命周期」）。
