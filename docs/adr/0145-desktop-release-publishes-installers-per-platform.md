# ADR-0145: Desktop 发版按平台上传安装包，更新清单由开发者上线

## 状态

Accepted

## 背景

发版流水线原本由 `publish-r2` / `publish-github` 在四个平台全部构建完成后统一发布：合并 macOS 两份
更新清单、上传安装包，最后上传 `latest*.yml` 让客户端看到新版本。最慢的 macOS x64（Intel runner
常要排队）拖住了其他平台的发布；任何一个平台失败，已经构建好的安装包也发不出去。更新清单一旦
上传就会推送给所有用户，何时上线应由开发者决定，而不是跟随 CI 完成时间。

## 决策

- 删除 `publish-r2`、`publish-github` 与线上 feed 校验任务；每个平台构建任务在构建后直接发布自己的安装包。
- R2：安装包与 blockmap 上传到正式目录（按版本命名，已有同名对象内容不同则拒绝覆盖）；
  `latest*.yml` 只上传到 `<prefix>/pending/<版本>/`，客户端读不到。
- GitHub Release（非 test 渠道）：第一个完成的平台直接创建正式 Release，其余平台追加安装包；不上传更新清单。
- 更新清单仍由 electron-builder 生成：其中每个安装包的 sha512 与 size 是客户端下载校验的依据，手写易错。
  开发者决定上线时手动运行 `desktop-promote`：合并 macOS 清单、核对安装包哈希、拒绝降级后发布到正式目录，
  并附到 GitHub Release。

## 备选方案

- 拆成每个平台一条独立 workflow：矩阵任务本来就在不同 runner 上并行，拆分不会更快；
  去掉集中发布后矩阵任务已经互不等待。
- 保留自动上线清单、只把安装包提前上传：仍然由 CI 决定用户何时收到更新，不符合发布控制需求。
- 不生成更新清单：开发者需要自行计算每个安装包的 sha512，出错会让所有用户更新校验失败。

## 后果

各平台构建完即可下载安装包，Release 页面随平台完成逐步补齐，刚创建时可能只有部分平台。
CI 不再让任何客户端看到新版本，漏做手动上线步骤时用户收不到更新；线上 feed 的可达性检查移到
`desktop-promote` 上线之后执行。构建任务需要写 Release 的权限。
操作步骤见 [发版下载与失败恢复](../desktop/release-ci.md)。
