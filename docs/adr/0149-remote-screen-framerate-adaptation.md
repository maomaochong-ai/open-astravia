# ADR-0149：远程画面保帧率与发送端自适应

## 状态

已接受，2026-10-08。修订 ADR-0140 的清晰度优先策略。

## 背景

Windows 到 Android 的实测日志出现硬件 H.264 回退到 OpenH264 后，画面在带宽波动中长期停在 4 fps，而接收端渲染没有丢帧。Electron 34.5.8 使用 Chromium 132.0.6834.210；其 WebRTC 将屏幕共享的 `balanced` 实际转换为 `maintain-resolution`，因此应用原本希望的分辨率与帧率平衡没有发生。

此前只在编码器类型变化时，将软件编码限制到约 1920×1200。它没有根据持续负载降档或恢复；手机显示尺寸与统计回调各自异步写 sender 参数，失败也不可见。低 RTT 不能证明画面流畅，手机延迟估算不包含发送端截屏、编码和排队。

## 决策

- 截屏和发送统一以 30 fps 为上限，明确设置 `maintain-framerate`，保留 `contentHint = detail`。过载时允许画面变小，优先保证操作连续性。
- `RemoteDesktopHost` 保留信令、输入与控制编排；`ScreenSender` 独占视频轨道替换和参数写入。所有写入串行，读取最新参数和策略后再写；相同参数不重复提交，失败按错误类型去重记录并在后续采样重试。
- `ScreenStatsSampler` 每秒计算同一发送流的增量统计，使用 transport 指向的实际 candidate pair。替换轨道、计数重置和迟到采样不得产生负耗时或污染新流。
- `ScreenAdaptation` 在手机显示尺寸和软件编码像素预算之上增加动态缩放。持续两秒的运动负载才降档，降档间隔至少三秒；连续十秒达到帧率、编码耗时和带宽余量条件后才升档。静止画面的低帧率本身不触发降档。动态缩小保留至少 640×360 的包围框，原始小画面不放大。
- 软件编码预算的缩放系数向上取整，避免原有 1.33 系数使 2560×1600 实际仍超过 1920×1200 像素预算。
- 实际写入 sender 前进一步选择不会产生奇数宽高的缩放系数。Chromium 的硬件 H.264 `InitEncode` 明确拒绝奇数尺寸；例如旧的 1.5 系数会将 2560×1600 四舍五入为 1707×1067，改为略小的 1706×1066 即可避免这条回退。
- Windows + Chromium 132 在 app ready 前禁用 `KeepEncoderInstanceOnRelease`，保留其他 `disable-features`。本机对照实验在偶数尺寸 1280×800→2048×1280 上重复触发 `RTCVideoEncoder::Impl::NotifyErrorStatus`；禁用复用后，同一旧实现、同一 60 fps 输入保持硬件编码，表明错误位于复用编码器调整尺寸的路径，而非单纯负载不足。只重建编码器，不重建 PeerConnection。其他系统与 Chromium 版本不应用此兼容设置；升级 Chromium 时需重跑硬件尺寸切换测试。
- 采样不重叠，日志每五秒输出一次；记录源帧率、编码/发送帧率、实际码率、平均编码与包发送等待、QP、编码器变化和限制持续时间。Android 同期记录接收、解码、丢帧与冻结计数，渲染由现有 EglRenderer 日志核对。只保存尺寸、技术名称、计数和耗时。
- 恢复不重建 PeerConnection，不影响输入或业务控制通道。不增加协议字段；旧手机仍可使用，未提供显示尺寸时使用默认预算。

## 备选方案

- 只把码率上限继续提高：不能解决编码耗时和屏幕共享的保分辨率降级行为。
- 永久固定较低分辨率：实现简单，但文字放大后的损失无法恢复。
- 仅把 `balanced` 改为 `maintain-framerate`：必要但不足，软件编码和手机缩放仍需要统一状态、稳定恢复和可观测参数更新。
- 低帧率时重建整个连接：会中断控制消息，不能作为视频恢复常规路径。

## 后果与验证

帧率上限由 60 降到 30，过载或网络不稳期间文字可能暂时变软。策略不会保证任意硬件和网络都达到 30 fps，也不会将静止画面强行补成 30 帧。

单元与公共入口流程测试覆盖负载、恢复滞后、缩放、参数竞争、失败重试、轨道启停和关闭。Chromium E2E 使用 1920×1200 连续运动画面，在统计边界注入可控压力，验证实际编码尺寸下降与恢复、接收帧率、非空运动像素和输入通道。它验证真实媒体管线应用策略，不等价于真实弱网或 Android 真机性能验收。

硬件回退诊断使用与实际应用相同的 Electron 34.5.8，合成 2560×1600 运动画面与本机接收端，排除手机和外网干扰。对照原始提交与新实现、正常复用与禁用复用，Trace 确认复用后的尺寸重配置报错；奇数尺寸另有 Chromium 源码中的明确拒绝条件。最终组合（偶数尺寸、禁用有问题的复用、30 fps）在固定尺寸、放大、分数缩放及重复切换中保持 MediaFoundation 硬件编码。不能据此进一步断言某个具体显卡驱动缺陷；未取得底层 HRESULT。

兼容设置需要重新启动 Desktop 才生效；Renderer 热更新只能应用发送策略与尺寸对齐。重建编码器会增加分辨率切换时的短暂初始化开销。
