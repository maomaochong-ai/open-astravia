# ADR-0157：与参照实现 0.5.72–0.5.81 的对齐基线

## 状态

已接受。本记录确立「对齐」的判定规则与逐项基线，**不是**一次性实施计划：基线里标为
「待对齐」的条目按各自涉及的合同面单独开轮，需要新公共 API 或插件合同的项目各自
另立 ADR。

## 背景

本项目从一条上游代码线演进而来，两条线在 0.5.72 之后独立推进；参照实现在
0.5.72→0.5.81 之间落地了 247 个非合并提交（含 15 条版本号推进、15 条发布说明）。
两边的产品面已经分叉：参照实现有 Magpie 本机代理、像素白鼬应用图标、专家中心、
Splash 引导面板等本项目不存在的功能；本项目则有自己的字体系统、页签形态、
自动化与批量任务。

分叉带来的实际问题是：同一个缺陷在两条线上被独立发现、独立修复，而修复方式不同；
有的能力（顶栏收纳、管理会话面板、按钮组）在参照实现里已经成熟，本项目仍是散的
独立按钮。缺一份基线，每轮只能凭印象挑几个做，既做不全，也无法说明「为什么这一条
不做」。

本记录要解决的是**判定与记录**，不是「把 247 条都搬过来」。

## 决策

### 1. 三类判定，各有明确判据

| 判定 | 判据 |
| --- | --- |
| **已对齐** | 本项目在功能上达到同一可观察行为；实现方式可以不同（本项目更彻底或更轻都算） |
| **待对齐** | 参照实现修的是真实缺陷或提供了本项目缺失的可观察能力，且不违反本项目的产品面 |
| **不适用** | 依赖本项目不存在的产品功能（Magpie、像素白鼬图标、专家中心、Splash、能力页轮播），或属于参照实现自身布局形态的组成部分（沉浸式顶栏、红绿灯偏移） |

判定的依据是**代码检索与实测**，不是提交标题。表格里每行注明证据类型：
`检索` 表示按标识符在源码里确认了存在；`实测` 表示本轮实际运行验证过；
`未核实` 表示尚未逐项确认，需要单独一轮核查（不得按标题猜测）。

### 3. 本轮的落地范围

只有三条与本轮缺陷直接相关，其余均已标为待对齐：

1. 主线程同步阻塞（订阅同步读、每轮同步读配置、新增阻塞探针）
2. 文件搬运/拖放上限（100 → 5000）
3. 字体设置标题冗余

## 备选方案

- **按提交逐条搬**：247 条里有 30 条是版本号与发布说明，另有大量是参照实现自身
  产品面的迭代（Magpie、像素白鼬、专家中心、Splash）。逐条搬会把不存在的功能
  一起搬进来，且无法判断哪些属于「缺陷」「能力」「形态」。
- **只对齐 chat 领域**：chat 是投入最大、与本项目重合度最高的领域（32 条），但
  侧栏「管理会话」、MCP 传输层这些是能力缺口，不属于形态差异，搁置会持续产生
  两套不同的用户预期。
- **本文档采用的**：按领域归并成可判定的条目，每条给判据与证据类型；
  形态类差异明确记为不适用并写出理由，能力类缺口记为待对齐。

## 后果

- 正面：以后每条对齐工作有明确归属与判据；「不做」有可引用的理由，而不是每轮重新争论。
- 代价：表格里相当一部分行标着「未核实」。这是有意为之——按提交标题推断状态
  正是这份文档要防的错误；未核实的条目在动工前必须先补证据。
- 已知限制：参照实现的 100 条 `refactor` / `style` / `docs` / `chore` 提交未入表。
  它们多数是同一功能的中间迭代（例如顶栏 12 条、模型菜单 12 条），已归并到对应行；
  其余为发布流程与文案，不产生可观察行为差异。

## 下一步顺序

1. 补「未核实」的证据（按标识符检索 + 必要时实测），把表格从推断变成事实。
2. 侧栏「管理会话」面板（能力缺口，含 >80 条虚拟列表）。
3. 顶栏收纳（只做「多余按钮收进更多菜单」，不引入按钮组与插件贡献点）。
4. 图片解码两条与 MCP 传输层（都需要先取样本/取协议细节）。
