# ADR-0100：输入 Composer 使用能力与布局双重组合

## 状态

已接受

## 背景

普通对话与 Agent Team 都需要编辑、附件、命令、语音、队列和运行时交互等输入能力，但它们的发送目标与运行时生命周期不同。原输入栏把全部状态集中在一个 `InputBarModel`，主题层再通过固定 `regions` prop 对象接收路由、附件、编辑器和工具栏。新增能力需要同时修改中心 model、view 和固定 slot 合同，Team 只能复制功能或错误绑定普通会话状态。

## 决策

1. 输入 Composer 分为能力组合与布局组合。能力以稳定 ID 注册，可声明依赖、冲突和一个或多个语义区域贡献；组合器在装配时拒绝重复、缺失依赖和冲突，并按显式顺序稳定输出贡献。
2. 可主题化布局使用 Compound Components 表达 `Root`、`Content`、`Routing`、`Command`、`Attachments`、`Editor` 与 `Toolbar`，不再通过固定 `regions` 对象或持续增长的布尔 props 描述组件树。
3. props 继续用于叶子组件的数据、事件和局部视觉状态；能力是否存在由场景 preset 决定，能力出现在哪里由语义区域贡献决定，普通对话或 Team 的发送语义由各自 host 持有。
4. 一个能力可以向多个区域贡献内容。例如附件能力同时贡献附件预览和工具栏动作，删除能力时两者必须一起消失，避免残留半套 UI。
5. 语义区域是受控布局合同，不接受外部插件任意注入 React 组件。外部扩展只能提供宿主可验证的结构化描述，由可信 Renderer 映射为 UI。
6. 输入数据使用结构化合同传递。Team 附件沿用 `PromptAttachmentRef`，不再编码进用户文本；旧会话中的内联附件标记仅保留读取兼容。

## 后果

- 普通对话和 Team 可以共享能力实现，同时保留不同的会话、队列和多成员路由语义。
- 新增或移除能力不再要求扩展中央 View props；无效能力图会尽早失败。
- 布局在 JSX 中保持可读，主题和场景可以重组语义区域，但不能绕过可访问性、主题和安全边界。
- 迁移按行为保持方式渐进进行；尚未拆出的旧 `InputBarModel` 字段应随对应能力迁移删除，不能继续作为长期扩展入口。
