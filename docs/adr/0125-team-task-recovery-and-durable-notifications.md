# ADR-0125：团队任务恢复预算与持久化通知

## 状态

已接受

## 背景

openvetta/open-vetta#26 反馈主控在委派后停住，需要用户反复要求继续。当前流程只在成员成功发布结果时唤醒发起者；失败、阻塞与通知交付失败可能只留下任务状态。Runtime 的 `continue`、`retry` 和上下文触发回合不返回 prompt 回执，宿主不能仅凭它们正常返回或之前出现的进度文字判定成功。

此外，SDK 连接超时对象的 `name` 可能仍为 `Error`，按名称判断会丢失可重试语义。团队已有自己的重试调度，Runtime 自动重试在团队成员中关闭，必须保持单一恢复所有者。

## 决策

1. AI Provider 适配层按对应 SDK 的异常类型识别超时、连接失败和主动取消，保留已有协议错误。Desktop 在一次执行前记录持久化条目 ID，执行后同时检查新增结果和 Runtime 失败记录；失败后的旧进度不能作为成功结果。
2. 每项新任务保存 `recovery.maxAutomaticRetries` 与 `recovery.automaticRetries`。默认额外恢复 2 次；自建团队设置允许 0–10 次，0 表示关闭。设置只影响新任务。历史 attempt 编号继续用于身份，不再兼任预算。
3. 定时重试、宿主中断恢复以及模型请求恢复共用持久化预算；按任务 revision 原子领取，重复请求只消费一次。明确的用户恢复与匹配的外部条件变化可重置预算。达到上限进入 `attention-required`，记录 `TEAM_RECOVERY_EXHAUSTED`，不再保留下一次自动重试时间。
4. 完成、失败、阻塞或没有自动重试计划的中断向任务发起者发送通知。协调 Conversation 中的 `agent-team.task-notification.v1` 按任务 ID、revision、接收者去重；接收任务的 `notificationIds` 是持久化接收凭据。接收后的失败由该任务的恢复机制处理，不重复创建主控任务。恢复时可重建通知上下文，已经写入成员 Conversation 的上下文不重复导入。通知交付不占用发送成员的执行队列。
5. 已加载且未停止的团队每 30 秒进行一次本地检查，核对团队调度队列、执行登记、事件状态与 Runtime 状态。只有没有实际执行者的 `running` 任务才恢复；同时补建重试计时器和未交付通知。检查本身不调用模型，不使用静默时长终止仍在执行的工具或请求。单次检查串行完成后才安排下一次。
6. `agent-team.recovery-stop.v1` 在协调 Conversation 保存用户停止状态。停止先封住内存准入，再取消工作并持久化；新用户消息解除停止时废弃旧通知。历史已完成记录没有本次新增的恢复标记，不在升级时批量唤醒主控。

## 备选方案

- 周期性给主控发送“继续”：无法区分健康长任务与失联任务，还会产生模型调用费用。
- 仅添加错误通知：通知自身丢失、任务状态与执行者不一致时仍无法恢复。
- 同时启用 Runtime 与 Team 自动重试：形成两个预算、两个计时器及重复执行风险。
- 用总 attempt 数作为上限：用户主动恢复之后也会永久耗尽自动恢复机会。
- 通知写入前就删除内存待交付项：进程崩溃会丢失唯一交付意图。

## 后果与边界

新增配置和记录字段均可选，旧配置继续读取；不新增数据库、独立任务文件或 Runtime 公共 API。插件团队定义仍由插件维护，本次不开放编辑其恢复设置，沿用默认值。

本地状态无法证明一个仍占用 Runtime 的外部调用已经失效，因此此类调用仍依赖 Provider 超时、工具自身超时或用户停止；本次不承诺检测所有外部服务假死。自动恢复次数增加也会增加潜在模型消耗。恢复在团队已加载时运行，未打开的历史会话不会为巡检自动加载。

验证覆盖 SDK 真实错误对象、空返回执行的持久化失败、委派后的失败通知、恢复预算与重复领取、通知接收与重启、停止、健康长任务及本地巡检补偿；全部使用受控 Runtime 或内存 Conversation，不访问真实 Provider。
