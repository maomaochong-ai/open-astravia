# 迭代对齐决策文档：从 0.5.72 到 0.5.81

## 目的与范围

本文档把对照的参考实现（下称「参照项目」）在 0.5.72 到 0.5.81 之间落地的全部改动分好类，
逐项标注在本项目的落地状态，并给出本轮的取舍。**它不是变更清单的复制**：参照项目同期
有 247 个非合并提交（其中 15 个是版本号推进、15 个是发布说明、若干为样式微调），
本项目的目标不是把 247 个提交逐个搬过来，而是把其中**用户可感知的行为**对齐，
并明确说明哪些不做、为什么。

统计口径：`git log --no-merges --pretty=format:'%h|%s' v0.5.72..v0.5.81`（共 259 条，
含 12 条合并提交）。按领域分布（仅 feat / fix / perf）：

## 一、按主题归并后的清单与落地判断

### A. 会话页顶栏重构（参照项目投入最大的一块）

参照项目在这九个版本里把会话页顶栏拆成了三层：通用 `<ButtonGroup>` 组件（玻璃胶囊，
支持图标/文字/角标）、声明式「顶栏动作」贡献点（插件可以注册）、以及「收纳」机制
（窗口变窄时把多余按钮收进更多菜单，并支持拖动排序）。相关提交约 24 条。

**本项目现状**：会话页顶栏仍是分散的独立按钮，没有按钮组抽象、没有插件顶栏贡献点、
没有收纳。

**判断：本轮不做。** 理由是它同时触及三层新公共合同（组件 API、插件 SDK 贡献点、
布局状态持久化），而本项目的插件 SDK 版本与参照项目已经分叉；对齐它等于重做一次
插件合同，必须单独一轮并配 ADR。**但这直接对应了用户报告的一个问题**：窗口变窄时
顶栏按钮挤在一起——本轮用一个更小的改动解决（见 D）。

### B. 侧栏性能（与本次「应用卡顿」直接相关）

参照项目做了三件事：会话列表超过 80 条改虚拟列表、行组件 memo 化、顶栏动作探针去重。
另有 `perf(runtime-node): 会话文件解析结果按文件身份缓存，追加事件不再整份重读`。

**本项目现状**：会话行已经是 memo 组件（`DefaultSessionRowView` / `SessionRowView` 都
在用）；会话文件解析缓存上一轮已落地（按 size + mtimeNs 命中）；**虚拟列表未做**。

**判断：虚拟列表本轮不做**（改动面在侧栏列表容器，需要处理滚动定位与
`prepareSidebarSelection` 的锚点计算）；解析缓存的同类问题本轮已修，且修得比参照项目
更彻底（订阅通道改异步读取）。

### C. 运行时与主进程热点（与本次「应用卡顿」直接相关）

参照项目的 `perf(runtime-node)` 三条：图片按文件头尺寸放行不整图解码、模型输入图片
按原图记忆、会话文件解析按文件身份缓存。

**本项目现状**：第 3 条已落地。前两条在图片处理链路上，本项目尚未处理。

**判断：本轮只做「不再把主线程按住」这一类**（异步读取、同步配置读改缓存、
主线程阻塞探针）。图片解码的两条属于纯 CPU 优化，需要先有代表性样本才能判断收益，
本轮不做，列入下一轮。

### D. 窗口 / 布局的小修

参照项目：macOS 红绿灯按页头图标实测中线摆放（三次迭代）、会话页滚到顶第一条消息
不被沉浸式顶栏挡住、活动面板让出顶栏高度。

**判断：红绿灯与沉浸式顶栏不做**——本项目没有沉浸式顶栏，红绿灯偏移是参照项目自己
顶栏形态的一部分。**「会话顶栏过窄时把多余按钮收进更多菜单」做了**（见落地清单）。

### E. 能力页（插件市场）

参照项目：市场顶部轮播去掉实时模糊并在不可见时暂停、安装进度刷新不再重算目录、
插件图标改用 `.icns` 读取、新增系统插件「从外部应用打开」。

**判断**：`.icns` 那条不做（本项目没走到 `app.getFileIcon`，是 macOS 上主进程崩溃的
成因）；「从外部应用打开」不做（新增插件，超出对齐范围）；轮播性能不做（本项目能力页
没有轮播）。**与本轮直接相关的是安装网络失败**——参照项目没有这条改动，本轮自行修复
（见下）。

### F. 设置页重构（11 条）

参照项目把设置页大量改成「同款下拉 + 卡片」，并把插件可用性设置改为按钮组 + 下拉。

**判断：整体不做。** 这是视觉重构，与本次的缺陷修复无关；本项目设置页已在上轮对齐过
一轮（字体、外观）。**只做其中一条与本轮缺陷相关的**：字体设置的主标题与行标题重复
（见落地清单）。

### G. 更新器（7 条）

参照项目修了更新对话框无法滚动、按钮被盖住、更新日志还原成 Markdown、下载期间按钮
禁用。

**判断：不做。** 本项目的更新器是自建通道，对话框结构不同；这 7 条都属于
「已在参照项目结构内的问题」，在结构不同的地方强行套用会引入新问题。列入下一轮
（若本项目更新对话框也有同样症状）。

### H. 其余（theme / skill / project / plugin-sdk / open-in-app / mcp 等）

多为参照项目自己的品牌与产品线差异（主题包、专家中心、企微/飞书连接器）。**不做**，
与本项目无关。

## 三、明确不做，以及为什么

1. **会话页顶栏三层重构（24 条提交）**：需要新组件 API + 插件贡献点 + 布局持久化，
   等于重做插件合同，必须单独一轮并配 ADR。
2. **侧栏虚拟列表**：改动面在列表容器与滚动锚点，本轮没有可信的性能数据支撑收益。
3. **图片解码优化两条**：纯 CPU，需要代表性样本才能判断收益。
4. **设置页 / 更新器 / 主题 / 产品线相关的视觉重构**：与本轮缺陷无关，且参照项目的
   结构已与本项目分叉。

## 四、下一轮建议顺序

1. 侧栏虚拟列表（先量：会话数 100 / 500 / 2000 时的滚动帧时间）。
2. 顶栏收纳（小改：把「多余按钮收进更多菜单」单独做，不引入按钮组与插件贡献点）。
3. 图片解码优化（先取三张典型截图量处理耗时）。
