# 服务层模式（Service Layer）

**类别：** 企业应用模式

## 意图

定义应用边界和用例入口，协调事务、领域对象和基础设施。

## 什么时候使用

- 多个入口（HTTP、消息、CLI）需要复用同一用例。
- 事务边界应围绕业务用例。
- 需要隔离表现层与领域/持久化。

## 什么时候不要使用

- 业务极其简单，额外层只会一比一转发。
- 把所有领域规则都塞进 Service 导致贫血模型。

## 识别信号

- Controller 直接操作数据库
- 多个入口重复业务编排
- 事务边界混乱

## Agent 决策规则

- 当问题核心与“定义应用边界和用例入口，协调事务、领域对象和基础设施”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 按用例设计服务方法。
- Service 负责编排，领域对象负责核心规则。
- 接口 DTO 与领域模型适度隔离。

## 常见误用

- 巨型 XxxService。
- 一个 Service 方法几百行包含全部规则。
- Service 对 Controller/HTTP 细节强依赖。

## 常见组合

- Application Service
- Repository
- Unit of Work

## 最小示意

```text
CheckoutService.checkout(command)
```

## 深度分析

### 变化压力
Service Layer 定义应用用例边界，解决多个入口重复编排、事务边界混乱和表现层耦合。它不等于“所有逻辑都放 Service”。

### 结构与协作
Controller、消息消费者和 CLI 都调用面向用例的方法；服务协调授权、事务、Repository、领域对象和事件发布，并返回稳定结果。领域规则留在 Entity/Value Object/Domain Service，技术依赖通过端口注入。

### 关键权衡与替代
收益是流程复用和可追踪性，代价是额外跳转和服务拆分成本。若只有一条简单路径，直接 handler/函数更简单；若领域规则复杂，应采用 Application Service + 聚合，而不是扩充一个万能 Service。Façade 只提供子系统入口，不应承担所有用例。

### 落地与验证
按用户可执行的用例切片，一个服务方法一个事务边界。测试从入口命令到持久化/响应的连续流程，覆盖授权、领域错误、回滚和重复请求；日志带 useCase、correlationId 和结果类别。方法超过一个屏幕后按业务能力拆服务。

## 退出条件

当服务仅做无逻辑转发，或用例已自然归属单一领域对象时，合并服务层或下沉行为。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
