# 服务发现模式（Service Discovery）

**类别：** 分布式系统模式

## 意图

动态定位服务实例，使调用方不依赖固定 IP/端口。

## 什么时候使用

- 实例弹性伸缩、地址动态变化。
- 微服务需要负载均衡与健康实例发现。
- 平台不已透明提供 DNS/Service abstraction。

## 什么时候不要使用

- Kubernetes/服务网格已经提供充分发现机制，无需应用层再造注册中心。
- 固定少量服务且地址稳定。

## 识别信号

- 动态实例列表
- registry/DNS
- client-side/server-side discovery

## Agent 决策规则

- 当问题核心与“动态定位服务实例，使调用方不依赖固定 IP/端口”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 优先使用平台能力。
- 健康检查与注册 TTL 明确。
- 客户端缓存要有失效策略。

## 常见误用

- 应用内硬编码注册中心逻辑。
- 把发现与业务路由混在一起。

## 常见组合

- API Gateway
- Circuit Breaker

## 最小示意

```text
serviceName -> healthy instances -> load balancer
```

## 深度分析

### 变化压力
Service Discovery 解决实例地址动态变化、健康筛选和负载分发；它不是把业务路由规则塞进注册中心。先检查平台 DNS、Service Mesh 或负载均衡是否已提供同等能力。

### 结构与协作
服务注册/发现记录名称、实例、健康状态和 TTL；客户端或服务端负载均衡选择实例，缓存必须有失效和 stale 上限。调用层仍需要 timeout、retry 和 circuit breaker，发现失败要有明确的 fail-fast/缓存策略。

### 关键权衡与替代
自建注册中心增加一致性、心跳、拓扑和运维成本。固定地址可用配置/DNS；Kubernetes、Consul 或 mesh 已覆盖时直接复用。客户端发现灵活但每个客户端都要维护策略，服务端发现更集中但增加代理跳数。

### 落地与验证
先定义注册 TTL、健康检查、摘除延迟、区域/版本标签和回退策略，再接一个无状态服务。测试实例上下线、注册中心不可用、缓存过期、跨区选择和滚动发布；监控发现延迟、过期实例命中、健康误判和负载倾斜。不要把密钥放进实例元数据。

## 退出条件

当部署平台已透明提供发现，或实例地址长期稳定时，删除应用层注册/发现代码。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
