# 重试模式（Retry）

**类别：** 分布式系统模式

## 意图

对暂时性失败进行有限次数的再次尝试，提高远程调用成功率。

## 什么时候使用

- 失败是瞬态：网络抖动、限流、短暂不可用。
- 操作是幂等的或有去重保障。
- 重试成本和额外延迟可接受。

## 什么时候不要使用

- 参数错误、权限错误等永久失败。
- 非幂等写操作且没有幂等键。
- 下游已过载，盲目重试会放大故障。

## 识别信号

- timeout/503/429
- transient failure
- exponential backoff

## Agent 决策规则

- 当问题核心与“对暂时性失败进行有限次数的再次尝试，提高远程调用成功率”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 限制次数和总时间预算。
- 指数退避 + jitter。
- 仅对可重试错误重试。
- 写请求使用幂等键。

## 常见误用

- 无限重试。
- 多层同时重试造成 retry storm。
- 固定间隔同步重试造成惊群。

## 常见组合

- Circuit Breaker
- Idempotency
- Bulkhead

## 最小示意

```text
retry(max=3, backoff=exponential+jitter, when=transient)
```

## 深度分析

### 变化压力
Retry 只对可恢复的瞬态失败提供有限再试；它不能修复参数错误，也不能把非幂等写变成安全操作。先定义总时间预算和调用方可接受的延迟。

### 结构与协作
错误分类器只重试 timeout、连接中断、429/503 等明确类别；采用指数退避 + jitter、最大次数和总 deadline，并把剩余预算传给下游。写操作必须携带幂等键，重试层只能存在一个主要 owner，避免嵌套风暴。

### 关键权衡与替代
重试提高短暂故障成功率，但会增加延迟、负载和重复副作用。对持续故障应组合 Circuit Breaker/Bulkhead；对可接受降级的读请求，fallback 可能比再试更好。客户端和服务端都重试时要协调预算。

### 落地与验证
先针对一个远程依赖建立错误矩阵和 deadline 传递，再启用有限策略。测试退避上限、jitter、取消、429 Retry-After、预算耗尽和非重试错误；监控 attempt count、retry delay、success-after-retry、amplification ratio。日志记录错误类别和尝试次数，不记录凭证。

## 退出条件

当依赖不再有瞬态失败、调用不可安全重试或平台统一接管策略时，删除本地重试。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
