# 舱壁模式（Bulkhead）

**类别：** 分布式系统模式

## 意图

隔离不同资源池或故障域，避免一个依赖/租户耗尽全部资源拖垮系统。

## 什么时候使用

- 多个外部依赖共享线程池/连接池。
- 高风险调用可能阻塞。
- 多租户/多任务需要资源隔离。

## 什么时候不要使用

- 系统规模小且资源竞争不是问题。
- 隔离后资源碎片化成本高于收益。

## 识别信号

- 一个下游故障耗尽所有线程
- 独立连接池/线程池/并发限额

## Agent 决策规则

- 当问题核心与“隔离不同资源池或故障域，避免一个依赖/租户耗尽全部资源拖垮系统”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 按故障域隔离资源。
- 设置队列和并发上限。
- 配合限流、超时和监控。

## 常见误用

- 每个调用都建独立池导致资源浪费。
- 只有隔离没有容量规划。

## 常见组合

- Circuit Breaker
- Retry

## 最小示意

```text
paymentsPool != recommendationsPool
```

## 深度分析

### 变化压力
Bulkhead 针对资源竞争：一个慢或故障的依赖不应耗尽整个进程的线程、连接或并发额度。先用指标证明资源池共享导致了级联影响，而不是凭感觉拆池。

### 结构与协作
按故障域划分并发信号量、线程池、连接池或租户配额；每个隔离区设排队上限、超时和拒绝策略。调用链要把资源归属和 trace 传递清楚，必要时配合 Circuit Breaker 快速释放占用。

### 关键权衡与替代
隔离提高故障局部性，但会造成容量碎片、调度复杂和低峰浪费。若瓶颈是请求速率而非资源耗尽，限流更合适；若是持续下游故障，熔断更直接。过细的租户池可能比共享池更不稳定。

### 落地与验证
先为最高风险依赖增加一个有界信号量，记录 acquire wait、reject 和 queue depth，再逐步分离资源。测试满池、超时、取消释放和一个池故障时其他池仍可用；压测验证隔离后的吞吐和尾延迟。指标必须能按池/租户观测。

## 退出条件

当资源竞争消失或隔离后的空闲容量长期高于收益时，合并资源池并保留总量限流。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
