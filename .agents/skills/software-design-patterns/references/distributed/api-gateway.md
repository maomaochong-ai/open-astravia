# API 网关模式（API Gateway）

**类别：** 分布式系统模式

## 意图

为外部客户端提供统一入口，处理路由、认证、限流、协议转换和聚合等边缘能力。

## 什么时候使用

- 多个微服务需要统一外部入口。
- 横切边缘策略需集中。
- 客户端不应感知内部服务拓扑。

## 什么时候不要使用

- 单体或少量服务无需额外网络跳数。
- 把核心业务编排全部塞进网关。
- 内部服务之间也被强迫经过外部网关。

## 识别信号

- 统一域名
- route/auth/rate-limit
- BFF

## Agent 决策规则

- 当问题核心与“为外部客户端提供统一入口，处理路由、认证、限流、协议转换和聚合等边缘能力”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 网关处理边缘关注点。
- 复杂客户端定制可拆 BFF。
- 核心业务仍在服务内部。

## 常见误用

- God Gateway。
- 网关持有领域状态。
- 单点容量/可用性没有冗余。

## 常见组合

- Facade
- Service Discovery
- Circuit Breaker

## 最小示意

```text
Client -> Gateway -> Orders/Users/Payments
```

## 深度分析

### 变化压力
API Gateway 解决外部客户端需要统一入口、认证和拓扑隐藏的问题；它不是把微服务内部所有业务集中起来的“总服务”。先确认客户端数量、协议差异和边缘策略是否已经产生重复。

### 结构与协作
Gateway 完成 TLS、身份验证、限流、路由、超时和少量响应聚合，调用下游通过 Service Discovery 和熔断器。核心领域校验、事务和状态写入仍在下游服务；按客户端体验差异可拆成多个 BFF，避免一个入口承载所有受众。

### 关键权衡与替代
集中入口便于治理，但增加网络跳数、单点容量和发布耦合。单体或固定服务可用反向代理/DNS；仅需协议转换时用 Adapter；只需模块级简化 API 时用 Facade。聚合多个下游时必须定义部分失败和响应降级语义。

### 落地与验证
先把一个只读路由迁移到 Gateway，明确 header、鉴权、超时和错误映射契约。测试未授权、限流、下游超时、部分成功和追踪上下文；监控 p95、下游错误率、队列/连接池和每路由成本。若网关开始写领域状态，立即拆回服务。

## 退出条件

当服务数量、客户端差异或边缘策略不足以抵消网络与运维成本时，回退到平台反向代理或直接服务入口。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
