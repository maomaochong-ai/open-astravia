# 抽象工厂模式（Abstract Factory）

**类别：** GoF / 创建型

## 意图

创建一组彼此兼容、属于同一产品族的对象，而无需暴露具体类。

## 什么时候使用

- 系统需要在多个产品族之间整体切换，例如不同云厂商的一组存储/消息/密钥客户端。
- 同一产品族中的对象必须保证兼容。
- 平台或主题切换会影响一整套组件。

## 什么时候不要使用

- 只需要创建一种对象；Factory Method 足够。
- 产品维度经常横向新增，导致每个工厂接口都要改。
- 产品之间没有族一致性约束。

## 识别信号

- AWS/Azure/GCP 各自一套组件
- 不同 UI 主题对应一组控件
- 需要成套替换实现

## Agent 决策规则

- 当问题核心与“创建一组彼此兼容、属于同一产品族的对象，而无需暴露具体类”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 定义“产品族”边界，再定义工厂接口。
- 保证同一工厂产出的对象可协同工作。
- 如果产品种类频繁新增，评估插件注册表而非固定抽象工厂接口。

## 常见误用

- 只有一个产品却引入整套抽象工厂。
- 产品族边界不稳定，接口频繁膨胀。
- 把服务定位器伪装成抽象工厂。

## 常见组合

- Factory Method
- Bridge
- Dependency Injection

## 最小示意

```text
cloud = CloudFactory.for(provider); storage = cloud.storage(); queue = cloud.queue()
```

## 深度分析

### 变化压力
Abstract Factory 处理的是“产品族整体切换”，例如同一云厂商的一组存储、队列和密钥客户端必须兼容。只有一种产品或产品族边界尚未稳定时，Factory Method 更合适。

### 结构与协作
定义按能力命名的工厂接口，具体工厂创建同族产品；composition root 根据配置选择一个工厂并注入，业务只依赖产品端口。新增产品种类会迫使所有工厂扩展接口，这是该模式最重要的演进成本。

### 关键权衡与替代
产品族一致性收益很大，但接口膨胀和全族升级成本也高。若产品独立变化，用多个 Factory/注册表；若只有参数差异，用配置；若两个正交维度导致类爆炸，Bridge 可能更清晰。不要把服务定位器伪装成工厂。

### 落地与验证
先列出必须成套兼容的产品和禁止混用组合，再实现一个完整族并在装配处切换。测试工厂产物互操作、缺失能力、配置错误和版本兼容；日志记录 provider/driver 版本。新产品加入时评估是否应拆成能力端口，而非继续扩张工厂。

## 退出条件

当产品族不再整体切换或工厂接口修改频率高于收益时，拆成独立工厂/注入端口。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
