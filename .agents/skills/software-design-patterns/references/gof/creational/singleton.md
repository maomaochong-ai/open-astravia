# 单例模式（Singleton）

**类别：** GoF / 创建型

## 意图

保证一个逻辑组件在给定作用域内只有一个共享实例，并提供稳定访问点。

## 什么时候使用

- 组件代表全局唯一资源或进程级协调器，例如配置注册表、进程内锁管理器。
- 实例数量必须被严格控制，而且生命周期清晰。
- 依赖注入容器已经把对象生命周期定义为 singleton scope，业务只需声明依赖。

## 什么时候不要使用

- 只是为了“少 new 几次”或节省少量内存。
- 对象包含请求级、用户级或租户级可变状态。
- 测试需要隔离状态，而全局实例会导致测试顺序依赖。
- 分布式系统中需要“全局唯一”；进程内 Singleton 无法满足跨进程唯一性。

## 识别信号

- 到处访问同一个服务实例
- 需要进程内唯一协调点
- 重复初始化昂贵且必须共享

## Agent 决策规则

- 当问题核心与“保证一个逻辑组件在给定作用域内只有一个共享实例，并提供稳定访问点”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 优先使用依赖注入容器管理生命周期，而不是手写静态 getInstance。
- 明确线程安全、初始化时机和销毁策略。
- 将状态最小化；尽量让 singleton 无状态。

## 常见误用

- 把 Singleton 当全局变量，造成隐式依赖。
- 双重检查锁写错或忽略内存模型。
- 在多租户系统把租户状态放入单例。

## 常见组合

- Dependency Injection
- Factory Method

## 最小示意

```text
Container.bind(ConfigRegistry).scope(SINGLETON)
```

## 深度分析

### 变化压力
Singleton 只承诺某个明确作用域内一个实例；常见合理范围是进程级无状态协调器或容器 singleton scope，而不是“全局变量”。先证明唯一性是不变量，而非节省几次 new。

### 结构与协作
优先在 composition root/DI 容器声明生命周期，显式注入使用者；定义初始化时机、线程安全、关闭和热重载策略。分布式唯一性必须使用 lease/共识存储，不能靠每个进程各自的 Singleton。

### 关键权衡与替代
共享实例减少资源和协调成本，但引入隐式状态、测试污染和并发耦合。普通无状态函数无需 Singleton；请求/租户状态应放作用域对象；需要可替换实现时，DI scope 比静态 getInstance 更容易测试。

### 落地与验证
先列出实例状态、并发访问和销毁 owner，再把现有静态访问迁移为注入。测试并行调用、初始化失败、重启/关闭、测试隔离和多实例部署语义；监控资源泄漏和初始化耗时。禁止在单例中缓存租户或用户数据。

## 退出条件

当容器生命周期已足够、共享状态造成更多耦合，或需求其实是跨进程协调时，删除 Singleton，改用作用域对象或 Leader/锁服务。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
