# 原型模式（Prototype）

**类别：** GoF / 创建型

## 意图

通过复制已有对象来创建新对象，适合初始化昂贵或需要保留模板状态的场景。

## 什么时候使用

- 创建成本高，而已有实例可作为模板。
- 需要从运行时模板派生大量相似对象。
- 具体类型在运行时才知道，复制比重新构造更自然。

## 什么时候不要使用

- 对象图简单且正常构造便宜。
- 对象包含不可安全复制的资源，如 socket、线程、文件句柄。
- 深拷贝/浅拷贝语义无法明确。

## 识别信号

- 模板对象复制
- 克隆复杂配置
- 初始化步骤昂贵

## Agent 决策规则

- 当问题核心与“通过复制已有对象来创建新对象，适合初始化昂贵或需要保留模板状态的场景”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 明确浅拷贝与深拷贝边界。
- 不可复制资源应重新绑定或排除。
- 复制后仍要维持对象不变量。

## 常见误用

- 默认 clone 导致共享可变引用。
- 复制数据库连接/锁等外部资源。
- 把 Prototype 当通用性能优化。

## 常见组合

- Builder
- Factory Method

## 最小示意

```text
draft = template.copy(overrides={"title": "New"})
```

## 深度分析

### 变化压力
Prototype 通过复制运行时模板创建对象，适用于初始化昂贵或模板状态复杂且具体类型未知的场景。必须先定义复制边界，否则共享引用会把 bug 变成隐式状态污染。

### 结构与协作
原型提供 copy/clone 或不可变派生 API；复制过程明确 intrinsic 数据、可变集合、身份字段和外部资源。数据库连接、锁、文件句柄、线程等资源不得复制，应由新对象重新绑定。

### 关键权衡与替代
复制省去重复构造，但深拷贝成本、版本兼容和调试复杂度很高。普通构造便宜时直接 new；参数多时 Builder；成套初始化用 Factory。序列化 round-trip 不能自动证明复制语义正确。

### 落地与验证
先为模板建立 ownership 表，规定哪些字段共享、复制或重置，再实现一个显式 copyWith。测试复制后修改互不影响、身份重置、资源重新绑定和旧模板版本；用 profile 证明构造成本确实是瓶颈。禁止无文档的通用深拷贝。

## 退出条件

当模板初始化已足够便宜、复制语义难以维护或对象含外部资源时，删除 Prototype。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
