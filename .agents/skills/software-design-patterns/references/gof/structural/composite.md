# 组合模式（Composite）

**类别：** GoF / 结构型

## 意图

把单个对象与对象组合统一成同一接口，适合树形层级结构。

## 什么时候使用

- 数据天然是树：组织、菜单、文件系统、表达式树、UI 组件。
- 客户端希望一致处理叶子与容器节点。
- 需要递归执行统一操作。

## 什么时候不要使用

- 结构不是树或共享节点会形成复杂图。
- 叶子和容器行为差异巨大，统一接口会很虚假。
- 层级很浅且没有统一处理需求。

## 识别信号

- 递归节点
- children 列表
- 叶子和容器需要统一 render/calc/validate

## Agent 决策规则

- 当问题核心与“把单个对象与对象组合统一成同一接口，适合树形层级结构”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 定义最小公共 Component 接口。
- 明确父子关系、生命周期和循环检测。
- 对昂贵递归操作考虑缓存或迭代实现。

## 常见误用

- 让叶子实现大量无意义的 add/remove。
- 忽略循环引用导致无限递归。
- 用 Composite 掩盖本应是关系图的数据模型。

## 常见组合

- Iterator
- Visitor

## 最小示意

```text
total = root.calculate(); // root 与 leaf 都实现 calculate()
```

## 深度分析

### 变化压力
Composite 适合真实的树，并且叶子与容器都能接受同一操作。先确认节点只有一个父节点、不会共享形成图；否则递归语义、删除和循环检测会变得含糊。

### 结构与协作
Component 定义最小公共操作；Leaf 执行本地行为，Composite 管理有序 children、父子生命周期和递归聚合。对外返回只读集合，深度优先/广度优先遍历通过原生 Iterator 或显式 Visitor 暴露。

### 关键权衡与替代
统一处理减少分支，但会迫使叶子实现不适用的方法，并带来深度、缓存和循环风险。图结构使用图模型；层级很浅用普通列表；需要新增跨节点操作可再加 Visitor。

### 落地与验证
先定义树不变量（无环、唯一父、删除语义），迁移一个递归计算。测试空树、深树、循环输入、重复节点、叶子/容器错误和大规模栈深；监控遍历耗时、节点数和缓存命中。不要让 Component 隐藏远程分页。

## 退出条件

当结构变成共享图或叶子/容器无法保持共同语义时，拆回显式树/图服务。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
