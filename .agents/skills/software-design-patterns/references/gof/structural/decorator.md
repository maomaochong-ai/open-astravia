# 装饰器模式（Decorator）

**类别：** GoF / 结构型

## 意图

在不修改原对象的情况下，通过包装动态叠加职责。

## 什么时候使用

- 功能可正交叠加，例如日志、压缩、加密、缓存。
- 继承会导致组合数量爆炸。
- 希望按运行时配置增减能力。

## 什么时候不要使用

- 增强顺序无意义且可以集中用 middleware/pipeline 更清楚。
- 需要的是访问控制或远程替身，Proxy 更贴切。
- 包装层太多导致调试和错误定位困难。

## 识别信号

- Wrapper 链
- 功能叠加
- 继承子类组合爆炸

## Agent 决策规则

- 当问题核心与“在不修改原对象的情况下，通过包装动态叠加职责”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- Decorator 与被包装对象实现同一接口。
- 每个装饰器只增加一个聚焦职责。
- 明确装饰顺序是否影响语义。

## 常见误用

- 装饰器偷偷改变核心语义而不只是增强。
- 几十层包装导致堆栈难懂。
- 与 Proxy 混淆，职责不清。

## 常见组合

- Proxy
- Chain of Responsibility

## 最小示意

```text
client = Metrics(Retry(Cache(HttpClient())))
```

## 深度分析

### 变化压力
Decorator 适合横切能力可正交叠加且顺序有意义，例如缓存、指标和压缩。先区分“增强同一契约”与“改变访问控制/远程替身”；后者通常是 Proxy。

### 结构与协作
每个 Decorator 实现同一接口并持有 next，只增加一个聚焦职责；composition root 按声明顺序组装，并为每层设置超时、上下文和错误传播规则。核心对象不应知道包装链存在。

### 关键权衡与替代
包装链避免子类组合，但会增加堆栈深度、顺序耦合和可观测性成本。中间件/pipeline 更适合需要统一上下文的请求流；简单日志可直接调用；功能不是正交增强时不要套 Decorator。

### 落地与验证
先选择一个能力（如 metrics）并定义前后置语义，再加入链。测试顺序、异常、取消、短路和上下文透传；日志/trace 标明 decorator 名称和链版本。限制层数并提供诊断输出，避免调试只能看匿名 wrapper。

## 退出条件

当链超过可解释上限、顺序不再稳定或装饰器改变核心业务语义时，合并为显式 pipeline/服务。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
