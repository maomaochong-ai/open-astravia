# 备忘录模式（Memento）

**类别：** GoF / 行为型

## 意图

在不破坏封装的前提下保存对象状态快照，以便后续恢复。

## 什么时候使用

- 编辑器 undo/redo。
- 短期回滚、草稿快照。
- 对象状态可被安全序列化/复制。

## 什么时候不要使用

- 状态很大、变化频繁，完整快照成本过高。
- 需要审计和事件重放，Event Sourcing 更合适。
- 状态包含不可恢复外部资源。

## 识别信号

- 撤销
- 快照恢复
- checkpoint

## Agent 决策规则

- 当问题核心与“在不破坏封装的前提下保存对象状态快照，以便后续恢复”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 快照应不可变。
- 控制保留数量和内存。
- 敏感数据要考虑加密/生命周期。

## 常见误用

- 把数据库备份简单等同 Memento。
- 无限保存快照导致内存爆炸。
- 快照漏掉关键状态导致恢复不一致。

## 常见组合

- Command
- Event Sourcing

## 最小示意

```text
history.push(editor.snapshot()); editor.restore(history.pop())
```

## 深度分析

### 变化压力
Memento 保存短期状态快照以支持 undo/redo 或草稿恢复，同时不暴露内部可变结构。先定义快照范围、大小上限和恢复后应保持的不变量。

### 结构与协作
Originator 创建不可变 Snapshot，Caretaker 管历史、顺序、容量和持久化；快照不应包含 socket、线程等不可恢复资源。恢复要经过版本/校验，必要时重新绑定外部资源。

### 关键权衡与替代
完整快照简单可靠但占内存/存储，增量快照或 Command inverse 可能更省；需要完整事实历史用 Event Sourcing；数据库备份不等于对象 Memento。敏感草稿要加密和过期清理。

### 落地与验证
先测量状态大小与频率，再选全量或增量。测试多步 undo/redo、分支历史、版本升级、损坏快照、容量淘汰和资源重建；指标记录快照大小、恢复耗时和丢弃数。恢复失败不能静默继续。

## 退出条件

当状态过大、变化频率高或业务需要长期审计时，改用增量命令、事件源或专用版本存储。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
