# 迭代器模式（Iterator）

**类别：** GoF / 行为型

## 意图

在不暴露集合内部表示的情况下顺序访问元素。

## 什么时候使用

- 自定义集合/树需要标准遍历协议。
- 希望提供多种遍历策略。
- 调用方不应了解内部存储结构。

## 什么时候不要使用

- 语言/框架已有迭代协议且直接实现即可，不必额外造层。
- 需要的是批处理流、响应式流或分页协议，而非内存迭代。

## 识别信号

- for-each 支持
- 树 DFS/BFS
- 隐藏内部集合结构

## Agent 决策规则

- 当问题核心与“在不暴露集合内部表示的情况下顺序访问元素”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 优先实现语言原生 iterable/iterator 协议。
- 定义并发修改策略。
- 大数据源注意惰性与资源释放。

## 常见误用

- 把远程分页伪装成廉价 Iterator，隐藏 I/O。
- 迭代器持有资源却没有 close。

## 常见组合

- Composite
- Visitor

## 最小示意

```text
for item in collection: ...
```

## 深度分析

### 变化压力
Iterator 的目标是隐藏集合内部表示，同时提供遍历协议；在 TypeScript/Go/Kotlin 中应优先使用原生 iterable、iterator、sequence 或 stream 接口，而不是再造同名抽象。

### 结构与协作
Iterator 明确游标、惰性求值、结束和并发修改语义；若底层是文件、网络或数据库，协议必须包含 close/cancel/生命周期。分页和流式消费要显式标注 I/O 与背压。

### 关键权衡与替代
抽象遍历便于替换存储，但隐藏远程成本会造成资源泄漏和超时误用。数组/集合直接 for-each；复杂树可用 Visitor；批处理系统用分页/流协议而不是伪装 Iterator。

### 落地与验证
先确定遍历是否纯内存，再实现原生协议。测试空集合、早停、重复 next、并发修改、资源释放和背压；指标记录读取批次、游标年龄和未关闭句柄。禁止让迭代器跨请求无限持有连接。

## 退出条件

当语言原生协议已足够或遍历不是独立变化点时，删除自定义 Iterator。
