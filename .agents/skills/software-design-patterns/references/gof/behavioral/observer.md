# 观察者模式（Observer）

**类别：** GoF / 行为型

## 意图

当一个对象发生变化时，向多个订阅者广播通知，降低发布者对具体订阅者的依赖。

## 什么时候使用

- 一个事件要触发多个相互独立的反应。
- 订阅者集合会变化。
- 允许最终一致或异步处理。

## 什么时候不要使用

- 后续动作必须严格事务一致且失败要整体回滚。
- 事件链会形成难以追踪的隐式控制流。
- 只有一个固定调用方，直接调用更清晰。

## 识别信号

- 事件监听器
- publish/subscribe
- 订单完成后多个后续动作

## Agent 决策规则

- 当问题核心与“当一个对象发生变化时，向多个订阅者广播通知，降低发布者对具体订阅者的依赖”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 事件名称表达“已经发生的事实”。
- 明确同步/异步、顺序、失败策略。
- 跨进程场景考虑消息系统、幂等和 Outbox。

## 常见误用

- 把命令当事件，例如“SendEmailEvent”。
- 循环事件导致风暴。
- 订阅器做关键强一致业务却没有事务策略。

## 常见组合

- Domain Event
- Outbox
- Mediator

## 最小示意

```text
eventBus.publish(OrderPaid(orderId))
```

## 深度分析

### 变化压力
Observer 解决一个发布者需要通知可变订阅者集合的问题。事件必须说明同步/异步、顺序、失败和生命周期，否则解耦会变成隐式控制流。

### 结构与协作
Publisher 只依赖事件契约；订阅者注册/取消有明确 owner，事件不可变且 payload 最小。进程内同步通知可直接使用；跨进程需 Outbox、幂等、重试和死信策略。

### 关键权衡与替代
广播减少发布者依赖，但订阅者故障、循环事件和顺序问题会增加调试成本。强一致动作直接调用或同一事务；业务事实用 Domain Event；组件交互协调用 Mediator。

### 落地与验证
先为非关键反应建立事件流，定义 listener error policy 和最大 fan-out。测试取消订阅、重复/乱序、一个订阅者失败时其他订阅者行为和循环保护；监控 fan-out、lag、failure 和 dropped events。禁止把命令命名成 Event。

## 退出条件

当只有一个固定消费者或事件链无法可靠观测时，回退显式调用。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
