# 访问者模式（Visitor）

**类别：** GoF / 行为型

## 意图

把对稳定对象结构的新操作外置，使新增操作不需要修改每个元素类。

## 什么时候使用

- 对象结构类型集合稳定，但要频繁新增横跨所有类型的操作。
- 编译器 AST、文档树、规则树需要多种遍历操作。
- 需要双分派。

## 什么时候不要使用

- 元素类型经常新增；每加一种元素都要改所有 Visitor。
- 操作很少，直接放在元素中更自然。
- 语言支持代数数据类型 + pattern matching 已更简洁。

## 识别信号

- AST 多种分析/打印/优化
- 稳定节点类型 + 新操作多
- 双分派

## Agent 决策规则

- 当问题核心与“把对稳定对象结构的新操作外置，使新增操作不需要修改每个元素类”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 元素提供 accept(visitor)。
- Visitor 接口覆盖全部元素类型。
- 把跨节点操作集中，避免访问者之间共享大量可变状态。

## 常见误用

- 对象类型变化频繁时造成修改风暴。
- Visitor 依赖元素内部太多实现细节。
- 简单业务强行使用双分派。

## 常见组合

- Composite
- Iterator

## 最小示意

```text
node.accept(typeCheckerVisitor)
```

## 深度分析

### 变化压力
Visitor 把对稳定元素结构的新操作外置，适合 AST/文档树等“节点类型稳定、操作不断增加”的模型。若节点类型变化更快，Visitor 会造成所有访问者同步修改。

### 结构与协作
元素实现 accept(visitor) 并提供双分派；Visitor 覆盖全部节点类型，操作状态通过显式上下文传递。遍历、错误和部分结果策略要明确，不能让访问者依赖未声明的内部字段。

### 关键权衡与替代
新增操作成本低，但新增节点成本高、接口刚性大。现代语言 pattern matching/代数数据类型可能更简单；单一操作直接放元素；树结构本身由 Composite 管理。

### 落地与验证
先统计节点与操作变化频率，迁移一个分析 visitor。测试每种节点、未知节点、嵌套树、错误恢复和资源限制；指标记录 visitor 版本、节点计数和耗时。避免访问者在遍历中修改结构导致迭代失效。

## 退出条件

当节点类型持续新增、visitor 接口频繁破坏或语言原生匹配已足够时，迁移 pattern matching/节点方法。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
