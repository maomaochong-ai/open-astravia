# 模板方法模式（Template Method）

**类别：** GoF / 行为型

## 意图

在基类中固定算法骨架，把少数可变步骤留给子类/钩子实现。

## 什么时候使用

- 多个流程整体顺序一致，仅少数步骤不同。
- 需要复用公共流程并保证关键顺序不被改变。
- 框架提供生命周期钩子。

## 什么时候不要使用

- 变化点很多且组合灵活，Strategy/组合优于继承。
- 继承会造成强耦合或已有多重继承限制。
- 流程本身也经常变化。

## 识别信号

- 多个方法复制相同步骤
- 基类 hook
- 公共流程 + 少量差异

## Agent 决策规则

- 当问题核心与“在基类中固定算法骨架，把少数可变步骤留给子类/钩子实现”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 模板方法控制流程，hook 只实现明确差异。
- 对可覆盖方法标明前置/后置约束。
- 优先浅层继承；复杂时转向组合策略。

## 常见误用

- 脆弱基类问题。
- 子类覆盖过多步骤破坏不变量。
- 为了复用几行代码制造继承体系。

## 常见组合

- Strategy
- Factory Method

## 最小示意

```text
process() = validate -> transform* -> persist -> notify*
```

## 深度分析

### 变化压力
Template Method 适合流程骨架稳定、少数步骤变化，并且需要强制顺序和不变量。它依赖继承，因此先确认扩展者可控且不会形成脆弱基类。

### 结构与协作
基类 final/template 方法控制生命周期，hook 只暴露局部差异；子类不得跳过必须步骤。若步骤需要运行时组合，改用 Strategy/显式 Pipeline，避免把可变流程锁死在继承层。

### 关键权衡与替代
模板减少重复并保护顺序，但继承耦合高、测试矩阵随子类增长。变化维度多用组合；只有一个流程用函数；需要创建不同实现用 Factory Method。

### 落地与验证
先提取公共时序和 hook 合同，迁移一个子类。测试骨架顺序、hook 前后条件、异常清理、取消和每个实现差异；指标记录模板版本和阶段耗时。禁止 hook 修改基类关键状态。

## 退出条件

当流程顺序也开始变化、子类覆盖超过少数步骤或继承限制扩展时，改为组合策略。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
