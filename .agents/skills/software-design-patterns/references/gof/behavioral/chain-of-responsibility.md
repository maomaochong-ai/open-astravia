# 责任链模式（Chain of Responsibility）

**类别：** GoF / 行为型

## 意图

让请求沿一系列处理器传递，每个处理器决定处理、拒绝、修改或继续。

## 什么时候使用

- 存在顺序明确的校验、过滤、风控、审批或中间件步骤。
- 处理步骤需要可插拔、可重排。
- 调用方不应知道由哪个节点最终处理。

## 什么时候不要使用

- 步骤之间共享大量隐式状态和强依赖，普通显式流程更易懂。
- 必须保证每一步都执行且顺序固定，pipeline/template 可能更明确。
- 链很短且永远不变。

## 识别信号

- 长串 validation if
- filter/interceptor chain
- 规则按顺序短路

## Agent 决策规则

- 当问题核心与“让请求沿一系列处理器传递，每个处理器决定处理、拒绝、修改或继续”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 定义清晰的继续/停止协议。
- 使每个 handler 单一职责。
- 对顺序、短路原因和执行轨迹做可观测性。

## 常见误用

- 不清楚谁吞掉了请求。
- handler 依赖前序的隐式副作用。
- 链顺序靠容器偶然决定。

## 常见组合

- Strategy
- Template Method
- Command

## 最小示意

```text
result = chain.handle(context) // CONTINUE / STOP / REJECT
```

## 深度分析

### 变化压力
Chain 适合顺序明确、可插拔且能短路的处理步骤，如校验、风控和中间件。若所有步骤必定执行且顺序是业务不变量，显式 Pipeline 更容易审计。

### 结构与协作
每个 Handler 接收共享上下文并返回 CONTINUE/STOP/REJECT 等显式结果；链的组装顺序在 composition root 固定，Handler 不依赖前序隐式副作用。错误、短路原因和已执行节点应进入 trace。

### 关键权衡与替代
链减少调用方分支，但控制流变得间接，顺序错误会改变结果。规则算法切换用 Strategy；固定骨架用 Template Method；一次操作对象化用 Command。

### 落地与验证
先列出每个处理器输入/输出和终止条件，再迁移一条验证链。测试空链、每种短路、顺序、异常、上下文隔离和超时；指标记录节点通过率、拒绝率和链版本。禁止 Handler 静默吞错。

## 退出条件

当链顺序永久固定、节点强耦合或追踪成本高于可插拔收益时，改为显式流程。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
