# 状态模式（State）

**类别：** GoF / 行为型

## 意图

把依赖状态的行为封装到状态对象中，避免大规模 status 分支，并显式约束状态转换。

## 什么时候使用

- 同一对象在不同状态下允许的操作明显不同。
- 状态转换规则复杂且持续增加。
- 大量 if(status)/switch(status) 散落各处。

## 什么时候不要使用

- 只有 2~3 个状态、行为简单且稳定。
- 状态只是数据标签，不影响行为。
- 真正需要的是跨服务工作流/持久状态机。

## 识别信号

- 订单状态分支
- 审批状态转换
- 不同状态不同方法行为

## Agent 决策规则

- 当问题核心与“把依赖状态的行为封装到状态对象中，避免大规模 status 分支，并显式约束状态转换”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 每个 State 封装允许操作和转换。
- 把非法转换变成显式错误。
- 复杂流程可升级为状态机/工作流引擎。

## 常见误用

- 每个状态复制大量相同逻辑。
- 状态对象直接访问过多外部服务。
- 把流程步骤与状态语义混淆。

## 常见组合

- Strategy
- Command
- Saga

## 最小示意

```text
order.state.pay(order); // state decides legality and next state
```

## 深度分析

### 变化压力
State 用对象封装依赖当前状态的行为和转换，适合状态分支已散落且每个状态允许的操作明显不同。状态只是展示标签时，普通枚举和表驱动更简单。

### 结构与协作
Context 持有当前 State；State 定义允许操作、前置条件和下一状态，非法转换返回明确领域错误。持久化存储稳定状态 ID/版本，状态对象本身不应持有跨请求外部资源。

### 关键权衡与替代
State 提升局部性和转换可测试性，但会增加对象数量和迁移/序列化工作。少量分支用显式 switch；算法切换用 Strategy；跨服务长流程用 Saga/工作流状态机。

### 落地与验证
先画状态转换表和不可达状态，再迁移两个高风险操作。测试每个状态的允许/拒绝、转换原子性、并发版本、恢复和未知旧状态；指标记录 transition、rejection 和 stuck duration。不要让状态对象偷偷发起副作用。

## 退出条件

当状态数量少且稳定，或流程已由工作流引擎承载时，回退枚举/引擎模型。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
