# 聚合根模式（Aggregate Root）

**类别：** DDD 模式

## 意图

作为聚合对外唯一入口，负责维护聚合内部不变量和生命周期。

## 什么时候使用

- 聚合内部有多个实体/值对象。
- 需要限制外部对内部对象的直接修改。
- Repository 以聚合根为加载/保存单位。

## 什么时候不要使用

- 对象本身没有聚合边界。
- 为了形式主义给每个实体都标 AggregateRoot。

## 识别信号

- 外部只拿 Order，不直接保存 OrderItem
- 根对象控制内部变更

## Agent 决策规则

- 当问题核心与“作为聚合对外唯一入口，负责维护聚合内部不变量和生命周期”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 公开表达业务意图的方法。
- 内部集合返回只读视图。
- 通过根发布 Domain Event。

## 常见误用

- 暴露 mutable children。
- Repository 为聚合内部每个实体单独保存。

## 常见组合

- Aggregate
- Repository
- Domain Event

## 最小示意

```text
order.addItem(product, qty) // not order.items.append(...)
```

## 深度分析

### 变化压力
当多个内部对象必须共同满足余额、数量或状态不变量，而调用方开始直接改 children 时，聚合根把“谁可以改变什么”重新收拢到一个入口。它不是给实体加一个 Root 后缀，而是明确一个事务写入所有权。

### 结构与协作
根对象持有内部实体和值对象，并只暴露表达意图的方法；Repository 只加载和保存根。外部引用子对象时传递只读投影或标识，跨聚合修改通过另一个用例/领域事件完成。根产生的事件在本地提交后由应用层发布。

### 关键权衡与替代
收益是边界清晰、并发冲突可控；代价是一次用例不能随意跨根更新，查询也不能把根当报表模型。若不存在跨对象不变量，普通 Entity + Repository 更简单；若主要问题是聚合大小，应先拆 Aggregate，而不是增加更多根方法。

### 落地与验证
先禁止外部集合写入，再把一个高风险变更迁移到根方法。测试根方法的合法/非法转换、并发版本冲突和事件内容；记录根 ID、版本、命令 ID。若根方法开始依赖 HTTP/数据库，说明应用服务边界错位，应把副作用移出。

## 退出条件

当内部对象不再共享强一致规则，或根只剩转发 getter/setter 时，去掉聚合根层，恢复直接组合。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
