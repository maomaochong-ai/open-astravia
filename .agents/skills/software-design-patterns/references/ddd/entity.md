# 实体模式（Entity）

**类别：** DDD 模式

## 意图

用稳定身份而非属性值定义连续生命周期中的领域对象。

## 什么时候使用

- 对象身份在属性变化后仍有意义。
- 需要跟踪生命周期和状态转换。
- 业务规则围绕某个唯一业务标识。

## 什么时候不要使用

- 对象仅由值决定，没有独立身份；应使用 Value Object。
- 只是数据库表行，不代表领域概念。

## 识别信号

- 订单、账户、工单
- id 相同即同一对象
- 生命周期状态变化

## Agent 决策规则

- 当问题核心与“用稳定身份而非属性值定义连续生命周期中的领域对象”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 定义业务身份和不变量。
- 实体方法表达领域行为而不是 setter 集合。
- 避免用数据库自增 ID 代替全部业务语义。

## 常见误用

- 贫血实体。
- 所有字段公开 set。
- equals/hash 语义与身份冲突。

## 常见组合

- Value Object
- Aggregate Root
- Repository

## 最小示意

```text
order.pay(payment) // behavior belongs to the entity/aggregate
```

## 深度分析

### 变化压力
Entity 用稳定身份表达“这是同一个持续存在的对象”，即使名称、状态或其他属性变化。判断依据是业务生命周期和身份语义，不是是否有一张数据库表。

### 结构与协作
实体封装能维护自身不变量的行为，身份通常由业务 ID/稳定 UUID 表达；创建、重建和比较要区分新对象、持久化对象和代理对象。实体可位于聚合内部，只有根对外暴露跨实体操作。

### 关键权衡与替代
实体允许状态演进，但会带来生命周期、并发和 equality 复杂度。若对象只由金额、区间或地址值决定，应使用 Value Object；若状态转换复杂，再考虑 State。不要用全量 setter 让调用方绕过规则。

### 落地与验证
先列出身份不变量、允许转换和并发版本，再把一条高价值行为从 setter 改为命令式方法。测试同 ID 的相等性、属性变化后的身份保持、非法转换和序列化重建；日志记录业务 ID 而非敏感字段。若实体只是数据容器，考虑回退为数据结构或 Active Record。

## 退出条件

当身份没有业务意义或对象不跨请求/事务存续时，改用 Value Object、DTO 或普通记录。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
