# 规约模式（Specification）

**类别：** DDD 模式

## 意图

把可组合的业务谓词/规则封装成对象，用于验证、筛选或查询表达。

## 什么时候使用

- 业务规则需要 AND/OR/NOT 组合。
- 同一规则要在内存验证与查询筛选中复用。
- 规则名称具有清晰领域语义。

## 什么时候不要使用

- 只有一个简单条件。
- 为了复用数据库查询而把基础设施表达式污染领域。
- 复杂决策更适合规则引擎。

## 识别信号

- isSatisfiedBy
- 组合 eligibility rules
- 复杂筛选条件

## Agent 决策规则

- 当问题核心与“把可组合的业务谓词/规则封装成对象，用于验证、筛选或查询表达”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 保持规约语义单一。
- 组合操作显式。
- 若需转 SQL，使用翻译层而不是把 ORM 细节放入规约。

## 常见误用

- 大量微小 Spec 类造成碎片化。
- Spec 既做校验又执行副作用。

## 常见组合

- Composite
- Repository
- Strategy

## 最小示意

```text
eligible = adult.and(active).and(notBlocked); eligible.isSatisfiedBy(user)
```

## 深度分析

### 变化压力
Specification 适合具有领域名称、需要组合并可能在验证与筛选之间复用的谓词。它把“是否满足”从散落条件提升为可解释、可测试的规则对象。

### 结构与协作
基础规约只描述一个纯条件，组合规约实现 AND/OR/NOT；内存求值与数据库表达式翻译分层，避免把 ORM 类型带入领域。规格可以作为策略输入或 Repository 查询条件，但不应执行副作用。

### 关键权衡与替代
组合性和可复用性有收益，代价是对象数量、解释和 SQL 翻译维护。一个简单 if 用函数即可；需要大量动态规则、版本和运营配置时，规则引擎可能更合适。不要为了查询复用而牺牲领域模型纯度。

### 落地与验证
先把一条重复且容易出错的资格判断提取为命名规格，明确短路和 null 语义，再添加组合。测试真值表、边界日期/时区、内存与查询翻译的一致性；记录命中的规则名称和版本。若规格开始读取数据库或发送消息，立即拆出端口/应用服务。

## 退出条件

当规则只有一个调用点或组合层级让阅读成本高于收益时，合并回普通函数/查询构造器。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
