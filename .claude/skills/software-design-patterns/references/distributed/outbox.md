# 事务发件箱模式（Transactional Outbox）

**类别：** 分布式系统模式

## 意图

在同一本地事务中写业务数据和待发布事件，再由独立发布器可靠发送，避免双写不一致。

## 什么时候使用

- 数据库更新与消息发布必须最终一致。
- 无法使用跨数据库+消息队列的 2PC。
- Domain Event 需要可靠跨进程传播。

## 什么时候不要使用

- 没有消息发布需求。
- 基础设施已提供等价的事务消息且语义满足。
- 把 Outbox 当去重机制；消费者幂等仍需单独处理。

## 识别信号

- DB commit 成功但 MQ send 失败
- 双写问题
- 可靠事件发布

## Agent 决策规则

- 当问题核心与“在同一本地事务中写业务数据和待发布事件，再由独立发布器可靠发送，避免双写不一致”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 业务表和 outbox 同事务写入。
- 发布器支持重试、状态/游标和监控。
- 消费者按事件 ID 幂等。

## 常见误用

- 发布后立刻删除导致难审计/难恢复。
- 没有清理策略。
- 误以为 exactly-once。

## 常见组合

- Domain Event
- Idempotency
- Saga

## 最小示意

```text
TX: update order + insert outbox_event; publisher later sends event
```

## 深度分析

### 变化压力
Transactional Outbox 解决本地数据库提交与消息发送之间的双写窗口，目标是“至少最终送达”，不是 exactly-once。没有跨进程事件需求时不应引入。

### 结构与协作
应用事务同时写业务数据和 outbox 记录；发布器按状态/锁/游标批量读取、发送并确认，失败可重试。事件带稳定 ID、schema 版本和关联 ID；消费者必须幂等，清理策略不能早于重放/审计窗口。

### 关键权衡与替代
Outbox 增加表、扫描延迟、清理和监控；若数据库或消息系统提供事务消息且语义已验证，可直接使用。CDC 可作为发布器，但仍需明确事件边界和消费者重复。不要在业务事务中同步等待 MQ。

### 落地与验证
先为一个领域事件建立同库 outbox，定义最大延迟、批量大小、锁竞争和死信处理。测试业务回滚不发事件、发布器崩溃重启、重复发送、排序和清理恢复；监控 outbox lag、oldest age、publish failure、dead-letter。事件 payload 最小化并脱敏。

## 退出条件

当平台事务消息已覆盖同一一致性合同，或事件传播被删除时，迁移并移除 outbox 表。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
