# CQRS 模式（Command Query Responsibility Segregation）

**类别：** 分布式系统模式

## 意图

把写模型与读模型分离，使它们可针对不同一致性、性能和复杂度需求独立设计。

## 什么时候使用

- 写侧有复杂领域规则，而读侧查询形态与写模型差异很大。
- 读写扩展需求显著不同。
- 需要多个专用读模型。

## 什么时候不要使用

- 普通 CRUD 应用。
- 团队无法承担双模型、同步和最终一致复杂度。
- 只是想把 query 方法和 command 方法分文件。

## 识别信号

- 复杂聚合 + 多维报表
- 读多写少且查询模型特殊
- command/query 分离

## Agent 决策规则

- 当问题核心与“把写模型与读模型分离，使它们可针对不同一致性、性能和复杂度需求独立设计”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- CQRS 可以只做逻辑分离，不必一开始就双库。
- 明确读模型延迟和一致性 SLA。
- 写侧返回必要结果，读侧专注查询。

## 常见误用

- 把 CQRS 等同 Event Sourcing。
- 为简单系统强行双库。
- 没有处理读模型重建和版本。

## 常见组合

- Event Sourcing
- DDD Repository
- Outbox

## 最小示意

```text
Command -> write model; Events/CDC -> read projections -> Query
```

## 深度分析

### 变化压力
CQRS 适用于写侧不变量复杂、读侧需要与写模型不同的查询形状；“把 command 和 query 分两个文件”不构成 CQRS。先量出读写扩展、查询延迟和一致性需求差异。

### 结构与协作
Command 进入写模型/聚合并产生事实；Query 读取专用投影。可以先在同一数据库做逻辑分离，再根据负载拆库。投影必须有版本、游标、重建和延迟 SLA；写接口要说明何时读模型可见。

### 关键权衡与替代
读写独立优化的收益伴随最终一致、双模型迁移和运维成本。普通 CRUD 用单模型；只是查询慢先优化索引/投影；需要完整事实历史才额外考虑 Event Sourcing，不要默认绑定。

### 落地与验证
先选一个高读复杂度场景建立只读投影，保留旧查询作差分校验。测试命令不变量、投影重复/乱序、重建一致性和读己写策略；指标关注 projection lag、重建耗时、查询 p95 和丢失事件。所有投影更新要可重放。

## 退出条件

当读写模型需求重新同构或最终一致性无法被业务接受时，合并模型，保留必要的索引/缓存。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
