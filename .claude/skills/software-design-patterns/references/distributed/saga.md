# Saga 模式（Saga）

**类别：** 分布式系统模式

## 意图

把跨服务长事务拆成一系列本地事务，并用补偿动作处理后续失败。

## 什么时候使用

- 一个业务流程跨多个独立服务/数据库。
- 不能使用单一 ACID 事务。
- 业务允许最终一致并可定义补偿。

## 什么时候不要使用

- 单库本地事务即可解决。
- 业务要求绝对同步强一致且无法补偿。
- 流程非常短且采用幂等重试即可。

## 识别信号

- 下单-库存-支付-物流跨服务
- 补偿事务
- 长事务

## Agent 决策规则

- 当问题核心与“把跨服务长事务拆成一系列本地事务，并用补偿动作处理后续失败”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 选择 choreography 或 orchestration。
- 每一步都定义幂等、超时、重试和补偿语义。
- 持久化 Saga 状态并可恢复。

## 常见误用

- 把补偿误解为数据库 rollback。
- 没有处理补偿失败。
- 没有关联 ID，难以追踪。

## 常见组合

- Outbox
- Idempotency
- Retry
- State

## 最小示意

```text
reserveInventory -> chargePayment -> createShipment; failure => compensations
```

## 深度分析

### 变化压力
Saga 把跨服务流程拆成多个本地事务，用补偿处理失败；它承认最终一致，不提供数据库 rollback。只有跨服务、无法共享 ACID 且业务能定义补偿时才使用。

### 结构与协作
每一步有明确 command、成功事件、超时、重试、幂等键和补偿；Orchestrator 适合流程可视化，Choreography 适合参与者少且事件边界清楚。Saga 状态持久化，支持恢复、人工介入和关联追踪。

### 关键权衡与替代
Saga 可扩展但增加状态机、补偿失败、乱序和运营处理。单库流程用 UoW/本地事务；短流程可用幂等重试。补偿可能不是原操作的逆函数，必须建模资金、库存和用户体验后果。

### 落地与验证
先画正常路径、每个失败点和补偿矩阵，选择一个低风险流程试点。测试重复/乱序消息、超时恢复、补偿失败、人工重试、版本升级和最终状态；指标关注 saga duration、step failure、compensation success、stuck instances。Outbox 保证命令/事件可靠送达。

## 退出条件

当流程可收回单库事务或补偿语义不可接受时，停止 Saga 化并重新划分服务边界。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
