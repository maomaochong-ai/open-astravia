# 断路器模式（Circuit Breaker）

**类别：** 分布式系统模式

## 意图

当远程依赖持续失败时快速失败，阻止雪崩，并在冷却后尝试恢复。

## 什么时候使用

- 调用远程服务且失败可能持续一段时间。
- 线程/连接池可能被失败请求耗尽。
- 系统可接受快速失败或降级。

## 什么时候不要使用

- 本地纯函数。
- 失败必须每次都尝试且无替代路径。
- 错误来自调用方参数，不应因 4xx 等业务错误触发断路。

## 识别信号

- 远程依赖不稳定
- 大量超时堆积
- 需要 fail-fast

## Agent 决策规则

- 当问题核心与“当远程依赖持续失败时快速失败，阻止雪崩，并在冷却后尝试恢复”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 定义 CLOSED/OPEN/HALF_OPEN。
- 基于合适错误类型、窗口和阈值。
- 与 timeout、retry、bulkhead 配合并控制顺序。

## 常见误用

- 对所有异常一视同仁。
- Retry 无限重试后再断路导致放大流量。
- 没有监控断路状态。

## 常见组合

- Retry
- Bulkhead
- Proxy

## 最小示意

```text
timeout -> limited retry -> circuit breaker -> fallback
```

## 深度分析

### 变化压力
Circuit Breaker 解决下游持续失败时“每个请求仍等待并重试”造成的资源耗尽。它不是通用错误处理，也不应把一次业务拒绝误判为依赖故障。

### 结构与协作
每个依赖或故障域维护 CLOSED、OPEN、HALF_OPEN 状态；按时间窗口、失败率/连续失败和最小样本数触发，OPEN 冷却后只放少量探测。超时、有限重试、熔断和 fallback 的顺序要固定并记录原因。

### 关键权衡与替代
熔断能保护调用方，但会牺牲短期成功率并引入阈值调参、半开竞争和降级数据一致性。若只是瞬态错误，Retry 足够；若主要问题是并发耗尽，Bulkhead 必须先做。对非关键读可降级，对支付写不可静默 fallback。

### 落地与验证
先在一个可降级读依赖上启用，定义错误分类和 fallback SLA。测试状态转换、半开并发、探测成功/失败、配置热更新和恢复；监控 breaker state、open duration、fallback rate、下游 latency。日志要带依赖名和触发原因，不记录敏感 payload。

## 退出条件

当依赖稳定、无资源耗尽风险且 fallback 语义不可接受时，移除熔断，仅保留超时和明确错误映射。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
