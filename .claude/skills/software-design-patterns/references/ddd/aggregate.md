# 聚合模式（Aggregate）

**类别：** DDD 模式

## 意图

把一组强一致对象定义为事务一致性边界，外部通过聚合根访问。

## 什么时候使用

- 对象之间存在必须在同一事务保持的不变量。
- 需要限制跨对象任意修改。
- 领域模型复杂，需控制一致性范围。

## 什么时候不要使用

- 只是为了把相关表都塞进一个大对象。
- 聚合过大导致长事务和并发冲突。
- 对象之间只需最终一致。

## 识别信号

- 强一致规则跨多个对象
- 事务边界
- 内部实体不能被外部随意修改

## Agent 决策规则

- 当问题核心与“把一组强一致对象定义为事务一致性边界，外部通过聚合根访问”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 围绕业务不变量划边界，不围绕数据库外键。
- 跨聚合只引用聚合根 ID。
- 聚合保持尽可能小。

## 常见误用

- 超级聚合。
- 跨聚合直接对象引用并修改。
- 把查询需求当聚合边界。

## 常见组合

- Aggregate Root
- Repository
- Domain Event

## 最小示意

```text
Order aggregate owns OrderItems and enforces total/quantity invariants
```

## 深度分析

### 变化压力
聚合解决的是“哪些对象必须在同一事务中保持不变量”，不是数据库表之间有外键。典型信号是同一业务动作同时改变订单行与订单总额，且部分提交会产生不可接受的中间状态。

### 结构与协作
先写出不变量，再选择最小边界和唯一 Aggregate Root。根内对象同步修改；跨聚合只保存根 ID，通过应用服务协调多个用例或用最终一致事件衔接。Repository、锁/版本检查和事务提交都以根为单位。

### 关键权衡与替代
聚合越大，单次读取和锁竞争越高；越小则需要更多事件和补偿。若规则只要求最终一致，拆成多个聚合通常更稳。若只是读侧组合，使用 Query Service/投影，不要为了查询方便扩大写聚合。

### 落地与验证
从一个会导致脏状态的用例开始，建立 invariant table：前置条件、变更、后置条件、失败恢复。测试根内原子性、乐观并发冲突、跨根事件重复与乱序；指标关注事务时长、冲突率和聚合加载大小。发现频繁跨根事务时，优先重画边界。

## 退出条件

当没有跨对象强一致不变量，或聚合大小导致性能和并发问题持续高于收益时，退回普通模块/事务脚本。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
