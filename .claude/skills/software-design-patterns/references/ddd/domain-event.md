# 领域事件模式（Domain Event）

**类别：** DDD 模式

## 意图

表示领域中已经发生、对业务有意义的事实，用于解耦后续反应。

## 什么时候使用

- 聚合状态变化需要通知其他组件/聚合。
- 希望显式记录重要业务事实。
- 后续处理可异步或最终一致。

## 什么时候不要使用

- 操作是命令/意图而非已经发生的事实。
- 同一事务内必须立即满足的聚合内部不变量，不应靠异步事件。
- 事件只用于技术日志，没有领域意义。

## 识别信号

- OrderPaid、CustomerRegistered
- 过去式事件名
- 跨聚合反应

## Agent 决策规则

- 当问题核心与“表示领域中已经发生、对业务有意义的事实，用于解耦后续反应”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 事件不可变，包含最小必要事实。
- 聚合产生事件，应用层负责发布。
- 跨进程发布配合 Outbox 和幂等。

## 常见误用

- 事件名使用 DoSomething。
- 事件 payload 包含整个聚合。
- 把关键强一致规则丢给异步消费者。

## 常见组合

- Observer
- Outbox
- Saga

## 最小示意

```text
order.pay(); events += OrderPaid(orderId, paidAt)
```

## 深度分析

### 变化压力
领域事件表达“事实已经发生”，适合一个聚合变化需要通知多个独立反应的场景。事件不是把命令换成过去式；它必须能在没有发布者上下文时独立解释。

### 结构与协作
聚合在状态变更时产生不可变事件，事件先挂在根或 UoW 上；应用层在本地事务成功后发布，跨进程则写入 Outbox。消费者只依赖事件契约，按 eventId/业务键幂等，并明确顺序、延迟和失败重试。

### 关键权衡与替代
事件解耦了时间和依赖，却引入最终一致、重复、乱序和 schema 演进。若反应必须和主变更同事务，直接调用或同一聚合方法更可靠；若只是技术日志，使用审计日志而非领域事件。Observer 适合进程内通知，Domain Event 还要求业务语义和版本。

### 落地与验证
先定义事件命名、版本、最小 payload、敏感字段和保留期，再接一个非关键消费者。测试事件只在提交成功后可见、重复/乱序安全、旧版本兼容和发布失败可恢复；指标关注 outbox lag、handler failure、重试次数。禁止把整个聚合序列化进事件。

## 退出条件

若只有一个同步消费者且没有解耦收益，回退为显式调用；若事件契约无法长期维护，先收敛为模块内事件。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
