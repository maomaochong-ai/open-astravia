# 值对象模式（Value Object）

**类别：** DDD 模式

## 意图

用属性值定义无身份的领域概念，并通过不可变性表达语义和约束。

## 什么时候使用

- 金额、地址、日期范围、坐标等由值决定。
- 多个原始类型组合具有领域含义。
- 希望把校验和运算封装在类型中。

## 什么时候不要使用

- 对象有独立身份和生命周期。
- 值经常局部修改且不可变复制成本极高。

## 识别信号

- primitive obsession
- Money/Currency
- EmailAddress
- DateRange

## Agent 决策规则

- 当问题核心与“用属性值定义无身份的领域概念，并通过不可变性表达语义和约束”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 尽量不可变。
- 构造时保证有效。
- 定义值相等和领域运算。

## 常见误用

- Value Object 仍暴露 setter。
- 只是无意义包装单字段且没有语义/约束。

## 常见组合

- Entity
- Builder

## 最小示意

```text
total = Money.of(100, "CNY").add(tax)
```

## 深度分析

### 变化压力
Value Object 解决原始类型丢失语义和约束的问题：金额、币种、地址或日期区间如果到处以 string/number 传递，校验、单位和相等性很容易不一致。它没有独立身份，值相同就代表同一概念。

### 结构与协作
值对象在构造时校验，内部不可变，运算返回新实例；Entity/Aggregate 持有它并通过行为方法替换。序列化只暴露稳定值，时区、精度、单位和舍入规则要写进类型契约。不要让值对象访问数据库或发送消息。

### 关键权衡与替代
类型化可消除 primitive obsession 并集中边界规则，代价是对象数量、映射和复制成本。单个无约束字段可继续使用原始类型；有身份和生命周期的概念用 Entity；规则需要组合筛选时用 Specification。不可变复制成本高时先测量，不要为形式包装。

### 落地与验证
先选一个跨模块传递且已有重复校验的值（如 Money），建立工厂/解析器和领域运算，再逐步替换参数。测试边界、单位/时区、舍入、值相等、序列化往返和非法输入；指标关注转换失败与精度异常。值对象不应携带可变集合引用。

## 退出条件

当类型没有额外语义/约束、只做一层 getter/setter，或边界已经由可靠 schema 完整保证时，回退原始类型或 DTO。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
