# 领域服务模式（Domain Service）

**类别：** DDD 模式

## 意图

承载不自然属于某个实体或值对象、但仍是核心领域规则的无状态业务能力。

## 什么时候使用

- 规则需要多个聚合/对象协作，放任一实体都显得牵强。
- 能力属于领域语言，而不是技术基础设施。
- 服务可以基本无状态。

## 什么时候不要使用

- 只是应用编排、事务、发消息，应放 Application Service。
- 规则明显属于某个实体，却为了“service 化”抽出去。

## 识别信号

- 跨对象领域计算
- 领域动词但没有自然 owner
- 无状态规则

## Agent 决策规则

- 当问题核心与“承载不自然属于某个实体或值对象、但仍是核心领域规则的无状态业务能力”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 输入输出使用领域对象/值对象。
- 不直接依赖 HTTP、数据库、消息队列。
- 名称使用领域术语。

## 常见误用

- 万能 DomainService。
- 把贫血模型所有逻辑都搬进服务。

## 常见组合

- Entity
- Application Service

## 最小示意

```text
exchangeService.convert(Money, Currency)
```

## 深度分析

### 变化压力
当一条核心规则同时依赖多个聚合或外部输入，放入任一实体都会制造错误归属，领域服务可以承载这条无状态规则。它必须使用领域语言，不能只是“把代码移到 Service”。

### 结构与协作
Domain Service 接收实体/值对象和已解析的领域端口，返回决策或新值，不负责事务、HTTP、持久化和消息发送。Application Service 负责加载对象和提交；若规则可独立替换，再把其中算法抽为 Strategy。

### 关键权衡与替代
好处是保持实体内聚并能直接测试；代价是调用方要理解服务语义，过多服务会形成贫血模型。若规则明显属于一个实体，应把行为放回实体；若只是跨系统编排，应使用 Application Service；若依赖远程价格等技术能力，应定义端口并在外层适配。

### 落地与验证
先记录规则的输入、输出和不变量，提取纯函数版本，再接入领域服务。测试边界值、多个聚合组合和端口失败，不测试数据库细节；为关键决策记录规则版本和输入摘要。若服务需要保存自身状态或调用多个外部系统，重新划分为应用编排。

## 退出条件

当服务只有一个调用点、规则已自然归属实体，或服务数量开始成为“万能工具箱”时，合并/拆分并删除该模式。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
