# 设计模式决策指南

本文件用于 Agent 在阅读具体模式前做第一轮路由。原则：**先识别变化与约束，再选模式；不要从模式名反推需求。**

## 1. 先判断问题属于哪一层

| 问题层级 | 典型问题 | 优先查看 |
|---|---|---|
| 对象创建 | 创建逻辑复杂、需要切换实现、参数很多 | Factory Method / Abstract Factory / Builder / Prototype / DDD Factory |
| 类与对象组合 | 第三方适配、功能包装、访问控制、树结构 | Adapter / Decorator / Proxy / Composite / Facade / Bridge |
| 行为变化 | 算法切换、固定流程、规则链、状态变化 | Strategy / Template Method / Chain / State / Command |
| 应用分层 | 事务、持久化隔离、接口契约 | Service Layer / Repository / Unit of Work / DTO / DI |
| 领域建模 | 身份、值、不变量、聚合、领域规则 | Entity / Value Object / Aggregate / Domain Service / Specification |
| 跨服务可靠性 | 双写、重试、故障隔离、跨服务事务 | Outbox / Idempotency / Retry / Circuit Breaker / Bulkhead / Saga |
| 读写架构 | 写规则复杂、读模型特殊、审计重放 | CQRS / Event Sourcing |

## 2. 高频代码信号 → 候选模式

| 信号 | 优先候选 | 先排除 |
|---|---|---|
| `if (type)` / `switch(type)` 持续增长 | Strategy + Factory Method | 分支少且稳定时保持简单分支 |
| `if (status)` 散落多个方法 | State | 状态只是标签时无需 State |
| 同一流程复制多份，仅少数步骤不同 | Template Method / Strategy | 变化点很多时避免继承 |
| 连续校验/过滤，可短路 | Chain of Responsibility | 所有步骤强依赖时显式流程更清楚 |
| 一个事件触发多个独立反应 | Observer / Domain Event | 强一致动作不要盲目异步化 |
| 第三方 SDK 侵入业务代码 | Adapter | 只是简单同构接口时别过度包装 |
| 事务/权限/缓存/远程替身 | Proxy | 可选功能叠加更像 Decorator |
| 多个正交维度导致子类爆炸 | Bridge | 只有单一变化维度时用普通组合 |
| 复杂构造参数 | Builder | 语言命名参数已经足够时不需要 |
| 跨服务 DB + MQ 双写 | Outbox | 消费端幂等仍需单独解决 |
| 网络瞬态失败 | Retry | 非幂等写、永久错误不要重试 |
| 下游持续故障导致资源耗尽 | Circuit Breaker + Bulkhead | 本地调用没必要 |
| 跨服务事务 | Saga | 单库事务优先本地 ACID |

## 3. 模式选择的停止条件

满足以下任一条件时，Agent 应优先推荐“保持简单”，而不是套模式：

1. 当前只有一个实现，且未来变化没有证据。
2. 分支数量少、稳定、可读，抽象会让跳转成本高于收益。
3. 新模式会引入更多状态、异步、网络或持久化复杂度，但没有对应可靠性需求。
4. 团队无法可靠测试、监控或运维该模式，例如 Event Sourcing、Saga、复杂事件流。
5. 语言或框架已经提供更简单的原生机制，例如命名参数、DI 容器、Kubernetes Service Discovery。
6. 问题根因是职责划分错误或数据模型错误，不应靠模式掩盖。

## 4. Agent 推荐格式

推荐模式时应按以下顺序输出：

1. **当前变化点 / 痛点**：指出具体代码或架构压力。
2. **推荐模式**：最多优先给 1 个主模式，必要时给 1~2 个辅助模式。
3. **为什么适用**：引用可观察信号，而不是说“这是最佳实践”。
4. **为什么不是其他模式**：至少排除一个最相近候选。
5. **最小改造方案**：先给最小可落地结构，不直接设计成框架。
6. **成本与风险**：对象数量、间接层、事务、一致性、可观测性等。
7. **演进条件**：说明何时才值得升级到更复杂模式。

## 5. 评分与证据门槛

候选模式进入实施方案前，先用下表做轻量评分。评分不是数学真理，而是迫使设计讨论显式化；任何一项没有证据，都应记为 0，而不是按“未来可能”加分。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 变化压力 | 没有重复或变化 | 已出现 2 个实现/分支 | 变化频繁且修改容易回归 |
| 边界收益 | 无边界问题 | 能隔离一个局部依赖 | 能保护跨模块/事务/安全不变量 |
| 测试收益 | 更难测 | 可替换一个外部边界 | 可建立稳定的合同/状态测试 |
| 运行时成本 | 需新增网络/持久化/全局状态 | 新增少量间接层 | 需要异步、租约、投影或运维体系 |

总分低于 3，或“运行时成本”达到 2 而没有对应可靠性/一致性收益时，默认保持简单。分数高也不能替代领域边界判断：先解决错误的职责归属，再考虑模式。

## 6. 从现状到模式的迁移顺序

优先采用可回退的切片：先补基线测试和指标，再提取稳定端口，随后迁移一个调用路径，最后删除旧分支。对于事件、Outbox、Saga、CQRS 等模式，必须先定义事件/命令版本、重复处理和失败恢复，再扩大覆盖面；不能让新旧两条事实源长期并存。
