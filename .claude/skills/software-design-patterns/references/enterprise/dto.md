# 数据传输对象模式（Data Transfer Object）

**类别：** 企业应用模式

## 意图

为跨进程、跨层或外部 API 传输定义稳定的数据契约，避免直接暴露内部模型。

## 什么时候使用

- API 契约与内部领域模型生命周期不同。
- 跨网络传输需要序列化。
- 需要版本控制、字段裁剪或安全边界。

## 什么时候不要使用

- 层之间完全同构且没有边界价值，机械复制 DTO 只增加映射。
- 把 DTO 当领域对象并承载业务规则。

## 识别信号

- Request/Response model
- RPC schema
- 领域实体不应直接暴露

## Agent 决策规则

- 当问题核心与“为跨进程、跨层或外部 API 传输定义稳定的数据契约，避免直接暴露内部模型”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- DTO 尽量无行为。
- 在边界做验证与转换。
- 外部契约变更采用兼容策略。

## 常见误用

- 每层一个完全相同 DTO。
- 敏感字段无意暴露。
- DTO 跨层无限传播。

## 常见组合

- Adapter
- Facade
- Application Service

## 最小示意

```text
CreateOrderRequest -> command -> domain; domain -> OrderResponse
```

## 深度分析

### 变化压力
DTO 在跨进程、公共 API 或版本边界上保护内部模型，核心是稳定契约、字段裁剪和安全控制。进程内同构调用不应为了形式复制 DTO。

### 结构与协作
入口校验并解析 Request DTO 为命令/值对象；应用层返回结果模型，再由 Presenter 映射为 Response DTO。DTO 不携带实体行为、ORM 引用或敏感字段，版本兼容由 schema/adapter 处理。

### 关键权衡与替代
DTO 增加映射和版本维护，但能避免内部重构破坏客户端。内部模块可直接共享类型或使用函数参数；若需要协议演进、跨语言或权限裁剪，DTO 是更稳边界。不要把每个层都复制一份完全相同的 DTO。

### 落地与验证
先为一个公开端点定义字段白名单、必填/默认/未知字段策略和错误格式，再接入 schema 校验。测试向后兼容、敏感字段不泄漏、未知字段处理和大 payload 限制；记录 API 版本、字段缺失率和校验失败原因。领域对象只在映射层出现。

## 退出条件

当边界消失且 DTO 只做同构转发时，合并映射；当契约需要独立演进时，保留 DTO 并版本化。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
