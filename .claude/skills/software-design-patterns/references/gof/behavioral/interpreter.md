# 解释器模式（Interpreter）

**类别：** GoF / 行为型

## 意图

为小型语言或规则表达式定义语法表示和解释执行方式。

## 什么时候使用

- 有简单、稳定、规模有限的 DSL/规则表达式。
- 语法可以自然映射为表达式树。
- 需要用户可配置规则但不值得引入完整编译器。

## 什么时候不要使用

- 语言复杂、语法持续增长，需要 parser generator/成熟 DSL 引擎。
- 安全边界严格，不能轻易执行用户表达式。
- 只是几个 if 条件。

## 识别信号

- 规则字符串
- 表达式 AST
- 业务 DSL

## Agent 决策规则

- 当问题核心与“为小型语言或规则表达式定义语法表示和解释执行方式”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 先定义 grammar，再构建 AST/表达式对象。
- 限制语言能力并做输入校验。
- 复杂度上升时及时迁移到成熟解析工具。

## 常见误用

- 手写 parser 无限膨胀。
- 允许任意代码执行。
- 把配置文件解析也机械套 Interpreter。

## 常见组合

- Composite
- Visitor

## 最小示意

```text
expr = parse("age > 18 AND active"); expr.evaluate(ctx)
```

## 深度分析

### 变化压力
Interpreter 适合小而稳定的 DSL，语法树能直接表达业务规则并由受控解释器执行。先确认表达式范围、用户权限和错误反馈，绝不能把用户输入当任意代码执行。

### 结构与协作
Lexer/parser 将输入转为受校验 AST；各表达式节点只实现 evaluate/compile 的纯语义，变量通过白名单上下文提供。语法、AST、执行和外部副作用分层，复杂语言应交给成熟解析器。

### 关键权衡与替代
自定义 DSL 可配置但会引入 grammar、版本、性能和安全成本。几个条件用普通函数/Specification；复杂规则用规则引擎或 parser generator；查询表达式需专用编译/翻译层。

### 落地与验证
先定义 grammar、资源限制和错误位置，再实现一个只读谓词。测试优先级、短路、类型错误、恶意输入、深度/时间限制和版本兼容；监控解析失败、执行耗时和规则版本。禁止 eval、任意网络/文件访问。

## 退出条件

当语法持续膨胀、性能/安全要求超出自研能力或规则不再稳定时，迁移成熟 DSL/规则引擎。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
