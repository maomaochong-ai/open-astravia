# 策略模式（Strategy）

**类别：** GoF / 行为型

## 意图

把一组可替换算法/业务规则封装为统一接口，让调用方按上下文选择。

## 什么时候使用

- 同一业务目标有多种实现。
- 经常出现 if(type)/switch(type) 选择算法。
- 算法需要独立测试、替换或按配置注入。

## 什么时候不要使用

- 只有一个实现且没有可预见变化。
- 差异只是一两个常量，参数化比新策略类更简单。
- 算法步骤大体固定、只部分变化，Template Method 可能更合适。

## 识别信号

- 支付渠道
- 价格/折扣算法
- 排序/路由策略
- if(type) 分支

## Agent 决策规则

- 当问题核心与“把一组可替换算法/业务规则封装为统一接口，让调用方按上下文选择”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 定义最小策略接口。
- 用工厂/注册表选择策略，避免调用方 switch。
- 策略尽量无状态，必要状态显式作为参数。

## 常见误用

- 每个微小分支都建一个策略类。
- 策略读取全局上下文形成隐式依赖。
- 策略选择逻辑散落多处。

## 常见组合

- Factory Method
- Template Method
- State

## 最小示意

```text
pricing = strategies[customer.segment]; total = pricing.calculate(cart)
```

## 深度分析

### 变化压力
Strategy 处理同一目标存在多个可替换算法/规则，且选择逻辑会变化。至少应有两个真实实现或一个已证实的替换边界；只有常量差异时参数化更直接。

### 结构与协作
Context 依赖最小 Strategy 接口，Factory/注册表负责选择，策略接收显式输入并返回结果/决策，不读取全局状态。算法所需的外部能力通过端口注入，选择 key、版本和默认策略应可追踪。

### 关键权衡与替代
策略隔离变化、方便独测，但增加接口和选择错误。固定流程少数步骤变化用 Template Method；状态驱动行为用 State；类型选择创建对象用 Factory Method。不要让调用方再次 switch。

### 落地与验证
先列出实现差异矩阵，迁移一个算法并保留旧路径作差分。测试边界输入、策略选择、默认/未知 key、异常和版本兼容；指标记录 strategy key、版本、耗时和结果分布。若策略接口需要十余参数，先重画上下文。

## 退出条件

当只剩一个实现、差异可由配置表达或选择逻辑稳定时，合并为普通函数/参数。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
