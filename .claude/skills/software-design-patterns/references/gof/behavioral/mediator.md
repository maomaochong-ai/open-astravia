# 中介者模式（Mediator）

**类别：** GoF / 行为型

## 意图

集中协调多个对象间的交互，减少对象彼此网状依赖。

## 什么时候使用

- 多个组件互相调用形成高耦合网。
- 交互规则集中管理比散落在组件中更清晰。
- UI 控件、工作流节点或模块协作需要协调者。

## 什么时候不要使用

- 中介者会变成巨大业务中心。
- 对象间关系简单直接。
- 更合适的是发布订阅，组件无需知道交互结果。

## 识别信号

- A 调 B/C，B 又调 C/D
- UI 控件联动
- 协作关系网状

## Agent 决策规则

- 当问题核心与“集中协调多个对象间的交互，减少对象彼此网状依赖”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- Mediator 管协调，不承担各组件内部业务。
- 组件只与 Mediator 或事件契约交互。
- 规模大时按用例拆分多个 mediator。

## 常见误用

- God Mediator。
- 把所有领域逻辑集中进协调器。
- 中介者又反向暴露内部组件。

## 常见组合

- Observer
- Facade

## 最小示意

```text
dialogMediator.onCountryChanged(country)
```

## 深度分析

### 变化压力
Mediator 适合多个组件形成网状调用，而协调规则集中后更易理解和测试。先确认交互确实需要协调者；如果参与者只需广播事实，Observer 更合适。

### 结构与协作
组件只暴露最小端口给 Mediator，Mediator 按用例协调顺序、校验和结果；组件内部业务仍归自己。大型系统按场景拆分 mediator，并把状态和副作用显式传入，避免隐藏全局上下文。

### 关键权衡与替代
中介减少互相依赖，却容易变成 God Mediator 和新单点。简单两方调用直接连接；跨组件通知用事件；跨服务编排用 Application Service/Saga。不要把领域不变量全部搬进 mediator。

### 落地与验证
先画交互图识别环依赖，再迁移一个流程。测试参与者超时、部分失败、重入、顺序和取消；trace 记录用例和参与者节点。若 mediator 方法不断增加，按边界拆分或下沉行为。

## 退出条件

当参与者关系已简单、协调规则稳定或 mediator 成为领域中心时，删除/拆分它。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
