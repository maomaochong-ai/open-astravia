# 命令模式（Command）

**类别：** GoF / 行为型

## 意图

把一个操作封装成对象，使其可排队、记录、重试、撤销或延迟执行。

## 什么时候使用

- 操作需要进入队列、任务调度或消息总线。
- 需要 undo/redo、审计日志或重放。
- 调用者与执行者需要解耦。

## 什么时候不要使用

- 简单同步方法调用且无需操作对象化。
- 命令对象只是薄包装，没有生命周期或额外能力。
- 需要的是业务事件通知而非意图执行；考虑 Domain Event/Observer。

## 识别信号

- 任务队列
- undo/redo
- 操作审计
- 请求对象携带 execute

## Agent 决策规则

- 当问题核心与“把一个操作封装成对象，使其可排队、记录、重试、撤销或延迟执行”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 命令表达“意图”，执行器负责实际处理。
- 需要幂等时把命令 ID/业务键纳入协议。
- 若支持撤销，明确逆操作和不可逆边界。

## 常见误用

- Command 与 Event 混为一谈。
- 命令对象携带整个对象图。
- 重试非幂等命令造成重复副作用。

## 常见组合

- Memento
- CQRS
- Idempotency

## 最小示意

```text
queue.enqueue(CreateInvoiceCommand(orderId))
```

## 深度分析

### 变化压力
Command 把“意图”变成可持久化、排队、重试或撤销的对象。它与 Event 的区别是：Command 请求执行，Event 描述已发生事实；两者的失败和所有权不同。

### 结构与协作
命令包含稳定 ID、版本、业务键和最小参数；Invoker/队列负责调度，Handler 负责授权、幂等和执行，领域对象维护规则。序列化命令必须能在未来版本解析，敏感参数不应直接落日志。

### 关键权衡与替代
对象化带来延迟、存储和重放复杂度。简单同步调用直接使用函数；跨用例通知用 Domain Event；撤销不可逆外部副作用时应建补偿而非假装 undo。

### 落地与验证
先为一个异步或可审计操作定义 schema 和状态（accepted/running/succeeded/failed）。测试重复投递、版本不兼容、取消、重试和权限；监控队列延迟、处理时长、失败类别和 dead-letter。命令处理结果要可查询。

## 退出条件

当命令永远同步、无排队/审计/撤销需求且对象只是薄包装时，回退直接调用。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
