# 桥接模式（Bridge）

**类别：** GoF / 结构型

## 意图

把抽象维度与实现维度分离，使两者可独立扩展，避免子类组合爆炸。

## 什么时候使用

- 存在两个或更多独立变化维度，例如“通知类型 × 发送渠道”。
- 继承层次因为组合维度不断膨胀。
- 运行时需要替换实现。

## 什么时候不要使用

- 只有一个变化维度。
- 组合关系很少且稳定，普通组合即可。
- 抽象和实现并非正交，强行拆分反而增加理解成本。

## 识别信号

- EmailUrgentNotification、SmsUrgentNotification 等类组合爆炸
- 两个维度分别变化
- 需要抽象与平台解耦

## Agent 决策规则

- 当问题核心与“把抽象维度与实现维度分离，使两者可独立扩展，避免子类组合爆炸”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 用组合持有 Implementor，而不是为每种组合建子类。
- 确保两个维度的职责边界清晰。
- 必要时配合 Factory 创建桥接两端。

## 常见误用

- 把任何组合都称为 Bridge。
- 拆分出空洞接口但没有独立变化需求。
- 桥接两端相互反向依赖。

## 常见组合

- Abstract Factory
- Strategy

## 最小示意

```text
Notification(kind).sender = ChannelSender(provider)
```

## 深度分析

### 变化压力
Bridge 用于两个正交维度都在变化，继承组合已出现类爆炸。先证明“抽象维度”和“实现维度”可独立发布/测试；如果两者总是一起变化，普通组合更简单。

### 结构与协作
Abstraction 持有 Implementor 端口，客户端只依赖抽象；两端通过最小接口通信，Factory/DI 在 composition root 组装。抽象负责业务语义和生命周期，实现负责平台/渠道差异，避免相互反向依赖。

### 关键权衡与替代
Bridge 把 O(n×m) 子类组合降为 O(n+m)，代价是接口跳转和跨维度错误处理。单一维度用 Strategy 或普通组合；产品族成套切换用 Abstract Factory；只有一个实现时不要提前拆桥。

### 落地与验证
列出两个维度的独立变化样本，先迁移一组组合并删除对应子类。测试每个抽象与实现的组合、实现替换、生命周期和错误映射；指标按两个维度拆分延迟与失败率。若任何一端开始了解另一端具体类型，桥已失效。

## 退出条件

当一端不再变化或组合矩阵稳定很小，合并为直接组合/策略。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
