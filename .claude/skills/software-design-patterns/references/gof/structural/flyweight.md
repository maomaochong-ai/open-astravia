# 享元模式（Flyweight）

**类别：** GoF / 结构型

## 意图

共享大量对象中的重复、不可变内在状态，以降低内存或创建成本。

## 什么时候使用

- 存在海量细粒度对象且重复状态占用显著。
- 可把状态拆成共享的 intrinsic 与外部 extrinsic 部分。
- 性能分析已经证明对象数量/内存是瓶颈。

## 什么时候不要使用

- 没有实际内存压力。
- 共享状态可变，容易引发并发和污染。
- 为了理论优化牺牲代码清晰度。

## 识别信号

- 百万级相似对象
- 大量重复字符串/样式/元数据
- 对象缓存池

## Agent 决策规则

- 当问题核心与“共享大量对象中的重复、不可变内在状态，以降低内存或创建成本”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 共享部分必须不可变或线程安全。
- 外部状态由调用方传入。
- 先 profile，再决定是否引入。

## 常见误用

- 过早优化。
- 把连接池等资源池简单等同于 Flyweight。
- 共享可变对象导致幽灵状态。

## 常见组合

- Factory Method
- Prototype

## 最小示意

```text
glyph = glyphFactory.get(charCode); glyph.draw(position)
```

## 深度分析

### 变化压力
Flyweight 只在大量对象共享不可变内在状态、且 profile 证明内存/创建成本显著时有价值。先区分 intrinsic（可共享）与 extrinsic（每次调用不同）状态。

### 结构与协作
Factory/Pool 按稳定 key 返回共享对象；共享对象必须不可变或线程安全，调用方传入位置、租户等外部状态。缓存有容量、淘汰和生命周期策略，不能把外部资源句柄混进共享状态。

### 关键权衡与替代
共享减少内存但增加缓存命中、并发和失效复杂度。普通对象数量不大时直接创建；连接池是资源复用而非 Flyweight；Prototype 解决复制模板而非共享状态。

### 落地与验证
先提供基线 profile，再实现一个共享热点。测试相同 key 复用、外部状态隔离、并发读、淘汰和缓存满；监控内存、命中率、对象数和 GC。若共享对象出现可变字段，立即拆分 ownership。

## 退出条件

当 profile 不再显示收益、缓存维护成本上升或状态无法保持不可变时，删除 Flyweight。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
