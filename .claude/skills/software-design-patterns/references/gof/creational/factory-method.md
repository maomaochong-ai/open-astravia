# 工厂方法模式（Factory Method）

**类别：** GoF / 创建型

## 意图

把“创建哪个具体对象”的决定延迟到子类、实现类或注册表，让调用方只依赖抽象。

## 什么时候使用

- 创建逻辑随类型、协议、渠道或环境变化。
- 新增实现时希望减少修改调用方。
- 对象创建需要校验、装配依赖或选择实现。

## 什么时候不要使用

- 只有一个简单实现且创建过程稳定。
- 为了消除一个非常小且不会扩展的 new 而引入多层抽象。
- 真正的问题是复杂参数构造，此时 Builder 更直接。

## 识别信号

- if/else 或 switch(type) 负责 new
- 调用方知道过多具体类
- 插件/渠道不断增加

## Agent 决策规则

- 当问题核心与“把“创建哪个具体对象”的决定延迟到子类、实现类或注册表，让调用方只依赖抽象”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- 工厂返回接口或抽象类型。
- 优先使用注册表 Map<Key, Creator> 代替不断增长的 switch。
- 让工厂负责“选择与创建”，不要把业务处理也塞进工厂。

## 常见误用

- God Factory：工厂知道所有业务细节。
- 工厂与具体类型枚举强耦合且仍需频繁修改。
- 把简单构造过度包装。

## 常见组合

- Strategy
- Abstract Factory
- Dependency Injection

## 最小示意

```text
handler = handlerFactory.create(request.type); handler.handle(request)
```

## 深度分析

### 变化压力
Factory Method 将具体创建决策隔离，适合按协议、渠道、插件或运行环境不断增加实现的系统。关键证据是调用方的类型分支持续增长或具体类泄漏。

### 结构与协作
调用方依赖抽象 Creator/产品接口；工厂负责选择、校验和装配，业务处理交给产品。可用注册表 Map<Key, Creator> 解耦新增实现，但注册表本身要有生命周期、重复键和未知键策略。

### 关键权衡与替代
工厂减少调用方改动，却增加间接层和错误映射。单一稳定实现直接构造；复杂参数用 Builder；产品族整体切换用 Abstract Factory；算法切换而非对象创建用 Strategy。不要让 God Factory 包含领域规则。

### 落地与验证
先锁定创建契约和未知类型错误，再把一个 switch 分支迁移到注册表。测试每种 key、依赖装配失败、重复注册、默认实现和插件卸载；指标记录选择 key、创建耗时和失败类别。新增实现应只改注册装配，不改业务调用方。

## 退出条件

当实现数量稳定、选择逻辑只有一条或工厂修改频率超过调用方收益时，回退直接构造/显式分支。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
