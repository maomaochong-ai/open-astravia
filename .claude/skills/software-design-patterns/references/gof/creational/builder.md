# 建造者模式（Builder）

**类别：** GoF / 创建型

## 意图

分步骤构造复杂对象，并让可选参数、约束和最终校验更清晰。

## 什么时候使用

- 构造参数很多且多数可选。
- 对象创建需要多个阶段或跨字段校验。
- 希望构造完成后对象不可变。

## 什么时候不要使用

- 只有 2~3 个清晰参数。
- 对象本身是简单 DTO，语言已有命名参数/record/data class 足够。
- 核心问题是选择不同实现而不是组装参数，此时用 Factory。

## 识别信号

- 超长构造函数
- 多个同类型参数容易传错
- 大量 setter 后才能成为有效对象

## Agent 决策规则

- 当问题核心与“分步骤构造复杂对象，并让可选参数、约束和最终校验更清晰”一致，且至少命中两个“识别信号”时，优先把本模式列为候选。
- 如果命中任一关键“不适用”条件，必须在推荐前解释为什么仍值得使用；否则不要推荐。
- 优先选择能解决当前变化点的最小模式；不要因为未来可能扩展而提前引入抽象。
- 输出设计建议时必须同时说明：变化点、模式承担的职责、未使用该模式时的替代方案、引入后的成本。

## 实现要点

- Builder 负责暂存构造状态，build() 做完整性校验。
- 对必填字段提供明确约束。
- 最终对象优先设计为不可变。

## 常见误用

- Builder 自己演变成业务服务。
- 允许 build 出非法半成品。
- 每个两字段对象都机械生成 Builder。

## 常见组合

- Factory Method
- Value Object

## 最小示意

```text
query = Query.builder().filter(f).sort(s).limit(100).build()
```

## 深度分析

### 变化压力
Builder 适用于对象创建步骤多、可选参数多或跨字段校验复杂的场景；它的目标是让“构造完成即有效”，不是替代所有命名参数。

### 结构与协作
Builder 持有未完成状态，必填字段可用分阶段 API/类型约束表达，build() 执行最终校验并返回不可变对象。Builder 不应调用远程服务或承担业务流程；领域创建规则应委托 DDD Factory。

### 关键权衡与替代
Builder 提升可读性和防错性，但会增加可变中间状态、方法数量和调试跳转。2~3 个参数使用构造器；配置对象可用 record/对象字面量；需要选择实现用 Factory。Builder 也不能取代 schema 验证。

### 落地与验证
先为一个超长构造函数建立必填/可选字段表，保留旧构造器适配到 builder。测试缺字段、跨字段冲突、默认值、不可变性和序列化；不要只测链式调用。若 Builder 需要大量上下文和副作用，拆回应用服务。

## 退出条件

当参数数量下降、语言命名参数已足够或 builder 只包一行 new 时，删除 Builder。

## 选择检查清单

在采用本模式前，Agent 应确认：

- [ ] 当前问题是真实存在的维护性、扩展性、一致性或可靠性问题，而不是纯粹追求形式。
- [ ] 模式引入的接口、对象、状态或基础设施数量与问题规模匹配。
- [ ] 团队能够测试和观测新增的间接层。
- [ ] 存在更简单方案时，已明确为什么更简单方案不足。
