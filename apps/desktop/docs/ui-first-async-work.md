# Desktop 异步交互的 UI 优先规范

本文规定 Desktop 中“用户操作会触发异步准备工作”的通用时序。目标是让用户先看到操作已经生效，再让 Runtime、进程、索引、网络和大规模数据恢复等次要准备工作占用资源。

它适用于 Renderer 发起、但可能跨越 Main、IPC、文件系统或外部服务的交互。视觉与组件规则仍分别遵循 [`../DESIGN.md`](../DESIGN.md) 和 [`composable-ui-components.md`](./composable-ui-components.md)。

## 1. 两个完成里程碑

设计异步流程时，必须区分：

1. **可见完成**：路由、选择态、标题、页面壳、输入草稿或占位内容已经提交，用户能确认点击生效。
2. **功能就绪**：Runtime、工作进程、Provider、插件、索引或完整历史已经可用。

除非前置结果决定页面是否合法、安全或可恢复，否则功能就绪不得阻塞可见完成。不要把“后端对象已完全构造”当作“可以导航”的默认前提。

## 2. 标准时序

推荐的交互关键路径是：

```text
用户操作
  → 同步记录意图
  → 更新路由或本地可见状态
  → 提交页面壳、选择态和可编辑草稿
  → 浏览器完成一次可见绘制
  → 启动昂贵的次要准备
  → 增量补齐数据与能力
  → 将临时标识规范化为持久标识
```

实现中可复用 `src/renderer/shared/lib/committed-paint.ts` 的 `waitForCommittedPaint()`，让已提交的 UI 获得绘制机会。它不是任意延时，也不保证后台工作变快；它只建立“先呈现、后争用资源”的顺序。

## 3. 必须遵守的边界

- 触发器只负责表达用户意图和进入目标界面，不在导航前等待昂贵的 IPC。
- 页面或领域 Connector 拥有加载、取消、错误恢复和持久标识规范化；纯 View 不调用 IPC。
- 首屏只读取构成页面身份和基本操作所需的数据。历史全文、插件发现、工具装配、索引、媒体解析和 Runtime 恢复按需或在绘制后加载。
- 可在本地确定的标题、选择态、空列表和草稿先乐观呈现。临时状态必须有稳定作用域，成功后迁移到持久 ID，失败后保留可恢复输入。
- 同一资源的后台初始化必须可去重或具备幂等性。React effect 重跑、重复点击和路由规范化不能创建重复资源。
- 后台工作不得在 Renderer 主线程执行重 CPU 或同步 I/O；需要计算或文件扫描时使用既有 Main、worker 或 utility process 边界。
- 只有授权、参数校验、不可逆确认或缺少关键身份会使目标页面无效时，才允许把对应检查放在导航前。

## 4. 状态与错误

UI 优先不等于隐藏加载状态。界面应分别表达：

- 操作已接受，但能力仍在准备；
- 可输入但暂不可提交；
- 部分数据已经可用；
- 准备失败，哪些输入或配置已保留；
- 用户可重试、返回或切换到其他内容。

避免用全屏空白或禁用整个导航区表示局部准备。若用户可以安全地继续浏览、编辑草稿或切换页面，应保留这些能力。

## 5. 通用示例

### 创建工作区页面

正确：先进入带名称和空内容区的工作区页面，绘制后再创建语言服务、扫描仓库和恢复扩展。

错误：`await startLanguageServer()`、`await scanRepository()` 全部完成后才调用 `navigate()`。

### 打开大型文档

正确：先显示文件名、工具栏和可滚动占位区域，再由 worker 解析正文，随后按页填充内容和索引。

错误：Renderer 同步解析完整文件后才挂载页面。

### 切换需要远端数据的详情

正确：立即更新路由和列表选中态，保留上一帧或显示目标详情壳；基础信息、历史和诊断信息分级加载。

错误：在列表点击处理器中等待所有请求成功，期间没有位置变化或状态反馈。

## 6. 测试与度量

涉及此类时序的改动必须覆盖用户可观察顺序，而不只断言最终成功：

- 操作发生后，路由或乐观状态在昂贵调用开始前已经更新；
- 绘制屏障未释放时，Runtime/进程/扫描等初始化尚未启动；
- 成功后临时状态被持久状态替换，且不会重复加载或创建；
- 失败时页面仍可恢复，用户输入不丢失；
- 卸载、切换目标或重复 effect 不会向错误页面提交过期结果。

性能记录至少区分 `intent → visible` 与 `intent → ready`。优化首帧时不能只报告总耗时；优化后台准备时也不能用更早显示空壳掩盖功能就绪退化。

## 7. 评审清单

- [ ] 是否有昂贵工作仍位于 `navigate()` 或可见状态提交之前？
- [ ] 首屏是否加载了用户尚未需要的数据、插件、工具或 Runtime？
- [ ] 是否在可见状态提交后给浏览器留下了绘制机会？
- [ ] Connector、View、IPC 和 Runtime 的职责是否清晰？
- [ ] 临时状态能否成功规范化、失败恢复并避免重复初始化？
- [ ] 测试是否证明了“UI 先于后台工作”，而非只证明最终结果？
