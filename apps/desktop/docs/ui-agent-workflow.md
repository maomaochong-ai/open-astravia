# Desktop UI Agent 工作流规则

> 本文件是面向 Coding Agent 的**流程规则**，解决“功能实现与 UI 设计同时推进时，视觉质量被功能优先级挤压”的问题。
> 本文件补充而不替代：
>
> - [Desktop 设计规范](../DESIGN.md)：颜色、Token、组件、动效和桌面端约束
> - [用户语言与 UI 设计](./user-language-ui.md)：用户目标、心智模型、信息架构和文案
> - [UI Review](./ui-review.md)：审查顺序、问题分级和视觉/交互检查清单

## 1. 核心决策

### 1.1 UI 不是功能实现的副产品

“能运行”与“容易理解、值得信任、效率高”是两种不同的完成条件。Agent 不得把组件拼装、默认布局或截图看起来完整，视为 UI 设计完成。

### 1.2 设计决策必须先形成可读的合同

自然语言 Feature Spec 只说明要解决什么问题，不能单独决定页面的层级、视觉方向、状态和交互。每个重要 UI 变更都必须先形成最小的 UI 合同（见第 3 节），再进入生产代码。

### 1.3 设计领先一个小切片，而不是领先整个项目

不要采用“所有功能完成后再统一美化”的大瀑布，也不要让 Agent 在同一轮里边猜视觉边写业务。采用小批量的纵向切片：设计先确定一个可交付切片，工程随后实现该切片的完整路径和状态。

### 1.4 不把“多 Agent”当成质量方案

默认使用单 Agent 的分阶段流程：规划 → 实现 → 审查 → 修复。只有任务确实需要独立研究、并行且不修改同一文件时，才考虑多 Agent；无论是否并行，设计合同和最终审查都必须是单一事实源。

## 2. 为什么需要这套流程

现有 UI 生成实践反复显示，单次提示词容易遗漏层级、状态和风格，且后续修改会意外影响无关区域。SpecifyUI 将页面拆成全局、区域、组件三级结构，并用参数化中间表示承载设计意图；研究中它相较纯提示词生成提升了意图对齐和局部修改可控性，同时把更多时间放在前期规格上、减少了后续返工。[SpecifyUI 研究（2025）](https://arxiv.org/abs/2509.07334)

Anthropic 的官方 `frontend-design` Skill 也要求在编码前明确产品目的、受众、视觉方向、约束和差异化选择，原因是没有明确方向时模型会收敛到模板化的平均答案。[Anthropic frontend-design Skill](https://github.com/anthropics/claude-code/blob/main/plugins/frontend-design/skills/frontend-design/SKILL.md)

对 AI 产品本身，还必须设计“系统如何表现、出错和恢复”，而不只是设计输入框。Microsoft HAX Toolkit 提供了 18 条经研究验证的人机交互指南，并建议在早期规划阶段选择适用准则、模式和失败场景；Google PAIR 也把用户需求、心智模型、控制、信任与优雅失败列为 AI 产品开发的独立章节。[Microsoft HAX Toolkit](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/)、[Google People + AI Guidebook](https://pair.withgoogle.com/guidebook-v2/)

## 3. UI 任务的最小输入和产物

当任务会改变用户可见的页面、文案、交互、状态、布局、主题或可访问性时，Agent 必须在实现前写出以下内容。小修复可合并在任务说明或 PR 描述中；重要页面应保存为 `docs/ui/` 下的文件或任务附件。

### 3.1 UX Brief（用户目标）

至少回答：

```text
主要用户：谁在什么情境下使用？
页面唯一任务：用户来到这里最重要的目标是什么？
关键决策：用户需要理解、比较或选择什么？
主要行动：完成目标的首要操作是什么？
成功反馈：用户如何知道已经完成？
不在范围内：本切片明确不解决什么？
```

规则：

- 不得把数据库实体列表直接当成页面结构或侧边栏结构。
- 如果用户、目标或术语未知，要标记为假设，并从现有产品语言和任务上下文推断；不得把推断写成事实。
- 页面应先表达用户的目标和下一步，再表达系统内部对象。

### 3.2 状态矩阵（可观察状态）

至少覆盖适用的：首次进入、正常、空、加载、成功、部分完成、错误、重试、权限不足、离线/不可用、未保存、长内容、窄窗口和键盘焦点。每个状态写清：用户看到什么、可以做什么、系统做了什么、如何恢复。

AI 功能还要补充：能力边界、处理中反馈、结果不确定时的解释、用户纠正/撤销路径、上下文不足或工具失败时的下一步。不要用“AI 正在思考”代替真实状态，也不要伪造精确进度。

### 3.3 Visual Spec（视觉决策）

在生产 UI 中至少记录：

- 信息层级和首屏注意力顺序；
- 产品气质、参考对象和明确避免的方向；
- 颜色、字体、间距、圆角、阴影、动效及其语义；
- 响应式降级策略；
- 一个可解释的差异化选择，以及它服务的用户目标。

颜色、间距、圆角和动效必须引用现有 `DESIGN.md` 与代码 Token，不得在任务中另起一套数值。Material Design 3 将颜色、字体、形状等决策建模为语义 Token，强调 Token 能改善设计与开发交接、主题一致性和可访问性；本项目应遵循同样的“语义名优先”原则。[Material 3 theming](https://developer.android.com/codelabs/m3-design-theming)

## 4. 分阶段执行协议

### Phase 0：路由任务类型

Agent 先把任务归类为以下一种，必要时拆成多个连续任务：

| 类型 | 先做什么 | 完成证据 |
|---|---|---|
| 纯功能 | 保持现有 UI，不顺手改风格 | 功能测试与回归检查 |
| 新页面/新流程 | UX Brief + 状态矩阵 + Visual Spec | 设计决策已确认 |
| 既有页面视觉修复 | 先按 `ui-review.md` 定位根因 | 截图前后对比 |
| 组件/Token 变化 | 影响面盘点和组件状态清单 | 组件合同/回归测试 |
| AI 交互变化 | HAX 风险与失败状态分析 | 可解释、可控、可恢复 |

### Phase 1：理解和方案

1. 阅读本文件、`DESIGN.md`、`user-language-ui.md`、`ui-review.md` 以及目标领域的 README/测试。
2. 盘点可复用组件、现有 Token、路由、i18n、状态和已存在的类似页面。
3. 输出 UX Brief、状态矩阵和一个 Visual Spec。
4. 如果存在两种会显著改变用户行为或视觉语言的解释，先请求确认；否则采用最小、可回退的方案。

**禁止**在本阶段写生产 JSX/CSS 来“试试看”。可以写低保真的结构草案或组件接口，但不能把未确认的视觉猜测扩散到多个页面。

### Phase 2：骨架优先

先实现路由、页面外层、信息层级、共享组件和主要状态的结构；暂不花时间做装饰性细节。骨架必须能让审查者回答：用户在哪里、要完成什么、下一步是什么、结果如何反馈。

多页面任务先让所有页面有可导航的骨架，再分批填充内容。共享导航、标题栏和重复结构只定义一次；生产实现遵循 Desktop 领域结构和 `@vetta/theme-ui` 的现有边界。

### Phase 3：一条完整纵向切片

每次只选择一个核心用户路径，例如“创建 → 保存 → 成功反馈”，并同时实现该路径的空、加载、错误和恢复状态。不要把多个半成品页面并行堆出来。

实现时：

- 消费已确认的 Visual Spec，不重新发明颜色、字体或布局语言；
- 优先复用 `shared/components/ui`、领域组件和既有模式；
- 用户可见文案全部走 i18n；
- 交互、状态、IPC、路由和异步行为按 Desktop `AGENTS.md` 的测试层级覆盖；
- 不为“看起来更丰富”添加没有用户目标支撑的统计、卡片、标签、渐变或动画。

### Phase 4：证据化审查

实现后必须先审查再润色，顺序固定为：

```text
用户目标 → 任务路径 → 状态反馈 → 信息层级 → 交互可预测性
→ 响应式 → 可访问性 → 视觉细节
```

截图应使用确定的窗口尺寸、确定的数据和确定的状态。对于重要组件，Storybook 的模式是为每个状态建立 story，并用截图与基线比较，以捕获布局、颜色、尺寸和对比度等回归；本项目可使用现有截图/E2E 能力实现同等证据，不要求引入 Storybook。[Storybook Visual Testing](https://storybook.js.org/docs/8/writing-tests/visual-testing)

审查结果按严重度记录：

- **P0**：不可用、内容不可见、关键操作失效、数据/状态误导；
- **P1**：任务明显变慢、层级错误、溢出/错位、核心状态缺失、响应式或可访问性不合格；
- **P2**：间距、颜色、圆角、动效或文案细节偏差。

一轮最多修复 3–5 个最高优先级问题；修改后只重新验证受影响的页面/状态。连续两轮没有新证据时停止盲目润色，记录剩余争议并交由人决定。

### Phase 5：交付门

只有同时满足以下条件，UI 任务才可标记完成：

- UX Brief、状态矩阵和 Visual Spec 已存在或在任务中明确记录；
- 主要路径可完成，失败和恢复路径可理解；
- 共享组件和 Token 没有重复事实源；
- 组件/Hook/IPC/E2E 测试覆盖本次行为风险；
- 截图或真实 UI 证据已检查，没有未解释的 P0/P1；
- 键盘、焦点、语义名称、对比度和目标尺寸符合项目要求；
- i18n、包边界、现有路由和主题规则没有回归；
- 交付说明列出未运行的验证、已知风险和需要用户决定的事项。

WCAG 2.2 将文本对比度、焦点可见/不被遮挡、键盘顺序和最小目标尺寸列为明确成功标准；这些不是“视觉加分项”，而是交付门的一部分。[WCAG 2.2](https://www.w3.org/TR/WCAG22/)

## 5. 给 Agent 的执行约束

### 5.1 权限和修改范围

- 规划/审查阶段默认只读；只有实现阶段修改生产 UI。
- 一次任务指定一个当前纵向切片和明确文件范围；不得无理由重写整个页面。
- 不允许同时存在两个主题、两个 Token 表或两个组件实现作为“临时方案”。
- 不得通过降低类型安全、删除状态或跳过截图来让任务变绿。

### 5.2 变更传播

- 改共享组件前先列出所有消费者和状态。
- 改 Token 前先说明影响的页面和明暗主题。
- 改术语前先搜索 i18n、文档、路由、菜单、通知和测试中的消费者。
- 改布局时同时检查窄窗口、长文案和空/错误状态。

### 5.3 视觉审查提示词模板

```text
你是 Desktop 产品的 UI 审查者，不要先评价“现代/漂亮”。
根据 UX Brief、状态矩阵、DESIGN.md 和当前截图检查：
1. 用户是否能在几秒内理解页面目的和下一步？
2. 首要信息和首要操作是否获得正确的注意力？
3. 空、加载、错误、权限、未保存和恢复状态是否真实可达？
4. 是否存在卡片堆叠、无意义统计、状态徽章膨胀、装饰性渐变或图标歧义？
5. 窄窗口、长文案、键盘焦点、对比度和点击目标是否合格？
请按 P0/P1/P2 输出“证据—影响—最小修复”，不要泛泛描述审美。
```

## 6. 衡量流程是否有效

在两个真实 UI 切片上试运行后，比较改造前后：

- 首次视觉验收通过率；
- 每个切片的视觉返工轮数；
- P0/P1 UI 问题在合并前发现的比例；
- Token/组件重复和 i18n 违规次数；
- 空、错误、权限和窄窗口状态的覆盖率；
- 从需求到设计确认、从设计确认到可交付的时间；
- 用户任务完成率、误操作率或支持反馈（如果有数据）。

不要把“Agent 写了多少代码”或“页面有多少组件”作为质量指标。流程的目标是减少用户理解成本和返工，而不是增加文档或代理数量。

## 7. 与现有 Desktop 规范的关系

本规则只增加流程门，不放宽现有硬性规范：

1. 先读本文件和 `user-language-ui.md`，明确用户问题与状态；
2. 再读 `DESIGN.md`，消费项目已有视觉 Token 和组件规则；
3. 实现后按 `ui-review.md` 审查；
4. 按 Desktop `AGENTS.md` 运行对应的组件、Hook、IPC 或 E2E 测试；
5. 只有在证据支持时才做第二轮视觉修改。

这套顺序把“设计专注度”从个人习惯变成可检查的工程流程，同时保留现有架构、i18n、测试和桌面端安全边界。

## 8. 参考资料与适用边界

以下资料用于形成规则，不是本仓库的替代规范：

- [Anthropic Claude Code frontend-design Skill](https://github.com/anthropics/claude-code/blob/main/plugins/frontend-design/skills/frontend-design/SKILL.md)：编码前的视觉方向和避免模板化设计。
- [SpecifyUI（arXiv, 2025）](https://arxiv.org/abs/2509.07334)：结构化、分层、可控的 UI 意图表示和迭代生成。
- [Microsoft HAX Toolkit](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/)：人机交互、AI 能力边界、反馈和失败恢复。
- [Google People + AI Guidebook](https://pair.withgoogle.com/guidebook-v2/)：用户需求、心智模型、信任、控制和优雅失败。
- [Material 3 theming](https://developer.android.com/codelabs/m3-design-theming)：语义 Design Token、主题一致性和可访问性。
- [Storybook Visual Testing](https://storybook.js.org/docs/8/writing-tests/visual-testing)：组件状态截图与视觉基线回归。
- [GOV.UK Design System](https://design-system.service.gov.uk/get-started/)：组件应复用、研究验证并记录适用范围；不要因为组件“看起来好”就跳过真实用户验证。
- [WCAG 2.2](https://www.w3.org/TR/WCAG22/)：对比度、焦点、键盘、目标尺寸和其他可访问性交付标准。

资料访问与核对日期：2026-09-01。研究结论只用于支持本流程的设计原则；具体实现仍以仓库源码、`AGENTS.md`、`DESIGN.md`、测试和可执行脚本为事实源。
