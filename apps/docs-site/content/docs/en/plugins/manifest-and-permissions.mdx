---
title: Manifest and permissions
description: Declare plugin identity, entry, styles, permissions, commands, network scope, and Agent contributions, and understand how grants are checked.
---

`plugin.json` sits at the root of the `.vettapkg` ZIP container, or inside its single top-level folder. The host validates identity, compatibility, and permissions from it before loading any code, so the manifest must match the build output.

The manifest structure has exactly one implementation: the TypeBox schema exported from `@vetta-org/plugin-sdk/manifest`. `PluginManifestSchema` serialises directly to JSON Schema, and `parsePluginManifest()` handles validation, defaults, de-duplication, relative-path normalisation, and cross-field constraints. The schema deliberately allows unknown fields so a newer manifest is not rejected outright by an older host.

```json
{
  "id": "my-plugin",
  "name": "My Plugin",
  "version": "0.1.0",
  "pluginApiVersion": "^2.0.0",
  "entry": "dist/mf-manifest.json",
  "moduleFederation": {
    "remoteName": "my_plugin",
    "expose": "./plugin"
  },
  "styles": ["dist/style.css"],
  "permissions": ["ui.slot.activity-tab", "agent.command.run", "network.fetch"],
  "commands": ["git"],
  "network": { "allowedHosts": ["api.example.com", "*.cdn.example.com"] },
  "defaultLocale": "en"
}
```

<Callout title="There is only one loading path" type="info">
  The manifest has no field for selecting a loading mode. A `runtime` field is rejected by the validator so a manifest never looks like it is choosing a path the host does not implement. The `agent_mode` field is deprecated and carries no runtime semantics; do not write it in new plugins.
</Callout>

## Paths and hostnames are normalised

Every manifest path is checked for escapes: absolute paths and drive prefixes are rejected, `.` and `..` are expanded, and climbing above the plugin root is an error. Installation checks again, requiring each declared resource to exist, to have the right type, and to stay inside the package root.

Each entry of `network.allowedHosts` and `browser.allowedHosts` is normalised too. `*` matches everything, `*.example.com` is a prefix wildcard, and entries carrying a port, username, or password are rejected. A wildcard does not match the bare domain: `*.example.com` does not cover `example.com`.

## Install directory and versions

User plugins are stored per version under `~/.vetta/plugins/<id>/versions/<version>/`. Installing a newer version is only recorded as pending; the app keeps loading the current active version until a reload switches over. While debugging, raise `version` and reload for a change to take effect reliably.

System plugins never enter that directory. They ship with the app, are rediscovered from a read-only location on every start, and have their declared permissions granted in full without the user being able to revoke them.

## Declare, approve, check

<Steps>
  <Step>
    ### Declare in the manifest

    List permissions in the `permissions` array of `plugin.json`. An undeclared permission can never be obtained.
  </Step>
  <Step>
    ### Approve at install time

    The user approves each permission on the plugin page. When an Agent installs from a local path, confirming can grant the declared set in one step.
  </Step>
  <Step>
    ### Check at runtime

    The host checks again when the API is called: declared and granted must both hold. A plugin can also inspect its own state with `ctx.permissions.has()` or throw deliberately with `require()`.
  </Step>
</Steps>

On update the host keeps permissions that were already granted and are still declared, does not auto-grant newly added ones, and does not restore permissions the user revoked. An empty grant record carries no information about what the user originally chose.

The manifest fields `agent.agents`, `agent.teams`, and `guidingWords` need no permission, and neither do `ctx.ui.notify` or `ctx.i18n`.

## commands is a second gate on execution

For `ctx.command.run` to launch a binary, the plugin needs the `agent.command.run` permission **and** the executable name must appear in the manifest `commands` array. A binary that is not listed is refused outright; a declared one can be toggled individually by the user in plugin settings, and calls are intercepted once it is off.

The host does not start processes through a caller-controlled shell, and `node`, `npm`, and `npx` are redirected to the host-managed runtime.

## Least privilege

Declare only what the plugin actually uses. A smaller set means an easier approval for the user and a faster review. Start from the minimal manifest, and when a host API reports a permission error, confirm the behaviour is really needed before adding the permission and re-running the approval flow. Do not copy another plugin's full permission array for convenience.

<Callout title="The build reconciles this for you" type="info">
  `@vetta-org/plugin-vite` scans the final JavaScript output during build and packaging. When it detects `registerTool`, `registerHook`, `registerSystemPromptProvider`, `registerContinuationProvider`, runtime tool toggles, or an `agent.toolPolicy` in the manifest without the matching permission, it fails the build. UI slots are not part of this check: a missing slot permission is only skipped silently at runtime, so verify those against [extension points](/plugins/extension-points/).
</Callout>

## Before publishing

<Steps>
  <Step>
    ### Check the archive layout

    Unzip the final `.vettapkg` and confirm `plugin.json` sits at the ZIP container root or in the single top-level folder, and that every entry, stylesheet, skill, and prompt file it references exists.
  </Step>
  <Step>
    ### Verify the permission prompt

    Run a fresh installation and confirm the prompt matches the manifest with nothing extra.
  </Step>
  <Step>
    ### Exercise each capability

    Trigger every capability, including how it degrades after a permission is revoked. A working development link is not a substitute for testing the published archive.
  </Step>
</Steps>
